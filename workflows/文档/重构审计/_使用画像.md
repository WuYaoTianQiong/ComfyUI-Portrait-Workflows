## 2. 结构性事实：提示词 100% 是碎片格式

- 308 条提示词中，**0 条**是纯文本（无 `【类型】` 标记）。
- 类型数分布：8 类 157 条、7 类 106 条、6 类 27 条、5 类 4 条、4 类 1 条、3 类 13 条。
- 实际出现的类型名共 **8 种**，与 `shared.py:FRAGMENT_TYPES` 一致。
- 被引用最多的类型：人物面部 302、姿态动作 297、人物服饰 295、拍摄视角 293、场景环境 291、画风技术 285、光影色调 242、人物身材 218。

**结论**：`【类型】内容` 不是"一种可选的写法"，而是这个项目的事实标准数据格式。
`Prompt.prompt` 是唯一真源；`Fragment` 表（0 行）和 `prompt_tags`（0 行）是失败的抽象。

## 4. 真正在用的

- **图片标签**：136 个标签、1121 次关联，平均每张图 0.93 个标签 → 这是用户唯一的整理手段。
- **组合模板**：358 条，平均 6.4 个碎片/条；但创建时间高度集中在 2026-07-05（211）、07-10（63）、07-17（44），之后每月新增 <10 条 → 属于**批量沉淀**，不是持续创作。
- **图片库**：1206 张，其中 `comfyui_sync` 543、`disk_scan` 350、`local`（经本项目任务生成）313。
- **任务**：最近一次 2026-10-15 18:01，共 109 次；失败 27 次（24.8%），失败原因全部是 `任务提交到 ComfyUI 失败（无 prompt_id）`，即提交时 ComfyUI 不可达，但前端仍允许提交。

## 5. 数据模型缺陷（由数据反推）

1. **画廊"最新"排序不可信**：`gen_history.created_at` 是**入库时间**，不是出图时间。
   - 任务生成的图（313 张）入库时间≈出图时间，没问题。
   - 同步/扫描进来的 893 张图，入库时间是批量导入那一刻（同步代码 `history.py:193` 明确注释"刻意不刷新 created_at"）。
   - 结果：占 74% 的图片按"最新"排序等于按"导入批次"排序，用户感知为"排序乱了"。
   - 缺失字段：文件 mtime / PNG 内嵌 `prompt_id` 对应的生成时间。
2. **图片与提示词的关联率只有 31%**（374/1206）。同步进来的图即使 ComfyUI history 里有 `prompt_id`，也只有部分能对上本地 `prompts` 表。
3. **任务失败没有可操作的反馈**：27 次失败只有一句"无 prompt_id"，用户无法知道是 ComfyUI 未启动、工作流缺节点，还是提交超时。
4. **`unknown` 状态 7 条**：任务完成后状态既不是 done 也不是 error，说明状态机存在无法收敛的分支（`jobs.py:206`）。

## 6. 对重构的直接含义

1. **减法优先**：碎片库、提示词标签关联表、评级、图片收藏、分类管理这 5 个功能 **零使用**，合计约 1/4 的前端交互面积。先删/藏，收益立竿见影且风险最低。
2. **主线是"结构化组合 + 图片整理"**：提示词、模板、组合三者在数据上已经是同一个东西（8 类碎片），应合并为一个"组合（Composition）"模型，而不是三个 Tab/三套 CRUD。
3. **画廊排序必须修**：这是用户能直接感知的"不统一"。补 `captured_at` 字段（文件 mtime 或元数据）并回填，成本低、收益高。
4. **失败要能解释**：把任务失败原因结构化（ComfyUI 不可达 / 工作流校验失败 / 节点缺失 / 超时），并在提交前做前置校验。
