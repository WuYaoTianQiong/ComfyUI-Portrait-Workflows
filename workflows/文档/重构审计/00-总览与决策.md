# 00 · 总览与决策：把五套平行实现收敛成四条主干

> 输入：6 份分报告（01 后端/02 前端/03 UX/04 视觉/05 任务/06 工程）+ `_使用画像.md`（生产库只读统计）。
> 本文件是**决策版**，只保留"要做什么、按什么顺序、怎么验收、哪里会翻车"。细节回查分报告。

## 0. 五句话结论

1. **代码不算烂，问题是"同一个东西被实现了 2–4 遍"**：同一份提示词文本有 7 种存储形态、同一个"跑图"有 8 条提交路径、同一个列表有 Jinja 和 JS 两套渲染、同一套分类/标签有 5 种筛选控件。所以每加一个需求都要在 N 处同步改，改漏一处就变成"点了没反应"。
2. **数据证明该做减法**：`fragments` 0 行、`prompt_tags` 0 行、提示词评级 0 条、图片收藏 0 条、用户自建分类 0 个——这 5 个功能占了提示词 Tab 与画廊侧栏的不少位置，但从未被使用。
3. **眼下的痛有一半是"坏"而不是"乱"**：跨页全选（`/api/history/ids` 恒 422）、导出（被 `/{prompt_id}` 遮蔽）、热门标签（NameError）、**手动给图片加分类/打标签（NameError）**——最后两个恰好是用户唯一的整理动作。这些是 1 天内能修好的。
4. **真正的重构不是换框架**，而是把四条主干各留一条：内容（提示词/模板/碎片/组合 → 一个 Composition）、任务（8 条提交 → 一个 Job 服务 + 一条 SSE）、素材（提示词/图片 → 一套 taxonomy 查询）、界面（5 Tab → 3 入口 + 2 共享层）。
5. **顺序**：安全网 → 修死路 → 任务主干 → 内容主干 → 界面收敛 → 视觉统一。每批 1–5 天、独立可回滚、改造期用户不中断。

| 病根 | 表现 | 后果 |

## 3. 目标：四条主干各留一条

### T0 渲染边界 = **保留 JS 渲染，删除 HTMX 实验分支**（先裁决，否则后面全打架）

事实修正：默认模式其实是 **JS 单轨**——`app.js:69` 只有在 `?htmx=1` 或 `localStorage.htmxMode=1` 时才启用 HTMX，否则在 DOMContentLoaded 前剥掉全部 `hx-*`。所以 Jinja 那一套是休眠实验，而且已经落后主路径三个功能：分页切页丢分类/标签、分面 chip 只改 UI 不发筛选、`openCreateFragmentModal` 在全仓不存在。

裁决：**保留 JS 渲染，删除 HTMX 分支**（排在状态收拢之后，HTML 端点最后删）。理由：
- 它已是默认路径，且只有它具备全功能；
- HTMX 分支每加一个筛选项要改 4 处（JSON 端点、HTML 端点、Jinja 模板、`hx-vals`），而它省下的"拼 HTML"被"其余 90% 界面本来就手写 HTML"抵消；
- `vendor/htmx.min.js`（51KB）在默认模式下是纯下载成本。

落地规则（写进 README）：**JS 渲染只从 store 取数，渲染函数里不发请求、不改状态；新代码用 `data-action` 事件委托 + `<template>` 克隆，禁止字符串拼 HTML**。M0 先冻结（新筛选项一律只进 JSON 路径）→ M3 删开关/分支/库 → M4 最后删 3 个 `/html` 端点与 4 个模板。

### T1 内容主干 = **Composition**

```
Composition = { name, negative, fragments: [{type, content, source}] }
source = literal（写死的文本） | ref（引用某条 Composition + 类型）
```
- **Prompt** = 全部 literal 的 Composition（现有 308 条 100% 符合，无需迁移数据）
- **Template** = 含 ref 的 Composition（现有 358 条 + 2308 引用，无需迁移）
- **Composer 草稿** = 尚未保存的 Composition
- **碎片库** = 删除（0 行）
- 落地方式：**不建新表**，新增 `services/composition.py`（parse / render / validate / materialize），把现有三张表投影成同一组 API：`GET /api/compositions?kind=prompt|template`、`POST /api/compositions/{id}/materialize`。
- 立刻可做的收益：4 份 `【】` 正则合并为 1 份；"另存为提示词/保存模板"变成同一个动作的两种 kind。

### T2 任务主干 = **一个 Job 服务 + 一条 SSE**

```
前端：submitTask({kind, source, workflow, params, count}) → job_id
后端：JobService.submit() → 唯一写者不断推进状态 → SSE 推送
前端：JobStore 一条连接订阅所有活跃任务 → 任务抽屉渲染
```
- 8 条提交路径收敛为 1 个 `submitTask`，UI 上的"跑图/变体/试跑/批量/换脸"只是**预设参数**。
- 取消归属到 job（现在是全局 `batch_stop_flag` + `ClearQueue`，取消 A 会杀掉 B）。
- `GET /api/jobs/{id}` 改为纯读；状态推进只在单写者里发生。
- SSE 而非 WebSocket：单向、原生重连、无构建依赖；多任务复用一条流（HTTP/1.1 同源 6 连接上限）。

### T3 素材主干 = **Asset + 一套 Taxonomy**

- 提示词和图片共享一套分类/标签**查询**语义：`taxonomy.py` 提供 `tags_for(kind,id)` / `counts(kind)` / `filter_ids(kind, cat, tags)`。
- 本期**不合并**四张关联表（迁移风险高、收益低）；先把"两套计数口径"和"图片标签快照 vs 来源提示词"统一成**查询时派生**（自打标签 ∪ 来源提示词标签），废弃 `count_scope` 双实现。
- 一个筛选参数解析器，所有列表端点共用（`/prompts`、`/history`、`/composer/fragments`、`/html`）。

### T4 界面主干 = **3 个入口 + 2 个共享层 + 1 个能力描述符**

```
顶部：工作流 ▾（带能力徽标） | 生成参数条 | ComfyUI 状态 | 任务(N) | ⚙
① 素材库   列表/网格切换，实体=提示词|图片|模板；共用筛选面板 + 详情面板
② 创作台   模式=组合拼接|双图换脸；共用选图器 + 参数条 + 提交
③ 设置     统计（降级为概览条）、工作流管理、清理、导入导出、日志
共享层 A：任务抽屉（任何页面可见，进度/停止/结果缩略图）
共享层 B：选图器（画廊/文件夹两种来源，带分类标签筛选）
```
- **工作流能力描述符** `GET /api/workflows/{path}/capabilities` → `{supports:{quality,orientation,images,mask}, params:[...]}`。UI 按能力渲染参数，删掉 `ui.js:168` 的"按 Tab 隐藏控件"和换脸页那句"顶部控件不生效"。
- 不再让画质/横竖屏做"页头全局态"，改为每个提交按钮上方的**参数条**（值仍存 `UiState`）。

## 5. 三条铁律

1. **不先补测试就动业务代码**。这个仓库没有 CI、没有 exit code、数据库是唯一真源，未覆盖的改动既发现不了也回滚不了。
2. **不做一次性大改**。不换框架、不引构建工具、不一次性统一 91 个端点的返回结构、不一次性格式化全库。所有变更"加键不删键、旧路由转调新 service、前端开关灰度、观察一周再删旧"。
3. **不删用户已经形成的路径**。`选中 → 跑图 → 看结果` 的肌肉记忆、换脸双栏"切模式不丢选择"、详情面板底部的就地生成历史——这些是好评点，收敛时必须保留。

## 7. 明确不做

- 不引 React/Vue/Vite（当前"双击 bat 即启动"是最大部署优势；如要做，排在 B5 之后单独立项，且必须保留无构建回退）。
- 不在状态收拢前删 HTMX（先冻结、再删开关、再删库、最后删 3 个 `/html` 端点与 4 个模板）。
- 不引 Alembic/SQLAlchemy/Celery/Redis/多进程（单用户本机工具，复杂度收益为负）。
- 不合并四张分类关联表（本期）；不拆 `gen_jobs.items` JSON（本期）。
- 不做全量 async 化（SSE 先用同步生成器，async 单独立项）。
- 不做 DOM 快照/视觉回归测试（维护成本 > 收益）。

## 8. 需要你拍板的 4 件事
