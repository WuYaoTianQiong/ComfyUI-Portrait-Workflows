# 06 · 工程保障与迁移路径

## 0. 结论先行

1. 现有唯一安全网 `verify_smoke.py` **不能**当回归基线：它没有 `sys.exit(1)`，失败也返回 0；而且它通过 `/api/history_sync` **写入生产库**（`verify_smoke.py:165,323` → `routers/history.py:300-312`）——"跑测试"本身就是一次数据变更。
2. 三个最大根因：**无隔离**（测试/脚本/迁移全部指向 `config.py:76` 单例库）、**无失败信号**（exit code + 断言 + 85 处 `except Exception` 中 19 处裸 `pass`）、**无回滚粒度**（单分支 main，3.06MB 二进制库与代码同 commit）。
3. 顺序只能是：**冻结 → 隔离 → 契约测试 → 才允许动第一行业务代码**。任何"先重构再补测试"的方案在这个仓库等于裸奔。
4. 重构期用户不中断的机制是"同路径内部并行 + 加键不删键 + 前端开关灰度"，不是 `/v2` URL 版本化（前端 100+ 调用点改不起）。

2. **`/api/prompts/export` 被 `/api/prompts/{prompt_id}` 遮蔽**：注册顺序实测 `[3] /prompts/{prompt_id}` 在 `[9] /prompts/export` 之前（`routers/prompts.py:317` vs `:531`），导出请求会走到 `get_prompt` 并 422。`prompt.js:1469` 的导出按钮是坏的。

## 2. 根因分析（为什么会长成这样）

1. **验证方式被固化成"人读输出"**：`verify_smoke.py` 的 docstring 写的是"彻底闭环验证"，实现却以"打印给人看"为终点（`:338-343`）。没有退出码这个细节，决定了它只能是脚本，不能是门禁——这是个习惯问题，不是能力问题。
2. **配置是模块级单例**：`config.py:84` 的 `settings` 在 import 时求值，`models.py:9` 的 `db` 也在 import 时绑定路径。于是"用别的库跑一次"没有一等公民入口，测试、迁移演练、冒烟只能打生产库。这是所有隔离问题的总闸。
3. **迁移被写成启动自愈**：`init_db()` 把建表、加列、改索引全塞在启动路径（`models.py:368-420`），`_migrate_column` 失败静默（`:249-258`）。好处是用户永不"迁移失败"，代价是没有版本、没有 dry-run、没有回滚点，且顺序敏感（`:372-374` 的注释就在提醒这件事）。
4. **monorepo 把二进制真源和代码放进了同一个可回滚单元**：db 每次刷新都产生新 commit，导致"回滚代码"和"回滚数据"耦合；反过来，为了不丢数据，任何重构都不敢碰 schema。

### U5 · stdlib logging（一次到位）｜M
**现状**：45 print、无 ID、无耗时、cp936 乱码。**目标**：一个 `logging_setup.py`（约 60 行），所有模块 `logger = logging.getLogger(__name__)`。
**最小改法**：

**验收**：`grep -r "except Exception" -A1 | grep pass` 为 0。**工作量 M（1 天，与 U2 合并跑）**。

### U7 · 数据安全：备份 + 版本化 SQL（不引 Alembic）｜M
**为什么 `safe=True` 不够**：`create_tables(safe=True)` 只做 `CREATE TABLE IF NOT EXISTS`——不 `ALTER`、不建部分唯一索引（`models.py:117-121` 已明说索引靠手写迁移）、不检测失败（`_migrate_column` 失败即 `pass`）。它适合"启动自愈"，不能承担"可回滚变更"。
**为什么不需要 Alembic**：单 SQLite、单进程、无 SQLAlchemy、库仅 3MB、无多环境；Alembic 的 autogenerate 在 peewee 上还要另写一层。**用 60 行 `migrate.py` + `PRAGMA user_version`**（当前 =0，第一步就 bump 到 1 建立基线）。
**改表三步法（每次 schema 变更照抄）**：
1. **冻结与基线**：停服务（或只读）→ `tools/db_backup.py` 用 `sqlite3.Connection.backup()` 生成 `文档/备份/提示词收藏_backup_YYYYMMDD_HHMMSS.db`（**不要文件复制**，`journal_mode=delete` 下运行中复制可能撕裂）→ 记录 `integrity_check`、12 张表行数、索引清单到 `备份/baseline_YYYYMMDD.json`。
2. **副本演练**：写 `migrations/00N_xxx.py`（幂等 SQL、单事务、成功才 `PRAGMA user_version=N`）→ `PB_DB_PATH=<副本> python migrate.py --to N` → 在同一副本上跑 `pytest` 全部契约测试 + 行数/索引 diff（必须与期望值逐项相等，不是"看起来对"）。
3. **生产执行 + 验收 + 回滚**：生产跑 `migrate.py --to N` → 冒烟 + 5 分钟手动清单（首屏画廊、收藏、筛选、单张跑图）→ 失败则：停服 → 还原备份 → `git revert` 对应代码 commit → 再验。**数据回滚永远走备份，不走 git**。
**工作量 M（1.5 天）**。

### U8 · Git 与发布流程｜S
**整理步骤（在动代码之前一次做完）**：
1. `git switch -c feat/faceswap`，把在途功能**先落地**：`routers/{faceswap,fsbrowse}.py`、`static/faceswap.{js,css}`、`static/img-missing.svg` + 其依赖的 `main.py/routers/*` 改动。**先跑冒烟**（`verify_smoke.py` 已覆盖 faceswap 与 fs/list），再 merge 回 main。理由：这批改动是"已完成待发布"，不是"重构半成品"，混在重构分支里会让每一次 revert 都可能回滚掉功能。
2. 剩下的改动逐个 `git add -p` 审：属于重构前置的（防缓存、SPA fallback、元数据容错）单独 commit；不确定的留在工作区，不进重构分支。
3. `git tag pre-refactor-20261018`（回滚锚点）。4. `git switch -c refactor/p0-safety`。
**commit 粒度**：1 个 U = 1 个 commit；**测试先行**——`测试(contract)：新增 C1/C2/C10（2 条 xfail 记录已知破损）` → `重构(history)：抽出筛选构造器（契约 C3/C7/C8 全绿，行为不变）` → `测试(contract)：C4 转绿，移除 xfail`。沿用仓库既有中文前缀风格（`重构/修复/测试/数据/文档`），不要为了 Conventional Commits 破坏 144 条历史的可读性。**DB 变更只出现在 `数据：` 提交，永不与代码同 commit**。
**回滚策略**：每个 commit 独立可 `git revert`；tag 用于整段回退；数据走 U7 备份；发布=merge 到 main + tag `v4.x.y`。
**pre-commit：值得加，但只加"抓真错"的**。`.pre-commit-config.yaml` 三个 hook：`ruff check --select E9,F63,F7,F82,F821 --fix`（语法错/未定义名，零风格噪音）、`node --check`（本地 hook，仅暂存 js）、`check-merge-conflict`。**明确不启用** `black`/`ruff format`/`trailing-whitespace`：现有 25 py + 22 js 一次性格式化会产生淹没真实改动的 diff，且 `core.autocrlf=true` 会放大行尾噪音。等 P3 收敛后再单独一个 commit 做格式化。**工作量 S（半天）**。

### U9 · 并行迁移模型 + 作战顺序｜L
**并行策略（用户全程可用）**：
- **不做 URL 版本化**：前端 100+ 调用点，改路径的风险远大于收益。
- A **同位薄壳**：新逻辑下沉到 `services/`，旧路由保留 1 行转调。契约测试证明"新旧等价"后才删旧逻辑（这一步对用户完全不可见）。
- B **加键不删键**：返回结构变更只增键；前端"有旧键用旧键，无旧键用新键"；观察 1 周后删旧键，并把"旧键不存在"写成断言。
- C **前端开关灰度**：`localStorage.pbImpl="new|old"`，默认 new，异常时一键回 old（与现有 `UiState` 同机制，不新增架构）。
- D **删旧**：删薄壳、删开关、删旧键；C1 路由快照此时会显式变红——这是"允许的破坏"，必须人工确认后改快照。
- **每阶段 DoD**：15 契约全绿 + `verify_smoke.py` exit 0 + 5 分钟手动清单 + `app.log` 无新增 ERROR/Traceback + 用户操作路径不增加点击。

## 4. 明确不建议做的事

1. **不要引 Alembic / SQLAlchemy**：单库 3MB、单进程、无多环境，迁移框架本身的复杂度超过被管理对象。`user_version` + 幂等 SQL 足够。
2. **不要做全量回归/追求覆盖率数字**：15 条契约 + 3 条 E2E 已覆盖 90% 的重构风险；追覆盖率会去测 `verify_smoke.py` 里那些一次性的路径探测。
3. **不要做 DOM 快照/视觉回归**：52KB HTML + 100KB CSS，维护成本高于收益。
4. **不要一次性 `black`/`ruff format` 全库**：会让第一个重构 commit 变成 5000 行 diff，回滚粒度直接丧失。
5. **不要 `git rm --cached` 把 db 从仓库移除**：3MB 换来的是可追溯的数据历史与单机灾备，删掉反而增加"数据只存在于一个文件"的风险。要的是"DB 只在 `数据：` 提交里变更"。
6. **不要在重构期切 WAL / 多 worker / async**：并发模型变更会让所有契约测试的时序假设失效，必须等 P3 之后单独立项。
7. **不要为了测试可跑而给生产代码加 `if TESTING` 分支**：用 `PB_*` 环境变量 + 依赖注入（`fetch_json` 可 monkeypatch），生产路径零特判。

## 5. 与其他分报告的交叉点（预期冲突）

1. **与架构报告的"统一 API 返回结构"**：我会反对一次性统一。`items/prompts/jobs/categories` 的混用必须走"加键不删键 → 前端切换 → 删旧"，否则 100+ 调用点同时炸且无法灰度。**契约 C2 是这条的护栏**。
2. **与前端报告的"引入构建工具/框架"**：当前"无构建"是唯一零故障的部署优势（`启动.bat` 双行启动）。我主张先上 `node --check` + 3 条 E2E，把构建工具排到 P3 之后；若前端报告坚持，需要它自己提供"构建失败时仍能启动"的回退方案。
3. **与数据模型报告的"合并 4 张分类关联表"**：技术上合理，但**必须排 U7 之后**——没有 `user_version` + 副本演练 + 行数对比，这类迁移在这个仓库不可回滚。请它把方案写成"可幂等重放的 SQL"而非"ORM 直接改模型"。
4. **与后端报告的"全量 async/异步 httpx"**：会同时改变 `job_monitor_loop`（`main.py:25-55`）与 `jobs.py` 轮询的时序假设，并让 86 处 `except` 的语义再次漂移。前置条件是 U2 的 ComfyUI mock + U1 的 C6 幂等断言先绿。
5. **与 UX 报告的"删掉重复批量面板"**：删除前必须有 E2E 覆盖换脸/组合两条路径（`#fsPanel`/`#batchPanel` 是两套独立 DOM），否则删完无法验证。我的 P3 才具备这个能力。
6. **共识点（预计无冲突）**：`print` → `logging`、`except pass` → 记录、DB 备份、分支与 tag、pre-commit 只做静态错误检查。
