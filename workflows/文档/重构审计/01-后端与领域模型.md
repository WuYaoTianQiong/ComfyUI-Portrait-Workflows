# 01 · 后端与领域模型审计

> 审计对象：`main.py`、`models.py`、`config.py`、`shared.py`、`state.py`、`routers/*.py`、`services/*.py`（只读）。
> 实测口径：`@router.*` 91 个（简报记 100，差异来自计数方式）；`except Exception|except:` 60 处；`print` 34 处；`atomic/transaction` **0 处**。

## 0. 结论先行

- 领域模型不是设计的产物，是 5 个 Phase 各自加表堆出来的：**同一个概念有 2–4 份存储，只有 `Prompt.prompt` 是真源，其余全是无失效策略的快照**。
- 分类/标签是"四表拷贝 + 五条计数口径"，同一张画廊筛选面板并排取两个数，**必然不相等**（`gallery.js:440` / `gallery.js:448`）。
- API 没有契约：9 种集合键、3 种分页、5 种错误形状、`/api/tags/popular` 与 `/api/history/ids` **当前必挂**。
- 全仓 0 个事务；7 处"建 job → push → 回写"无边界；写失败一律 `except: pass`，且已有代码注释自认"这条路径从未写入过任何一条记录"（`routers/history.py:174-179`）。
- 现有 1206 行历史图里 1159 行是软删墓碑，104 组文件名重复（单组最多 5 行）——软删 + 部分唯一索引的组合没有兑现注释里承诺的 upsert。

## 1. 现状盘点

### 1.1 八个实体，实际只有五个概念

| 概念 | 存储形态 | 关系证据 |
|---|---|---|
| 提示词文本 | `Prompt` / `Template` / `Fragment` / `TemplateFragment` / `GenHistory.preview` / `prompt_params.prompt` / `GenJob.items[].prompt_preview` | 见 1.2 |
| 提示词类型分类 | `Category`（`PromptCategory`）+ 图片侧 `ImageCategory` | `models.py:125-171` |
| 标签 | `Prompt.tags` 字符串 + `Tag`/`PromptTag` + `ImageTag` | `prompts.py:114`（字符串匹配）vs `prompts.py:125`（关联表） |
| 出图 | `GenJob.items[]` ↔ `GenHistory` 行 | `jobs.py:264-304` 把 item.images 投影成 history 行 |
| 组合模板 | `Template` + `TemplateFragment`，且 `/templates/as_items` 伪装成 prompt 行 | `templates.py:126-133`（`tags:"📦 组合模板"`、`_is_template`） |

- `Template` 本质是"由引用构成的提示词"：`TemplateFragment(prompt_id, fragment_type)` 就是 `Prompt.prompt` 里 `【】` 切片的指针（`templates.py:16-30`）。
- `Fragment` 是"切片内容的独立副本"，而 composer 同时从 Prompt 文本和 Fragment 表取内容、按 `type||content` 去重后混成一个池（`composer.py:44-100`）——同一段文字两个写入口、零同步。
- `GenJob.items[]` 与 `GenHistory` 是同一张图的两份投影；items 里还嵌套了 JSON **字符串** 形式的 `prompt_params`（现库 1222 个 item 中 129 个如此，其余是对象/缺失）。

### 1.3 四张关联表的拷贝式设计带来的具体不一致

**A. 计数口径 5 种**，字段名却都叫 `prompt_count`：
1. `/categories` 默认 → `PromptCategory` 计数（`categories.py:60-62`）
2. `/categories?count_scope=image` → `ImageCategory` 计数（`categories.py:78-80`）= **快照口径**，仅覆盖 171 张
3. `/tags?count_scope=image` → `UNION(image_tags, prompt→image_tags)` 去重（`tags.py:29-42`）= **活口径**，与 2 不是同一件事
4. `/tags` 默认 → `PromptTag` 计数（`tags.py:50`）；现库 `prompt_tags` **0 行** → 全部返回 0，而 `tag.js:137` 显示成"N 个提示词"
5. `/stats` 的 `top_tags` → `Tag.usage_count`（`stats.py:20-23`）；136 个标签该值**全为 0**

**B. 删除级联三套**：`categories.delete` 只递归删子分类，不删 `PromptCategory`/`ImageCategory`/`Template.category`（`categories.py:112-132`）；`tags.delete` 只删 `PromptTag`，不删 `ImageTag`（`tags.py:97-104`）；`prompts.delete` 删三表但不删 `TemplateFragment`（`prompts.py:483-486`）。现库 `pragma foreign_key_check` 有 **133 条违规**（`template_fragments → prompts`，涉 36 个已删 id）——FK 声明存在，但历史写入路径从未受它约束。

**C. 批量清理清单不一致**：单删与 `/prompts/batch_delete` 清理项不同（`prompts.py:483-486` vs `597-600`）；`/history/batch_delete`、`clear_history` 只置 `is_deleted`，不清 `image_categories`/`image_tags`（`history.py:679,733`）——现库 171 + 1121 行关联**全部挂在已软删图片上**。

**D. 导入导出丢分类法**：`/prompts/export` 只导 prompts 表列（`prompts.py:537-547`），不含分类/标签/关联；`/prompts/import` 不重建关联（`571-578`）；`templates` 只有 `batch_import` 没有 export（`templates.py:246`）。真正的标签数据是 `Prompt.tags` 文本（292/308 有值），与 `Tag` 表零同步。

**E. `count_scope` 语义不清**：只切计数来源，不改字段名、不改前端文案，且 categories 与 tags 对 "image" 的定义不同（快照 vs 活算）。自动分类还靠**魔法名称**匹配（"组合创作" `prompts.py:443-449`；"片段提示词" `models.py:271`），`Category` 没有"系统/用户"类型列，改名即断。

### 1.4 API 契约混乱程度

- 14 个 `response_model=dict`（等于没有契约）；58 处 `{"success": True}`；9 种集合键：`items/prompts/jobs/tags/categories/templates/workflows/grouped/ids`。
- 分页 3 种：`page+page_size`、`limit`、无；`/templates/as_items` 伪造 `page=1,page_size=999`（`templates.py:134`）。
- **同一资源两种类型**：`/jobs` 的 `items` 是 JSON 字符串（`jobs.py:33`），`/jobs/{id}` 的 `items` 是数组（`jobs.py:224`）。
- 错误形状 5 种：`{"detail": str}`；`{"valid": false, "error": ...}` 且 200（`comfyui.py:300`）；`{"comfyui":"offline"}` 200（`124`）；部分成功 `{"success":true,"errors":[...]}`（`prompts.py:584`）；裸 422 pydantic。没有全局异常处理器（`main.py` 只有 CORS 与 SPA 中间件）。
- 删除响应的 `deleted` 字段有时是 int、有时是 dict（`prompts.py:601` vs `487`）。
- **当前必挂的端点**（不是风格问题）：
  - `/api/tags/popular` → `NameError: count_scope`（`tags.py:114`，签名只有 `limit`）。
  - `/api/history/ids` → 装饰器挂错在 `_facet_base`（`history.py:498`），它要求 4 个必填 query；真实现 `history_ids` 无装饰器（`564-607`）→ 前端 `gallery.js:211` 传 favorite/sort/search/orientation，必 422。
  - `/api/history/{id}/categories|tags` → `Category`/`Tag` 未 import（`history.py:922,943`；导入见 `13`）→ 500。即"给图片打分类/标签"在 API 层完全不可用。
  - `/api/templates/batch_import` → 缩进错误，`TemplateFragment.create` 在 for 循环外（`templates.py:253-268`），只写最后 1 条，异常 `except: pass`。
- **必须保留的兼容点**（前端硬依赖，迁移前不能动）：`/api/{prompts,history,fragments}/html`；`/api/templates/as_items`；`/api/prompts/position`（0-based index）；`/api/history/ids`（要修不要删）；`/api/{tags,categories}?count_scope=image`、`?tree=true`；`/api/history/facets` 的 source/date/model/orientation 四键；`/api/jobs/{id}` 顶层字段；`/api/prompts` 的 `prompt_preview` 60 字截断；`/api/stats` 五字段；`/api/{image,thumbnail}` 的 `filename/subfolder/type(+v)`；`/api/fs/{list,thumb,image}` 的 `path`。

### 1.6 事务与一致性

多步写入全部无事务边界：

1. 提示词创建 + 自动分类（先清旧分类再建新的）：`prompts.py:438-449` + `models.py:304-319`
2. 单删/批删：3–4 条 DELETE 后才删主行，中途失败留半删状态（`prompts.py:483-490`）
3. 模板创建：`Template.create` 后逐条建碎片，异常返回 400 但模板行已落库（`templates.py:156-179`）
4. 模板更新：先删全部旧碎片再插新的，失败即清空（`templates.py:196-212`）
5. 出图入库：upsert history + 继承分类，逐图 try/except（`jobs.py:264-317`）
6. 任务状态回写：`GET /jobs/{id}` 每次写（`jobs.py:208`）+ 5s 监控循环写（`main.py:31-43`），无锁 → 后写覆盖先写
7. 历史同步：upsert + 回填分类（`history.py:162-208`）

**会被静默吞掉**：`history.py:209` 的 `except: pass` 包住整段 upsert（注释自认曾让同步"从未写入任何一条记录"，`history.py:174-179`）；`jobs.py:316` 同样包住入库，任务显示 done 但画廊无图时只 `print` 一行警告（`jobs.py:159-161`）；`templates.py:267` 包住导入；`comfyui.py:201` 包住落盘。

**读接口带副作用**：`/jobs/{id}`（写）、`/history`（`_enrich_item` 内补写 `prompt_id`/`prompt_params` 并继承分类，`history.py:58-66`）、`GET /history_sync`。

**软删 + 部分唯一索引不成立**：索引带 `WHERE is_deleted=0`（`models.py:358-362`），软删行不再参与唯一性 → 现库 1206 行中 1159 行软删、104 组 `(filename,subfolder,img_type)` 重复（最多 5 行/组）。注释宣称"同 upsert 覆写旧记录、标签不丢"（`models.py:339-341`）只对活行成立。

### 1.7 为了迁就前端而存在的后端形状（不评价前端）

3 个 HTML 片段端点 + Jinja 模板（`prompts.py:219`、`history.py:750`、`fragments.py:150`）；`/templates/as_items` 返回假 prompt 行；`/prompts/position` 为滚动定位全量取 id（`prompts.py:169-173`）；`count_scope=image`/`tree=true` 只为画廊筛选面板；`/history_sync` 把"同步"和"首页数据"打包且允许 GET（`history.py:614-626`）；`/composer/fragments` 保留 `total_prompts: 0` 兼容字段（`composer.py:119`）；`/thumbnail` 的 `v` 参数后端不参与逻辑（`comfyui.py:233`）；`/generate_missing/{count,list}` 为确认弹窗（`comfyui.py:569-611`）；`/fs/*` 直接暴露本地文件系统（无白名单，仅 127.0.0.1，`fsbrowse.py:1-5`）；`Template.category` 是第三条分类链接但 358 个模板全为 NULL。

## 2. 根因分析

- **R1 迭代只加不改**：`Phase 1/2/3/4/5` 注释遍布 `models.py`；每期新表不复用旧表，迁移靠 `_migrate_column` + 双重 try/except（`models.py:249-258`），无版本号、无回滚，于是"表比模型新"——`prompts` 已有 `scheduler/lora_name/steps_2/...` 9 列（当前全空），`template_fragments` 有 `fragment_id` 列（2308 行 0 非空），`models.py` 都不认识。
- **R2 没有领域层**：业务逻辑长在路由里，所以每加一个入口（HTML 端点、批量、换脸、补图）就复制一遍筛选/序列化/提交链；7 处提交链的差异纯属复制时手滑（`comfyui.py:390` vs `450` vs `481` 参数集各不相同）。
- **R3 没有"写成功/失败"语义**：SQLite + 无事务 + `except: pass`，一致性靠"下次轮询/同步会再写一遍"兜底，而兜底本身也被吞。
- **R4 计数器当真相**：`Prompt.usage_count`、`Tag.usage_count`、`Fragment.usage_count`、`preview`、`cached_content` 都是"写一次就没人维护"的冗余列；`Fragment.usage_count` 全仓无任何写入点，`Tag.usage_count` 现库全 0。
- **R5 前端的渲染形态反向渗进契约**：只要前端需要，就新增一个端点或一个兼容字段，而没有一处把"同一资源一种形状"作为约束。

## 3. 统一机会清单

**U1 提示词文本单一真源（S–M）**｜现状：7 份形态，4 种不同的 `【】` 解析。→ 目标：`Prompt.prompt` 为唯一可编辑文本；`Fragment` 增 `source_prompt_id` 成为派生视图或直接并入；`cached_content` 改为带 `source_updated_at` 的快照；`preview`/`prompt_params.prompt` 停止写入。→ 最小改法：先统一 `shared.fragment_lang`（1 个 parser + 1 个 stripper），让 4 处调用同一函数；再让 `_resolve_fragment` 返回 `stale` 标记。→ 影响：`shared.py`、`models.py`、`templates.py`、`comfyui.py`、`composer.py`。→ 风险：模板内容可能变化（历史快照 vs 实时）。→ 工作量 M。

**U2 图片分类法改为查询时派生（M）**｜现状：`ImageCategory`/`ImageTag` 是 Prompt 侧的快照副本，靠 `inherit_prompt_taxonomy`（`models.py:173`）单向补写，计数口径因此分裂。→ 目标：图片分类法 = `图片自有标签 ∪ 来源提示词标签`（`history.py:419-421` 已经这么查了），删除快照表或降级为"用户手动覆盖"。→ 最小改法：先把**读**路径全部切到活口径（一个 `effective_taxonomy(image_id)` 函数），写路径保留；`count_scope` 只留一个实现。→ 影响：`models.py`、`history.py`、`categories.py`、`tags.py`。→ 风险：手动改过的图片分类需要保留（加 `is_manual` 列或独立表）。→ M。

**U3 统一 envelope + 错误模型 + 分页（M，需与前端排期）**｜现状：9 集合键 / 3 分页 / 5 错误形状 / items 双类型。→ 目标：`{data, meta:{total,page,page_size}, error}`；错误统一 `{error:{code,message,detail}}` + 恰当状态码。→ 最小改法：**只让新端点与已坏端点走新形状**，旧端点加 `X-API-Legacy: 1` 响应头逐页迁移；`/jobs` 的 `items` 类型先统一为数组（前端已有解析分支）。→ 影响：全部 router + 前端 `api()`。→ 风险：前端 22 个 JS 文件同时受影响。→ M。

**U4 抽出 service 层（L，但可拆）**｜按 1.5 的 13 项，优先 1/3/4/7/8（重复次数最多、风险最低）。→ 每次只搬一个函数并保留旧 shim，`verify_smoke.py` 作为回归闸门。→ 影响：新增 `services/{storage,serializers,taxonomy,jobs,prompt_params,stats}.py`。→ 风险：循环 import（`jobs.py` 已被 `comfyui/composer/faceswap/history` 反向 import）。→ L（拆成 6 个小步后每步 S）。

**U5 写路径事务化（S）**｜现状 0 处 `atomic`。→ 目标：1.6 的 7 个多步写入各自包 `db.atomic()`。→ 最小改法：先做 3 个最痛的（模板创建/更新、单删、出图入库）；`with db.atomic():` 只包纯 DB 部分，HTTP/push 留在事务外。→ 影响：`prompts.py`、`templates.py`、`jobs.py`、`history.py`。→ 风险：SQLite `journal_mode=delete` 下长事务会加剧写锁（与存储报告冲突）。→ S。

**U6 任务状态机收敛（M）**｜现状：`GET /jobs/{id}` 写库 + 监控循环写库 + 状态值 `unknown` 泄漏到 DB（现库 7 行）。→ 目标：快照函数变纯函数；唯一写入点是 `advance_job(job_id)`；状态枚举 `pending/running/done/error/stopped`（去掉 `unknown`，改回 `pending`）。→ 最小改法：`get_job_status_snapshot` 拆成 `compute_snapshot()`（纯）+ `persist_snapshot()`；监控循环独占写。→ 影响：`jobs.py`、`main.py`。→ 风险：前端依赖轮询即入库（若轮询不再写，需靠 5s 循环兜底，最长 5s 延迟）。→ M。

**U7 计数口径统一（S）**｜现状 5 种口径、字段名恒为 `prompt_count`。→ 目标：一个 `collect_counts(scope)`；响应字段拆成 `prompt_count`/`image_count` 并同时返回；`Tag.usage_count` 要么由触发器维护、要么从 stats 里移除。→ 最小改法：先修 `/tags` 默认口径（当前全 0）+ `/tags/popular` 的 NameError。→ 影响：`tags.py`、`categories.py`、`stats.py`。→ 风险：前端文案 "个提示词" 需要同步改（前端报告）。→ S。

**U8 禁止静默吞写失败（S）**｜现状 4 处 `except: pass` 包写路径。→ 目标：写路径只允许 `except` 后 `log.exception` + 结构化 `last_error` 字段/`GenJob.extra` 记录；不再 `pass`。→ 最小改法：先在 `jobs._insert_history_for_item` 与 `history._sync_comfyui_history` 两处加计数与 `print` 到结构化日志。→ 影响：`jobs.py`、`history.py`、`templates.py`。→ 风险：日志量（配 5 秒轮询会刷屏，需去重）。→ S。

## 4. 明确不建议做的事

- **不要为统一 envelope 而一次性改 100 个端点**：前端无构建工具、29 个 `<script>` 顺序加载，任何形状变更同时触碰 22 个 JS 文件，回归面不可控。
- **不要引入通用 Repository/UnitOfWork 抽象**：`routers/base.py` 的 `BaseCRUDRouter` 已经是这类尝试的尸体（0 处使用）；service 层用普通函数即可。
- **不要立刻删 `ImageCategory`/`ImageTag` 表**：现库 171 + 1121 行是用户手动调整过的结果，先切读路径、加 `is_manual`，再谈合并。
- **不要顺手把 `/history/ids`、`/tags/popular` 删掉**：前者是跨页全选的唯一入口，后者虽坏但属公开 API。
- **不要给软删记录做物理清理**：与"部分唯一索引 + ON CONFLICT 恢复软删行"（`jobs.py:302`）强耦合，必须和 U2/U5 一起做。
- **不要在没有事务的情况下加并发**（uvicorn 多 worker）：`state.batch_stop_flag` 是进程内单例，多进程会直接失效。

## 5. 与其他分报告的交叉点

1. **前端报告（HTMX 双渲染）**：我要求"3 个 `/html` 端点最后删"，若前端报告主张先拆 HTMX，需它先给出替代渲染与迁移顺序——顺序反了会导致提示词/画廊列表直接空白（`index.html` 依赖 `hx-get`）。
2. **前端报告（API 调用层）**：U3 的兼容点清单必须由前端确认；任何"改字段名"的建议都会与我的"最小可行改法（只加不改）"冲突。
3. **存储/性能报告（SQLite）**：`journal_mode=delete` → WAL 应由它先做，我的 U5 事务化在其后；否则长事务 + delete 模式会放大写锁等待。
4. **数据清理/迁移报告**：1159 行软删墓碑与 104 组重复文件名的处置方案，不能只做 SQL 清理——唯一索引与 upsert 语义必须先定（U2/U5）。
5. **测试/CI 报告**：`verify_smoke.py` 未覆盖 `/history/ids`、`/tags/popular`、`/history/{id}/categories`（正是当前 3 个必挂端点），建议它补这三条；`faceswap.py`/`fsbrowse.py` 是**未跟踪的新文件**，不要当作"待新增功能"重复排期。
6. **前端报告（标签/分类面板）**：`tag.js`/`category.js` 把 `prompt_count` 一律显示为"个提示词"，即便后端返回的是图片数——这条文案修复属于前端，但字段语义由我这边 U7 定义，需要对齐。
