## 一、统一【】解析

| 能力 | 函数 |
|---|---|
| 解析成碎片列表 | `parse(text)` |
| 取某一类型 | `extract(text, type)` |
| 去掉标题（提交给 ComfyUI 的形态） | `strip_headers(text)` |

现在全仓只有 `composition.py` 里存在 `【】` 正则（已用 grep 验证）。

## 二、多步写入事务化

`db.atomic()` 覆盖 8 处：

| 位置 | 保护的内容 |
|---|---|
| `templates.create_template` | 模板 + 全部碎片 |
| `templates.update_template` | 模板字段 + 删旧碎片 + 插新碎片 |
| `templates.delete_template` | 碎片级联 + 模板行 |
| `templates.batch_import` | 每个模板单独一个事务，单个失败不影响其余 |
| `prompts.create_prompt` | 提示词 + 自动类型分类 + 自动归类 |
| `prompts.update_prompt` | 字段更新 + 内容变更后的重分类 |
| `prompts.delete_prompt` | 分类关联 + 标签关联 + 历史 + 主行 |
| `prompts.import_prompts` / `batch_delete_prompts` | 单条导入、批量删除 |
| `job_state._insert_history_for_item` | 出图入库 + 继承分类 |

## 三、captured_at：修掉"最新排序不可信"

- `gen_history` 新增可空列 `captured_at`；首次迁移时按文件 mtime 回填（文件缺失的保持 NULL）。
- 三条入库路径都写入：任务出图（`job_state`）、ComfyUI 同步、磁盘扫描。
- 画廊排序、日期分面、日期筛选统一改为 `COALESCE(captured_at, created_at)`：
  ```sql
  ORDER BY COALESCE(captured_at, created_at) DESC, id DESC
  ```
- API 返回新增 `captured_at` 字段；老数据没有值时前端仍可回退显示 `created_at`。

为什么必须修：1206 条记录里 74% 是同步/扫描进来的，`created_at` 是**导入时间**，
一次批量导入会让几百张图挤在同一天，"最新"实际排的是导入批次。

## 四、顺手修掉的两个真实 bug

1. **模板批量导入丢失碎片**：`TemplateFragment.create` 原本写在 `for` 循环外，
   导入的模板永远只剩 1 个碎片（localStorage 迁移路径必中）。已修，并有回归测试。
2. **提示词导入/批量删除没有事务**：中途失败会留下半截状态。已补 `db.atomic()`。

## 六、发现但没改的问题（需要你决定）

1. **删除提示词会硬删除它的生成历史**：`delete_prompt` 里执行
   `GenHistory.delete().where(prompt_id == ...)`，删一条提示词会连带删掉它所有出图记录
   （磁盘文件还在，但画廊记录消失，下次同步又会重新出现）。
   这属于产品语义，不是重构范畴；建议改成"只解除关联，不删记录"。要不要改？
2. **`_enrich_item` 仍然在读接口里补写**（`history.py` 中回填 `prompt_params`/`prompt_id`）。
   和 B2 修掉的 `GET /api/jobs` 是同类问题，属于"读取即修复"的历史包袱；
   建议 B4 时统一挪到入库路径。
3. **`gen_history` 里的 1159 条软删除墓碑**仍在。清理会与"部分唯一索引 + ON CONFLICT 恢复软删行"耦合，
   需要单独设计一次数据清理（建议先备份、再按 `updated_at` 分桶核对）。
