# 03 · UX 信息架构与任务流

## 0. 结论先行

1. 5 个 Tab 是**5 个迷你应用共用一个壳**，不是 1 个应用：各自有搜索框、分页、选择模型、提交按钮、进度面板，彼此靠 localStorage 隐式串味。
2. 真正的"提交任务"入口是 **8 条**（不是简报说的 4 条），对应 8 个后端端点、4 套参数语义；其中 2 条提交后界面无任何进度（组合单图/批量随机），1 条根本提交不出去（画廊批量处理）。
3. 最大的体感损失不在"功能缺"而在"**结果不知道去哪了**"：组合/批量跑完只留一条 3.5s toast，图进画廊还可能被旧筛选条件挡住。
4. 所有问题的同一个根：**没有"任务"和"文档"这两个一等对象**。页面是围绕"表"建的，用户想的是"我要出一张图"。
5. 目标形态是 3 个一级入口 + 2 个共享层（任务抽屉、选图器），可拆 6 步迁移，每步都能单独上线；不建议任何整体重写。

### 1.2 五条旅程实测（步数 = 用户需要做的显式动作）

**J1 找旧提示词 → 改 → 跑 → 看 → 不满意重跑 → 满意进画廊 → 分类打标**（找/改/跑在提示词 Tab 内闭环，体验 OK：列表→详情→`🚀 跑图`，`prompt.js:479`）
- 看结果：单图任务完成后 `#outputArea` 3 秒自动收起（`job.js:132-135`），标题写"✓ 已刷新到生成历史"但**不显示图**（`job.js:130` 注释明确"不展示大图"）；图只在详情面板底部 `#promptHistorySection`（`history.js:190`），要往下滚过 参数/分类/标签 才看到。→ **1 次滚动**。
- 不满意重跑：详情里 `🎲 变体`（`index.html:468-477`）或重开编辑弹窗 `🔬 试跑`。试跑结果只活在弹窗里（`prompt.js:1585-1590`），关掉弹窗即不可见；**第二次试跑会顶掉第一次的轮询**（全局单例 `job.js:16-17`），第一条永远停在"跑图中"。
- 满意进画廊：**没有"这张进画廊"的动作**，只有全量同步。分类/打标在画廊侧栏批量区（`index.html:243-250`），只能"加"不能"减"（`gallery.js:588-620`）。→ 本旅程末尾需要 **切 Tab + 重新选图 + 逐个加标签**。

**J2 组合创作：拼碎片 → 随机试几组 → 批量跑 → 存提示词/模板**（拼/随机/存是本 Tab 内闭环，也是全站设计最好的一段：固定碎片 `📌`、行/列视图、工作台弹窗）
- 跑图：`composerRun`（`composer-templates.js:3-31`）与 `composerBatchRandomRun`（`composer-random.js:81-118`）都只调 `trackJob`，而 `_showPendingProgress` 硬写 `#outputArea`（`generator.js:16-23`），`renderBatchJob` 硬写 `#batchPanel`（`job.js:153-155`）——两者都在 `#promptTab` 内（`index.html:182,137`），**当前 Tab 下完全不可见**。用户只看到 3.5s toast（`utils.js:130-137`），之后无任何进度、无法停止。
- 结果：`composer_run` 建的是 `single` 任务、`prompt_params` 里**没写 seed**（`composer.py:153-162`），画廊参数弹窗看不到种子，**无法复现**；批量随机反而写了 seed（`composer.py:245-248`）。
- 存成提示词/模板：`composerSaveAsPrompt`（`composer-templates.js:36-66`）复用编辑弹窗并预填"组合 2026/10/18 …"当名称、标签写死"组合创作"，用户要手动改名。

**J3 批量换脸：从画廊/文件夹选主图+参考图 → 设参 → 提交 → 等**
- 选图：两栏各自"画廊/文件夹"（`index.html:762-765,789-792`），是**第三套选图器**：自己请求 `/api/history?page&page_size&search`（`faceswap.js:466-467`），**没有分类/标签筛选**，尽管后端支持（`history.py:568-569` 的 category_id/tag_ids）。用户在画廊里靠分类树找到的图，进换脸要重新用文件名搜一遍。
- 设参：换脸独有"组合方式/种子模式/种子"（`index.html:840-857`），与全局画质/横竖屏**无交集**，页内自己承认"顶部画质/横竖屏对本工作流不生效"（`index.html:876-877`）。
- 提交与等待：`fsSubmit` 同步等后端逐组合入队，按钮只改文案（`faceswap.js:596-604`）；`#fsPanel` 是**唯一在本 Tab 内可见的进度**，却在页面最底部（`index.html:886`），提交后不滚动、不高亮；完成只留 toast + 图进画廊（`faceswap.js:641-649`），文件名前缀 `fs{job_id}_`，画廊没有"按任务筛选"入口。
- 工作流显示：`#fsWfName` 只在 `initFaceswap` 时同步一次（`faceswap.js:121-125`），在头部换工作流后该标签**保持旧值**（`workflow.js:90-115` 未刷新它）。

**J4 事后整理：画廊找图 → 按提示词/分类/标签筛（范式见 1.4）→ 批量打标/删除/下载**
- `全选全部`（`gallery.js:204-209`）只带 favorite/sort/search/orientation，**丢掉 category_id 与 tag_ids**，而后端支持（`history.py:568-569`）。→ 在"分类=某类"下点全选全部，会选中**该类之外**的图；紧随其后的批量删除（`history.js:337-355`）是真删。这是当前最危险的交互缺陷。
- 批量下载串行 `await` + 500ms（`history.js:395-406`），无进度、只有首尾两条 toast。
- 图片侧分类/标签只有"加"：`bulkAddCategory/bulkAddTag/bulkInherit`（`gallery.js:588-637`），没有"移除"，纠错只能逐张进灯箱。

**J5 系统维护：选工作流 / 看 ComfyUI 状态 / 清理失效 / 补全缺图**
- 工作流选择器：弹窗式（`index.html:599-617`），有隐藏/恢复、按名称/时间排序、从文件加载（`workflow.js:168-191`），但 `renderWorkflows` 还在找已不存在的 `#wfPopoverList`/`#wfSortBtn`（`workflow.js:37,156`；`index.html` 无此 id）——**死代码，说明壳被搬动过而控件没跟上**。
- 状态：`#statusBar` 只显示"在线·运行 N/队列 N"（`app.js:232`），**不可点**，没有队列详情；"有几个任务在跑"被画到 `历史画廊` 的 Tab 徽标上（`gallery.js:327-336`），语义错位（用户以为有新图）。
- 清理失效：`cleanupMissingFiles` 顺带清空**全部**缩略图缓存（`history.js:261-267`），一次维护后整库缩略图重生成，用户感知为"变慢了"。
- 补全缺图：审核弹窗是全站最好的批量选择 UI（`generator.js:110-168`：搜索/全选/反选/计数），但**用完即弃**，没沉淀成组件供画廊复用；守卫只查 `activeJobs`，不认识换脸任务（`faceswap.js:24` 的 `_fsJobId`），可并发提交。统计 Tab 则是 4 个**不可点**的数字（`app.js:200-222`），纯死胡同却占一个一级入口。

### 1.4 筛选范式冲突：同一套分类/标签，两种交互，三种语义

- 提示词 Tab：分类=`<select>`（`index.html:98`）、标签=自定义下拉多选（`tag.js:23-40`）、排序=两个 select + 箭头（`index.html:122-129`）。
- 画廊 Tab：分类=**树**（`gallery.js:475-489`，带计数与折叠）、标签=**云**（`gallery.js:452-456`）、另有 4 组分面 chip（来源/时间/模型/方向，`gallery.js:534-572`）+ 已选筛选 chip 条（`index.html:200`）+ 批量区。同一件事 5 套控件。
- 计数口径不同：画廊用 `count_scope=image`（`gallery.js:440`），提示词用默认 prompt 计数（`category.js:17`）。同名分类在两边数字不同，用户会怀疑数据错。
- **分类 select 还被塞进两个伪分类**：`__composed__`/`__templates__`（`category.js:41-58`）。选"🔧 组合创作"会把文字写进搜索框（`category.js:84-90`）；选"📦 组合模板"会让提示词列表**变成模板列表**（`category.js:79-83`），点一下又跳到组合 Tab（`prompt.js:98-103`）。一个筛选控件承担"筛选 / 空输入搜索 / 换实体类型 / 跨 Tab 跳转"四种职责。
- 结论：用户必须学两遍筛选，且第二遍里"计数"和"全选全部"（1.2 J4）都不可信。

### 1.5 信息密度与可发现性

- 提示词 Tab 侧栏：工具栏 3 行 13 个控件（`index.html:82-133`：新建/导出/导入/智能导入/搜索 · 分类+⚙/标签+管理 · 排序+↑/自动分类/补全缺图）+ 批量面板 4 + 选择条 4（`index.html:163-172`）≈ **21 个可点区域**，而高频只有 新建/搜索/分类/标签/选中/跑图。
- 一次性维护动作（导出/导入/智能导入/自动分类/补全缺图/清理失效/清空）与日常动作同级、同样式，且**不可撤销**（自动分类直接写库 `prompt.js:159-174`；清空历史 `history.js:283-294` 只一个 confirm）。
- 灯箱一行 13 个按钮（`imageViewer.js:32-46`），翻转/旋转/1:1/重置 等低频操作与 收藏/下载/重生成/删除 混排；全站又只有一个 toast 元素（`utils.js:130-137`），并发消息互相覆盖（批量失败 3 条错只剩 1 条），3.5s 后无痕。

## 2. 根因分析

1. **缺少"任务"这个对象**。任务状态散在 `activeJobId / jobPollTimer / activeJobs / _fsJobId / _fsTimer / _trialWatchers` 六个全局里（`job.js:4-7`、`faceswap.js:24-25`、`job.js:7`），每个"跑图按钮"作者各自拣一套；单例轮询（`job.js:16-17`）决定了**同一时刻只有一个任务有 UI**，于是每加一种批量玩法就得再抄一个面板。
2. **缺少"文档"这个对象**。提示词、图片、模板、碎片是四张表四种列表，各自带工具栏；所以"分类/标签/搜索"被实现 3 次，"选图"被实现 3 次（画廊网格、换脸双栏、碎片库 `index.html:550-562`）。
3. **响应式加需求，没有横切层**。每次需求落在"某个 Tab 的某行工具栏"（补全缺图→工具栏、智能导入→工具栏、一键补齐→画廊侧栏头部 `index.html:205`、清理失效→画廊工具栏），因为壳里没有"维护/设置"的容身处。
4. **参数归属没定**。画质/横竖屏/工作流是"本次生成"的属性，却被实现为"页头全局状态"（`ui.js:168-172`），于是按 Tab 隐藏成了唯一解法；换脸干脆声明自己不用（`index.html:876`），画廊批量则忘了传（`history.js:366-376`）。
5. **双渲染放大了不一致**：同一列表有 Jinja 与 JS 两版（`templates/prompts/list.jinja2:26-54` vs `prompt.js:206-238`），HTMX 版丢了 `order` 参数、置顶图标没有点击事件（`list.jinja2:48`），交互因 URL 参数 `?htmx=1` 而异（`app.js:69-78`）。（推断）这让"以页面为单位"的修改变得昂贵，进一步推动"再加一个 Tab/面板"。

## 3. 统一机会清单

### 3.0 目标信息架构（3 个一级入口 + 2 个共享层）

```
顶部：工作流 ▾ | 生成参数条（画质·横竖屏·种子） | ComfyUI 状态 | 任务(3) ▾ | ⚙
① 素材库（默认）= 现提示词 Tab ⊕ 现画廊 Tab；视图[列表|网格] × 实体[提示词|图片|模板|碎片]
   筛选：分类树 + 标签 + 搜索；右侧统一详情面板。动词：找 → 筛 → 选 → 整理 → 复用
② 创作台 = 现组合 Tab + 现换脸 Tab 作为两种"模式"，共用素材区/参数条/提交按钮
   动词：拼 → 试 → 批量跑 → 存（提示词/模板）
共享层 A 任务抽屉（右下常驻，任何页面可见：进度/停止/结果缩略图）
共享层 B 选图器（画廊网格 + 文件夹两种来源，带分类/标签筛选）
统计 → 素材库顶部概览条 + ⚙ 设置抽屉，不再是一级 Tab
```

一级入口从 5 降到 3，核心动词收敛为 **找/整理（库）· 拼/试（创作台）· 提交/看结果（任务抽屉）**。`画质/横竖屏/工作流` 从"页头全局态"改为"参数条"（出现在每个提交按钮上方一行，可折叠），换脸页内那句"顶部控件不生效"就能删掉。

### 3.1 U1 · 统一任务抽屉（Task Drawer）

- 现状：`#outputArea`/`#batchPanel`/`#fsPanel` 三个进度面 + 两套轮询（`job.js:13-87`、`faceswap.js:628-653`）。
- 目标：右下角常驻徽标 + 可展开抽屉；一个任务列表（运行的置顶，含类型图标/进度/停止/完成后 4 张缩略图）；任何 Tab 都可见。
- 最小可行改法：新增 `taskDrawer.js`，`trackJob` 与 `fsTrack` 都向它注册；先只做"只读镜像"——保留原面板显隐逻辑，抽屉额外渲染同一份 job 数据；`fsPoll` 合并进 `pollJob` 的 `job_type` 分支（`job_type` 已是 `faceswap`，`faceswap.py:272`）。同时消除单例轮询：`Map<jobId, timer>`。
- 影响：`job.js`、`faceswap.js`、`index.html`、`ui.js`、新增 `taskDrawer.js`；风险：轮询次数上升（简报 §3.4 已在写库），需与后端"轮询幂等"排期错开或加 2s 间隔。**M**

### 3.2 U2 · 统一参数条（Generation Params Bar）

- 现状：`#qualitySelect/#orientBtn` 在头部，按 Tab 隐藏（`ui.js:168-172`）；换脸不用；画廊批量没传。
- 目标：一个 `<div class="param-bar">` 组件，渲染在提交按钮旁边；值仍存 `UiState`，但**始终可见可改**，并在提交 toast 里回读"4K · 竖屏 · wfX"。
- 最小可行改法：把 `generator.js:332-340` 的读写抽成 `paramsBar.js`（`getParams()/mount(el)`），先在 combo/faceswap 各挂一个，头部保留作为"默认值"。

## 4. 明确不建议做的事

1. **不要一次性重写 5 个 Tab 的导航与渲染**。29 个静态文件、470KB JS、无构建无测试（简报 §1–2），同时改"IA"和"渲染模型"会让回归无法定位；且用户已形成的"选中→跑图"肌肉记忆会丢。上面的 S0–S5 每步都可单独回滚。
2. **不要在同一个 PR 里同时删 HTMX 或改双渲染**。本报告的所有步骤都能在"列表仍由 Jinja 渲染"的前提下完成；先统一**状态**而不是统一**渲染器**。
3. **不要为了减少 Tab 而把 5 个页面合并成一屏**。库（找/整理）与创作台（拼/试）是两种心智，合并会让 260–620px 的侧栏塞进树+网格+编辑器；也不要在换脸页再叠一组"全局参数"，它真正缺的是承认自己不用画质/横竖屏。
4. **不要删掉"生成历史"这类就地反馈**。详情面板底部的缩略图是当前唯一"改完立刻看到"的路径，统一到画廊之前必须保留。

## 5. 与其他分报告的交叉点（可能冲突）

1. **与后端/任务报告**：U1 抽屉依赖"轮询无副作用、可多任务并行"；若他们改成 SSE/WebSocket 或合并 `job_monitor_loop`，抽屉的数据源需同步换。建议顺序：先 S1/S2（纯前端可见性），再动轮询语义；否则两边同时改 `job.js`。
2. **与"双渲染/前端架构"报告**：若其主张"删除 HTMX 统一走 JS"或反之，S3–S5 的筛选器/选图器要等渲染器定案后再动手；S0–S2 不受影响，可先上。
3. **与"分类/标签体系"报告**：我建议提示词与图片共用一套筛选 UI，但**不要求**合并 `PromptCategory`/`ImageCategory` 四张表（简报 §3.7）；若他们主张多态关联，U4 可在表合并后再切数据源，UI 组件可先行。（冲突点：我要求提示词侧也显示 `count_scope=image` 口径的计数，可能与"两套分类语义应分离"的结论相反。）
4. **与"API 契约"报告**：U3 统一选图器要求 `/api/history` 与 `/api/fs/list` 返回同构条目（现状在 `faceswap.js:33-60` 手工映射两套）；若他们改字段名或集合键（简报 §3.8），选图器需排在契约稳定之后。
5. **与"性能"报告**：他们可能建议削减 `loadHistory` 的 30s 自动刷新（`app.js:181-186`），而 U6"跑完自动定位新图"依赖刷新时机；需约定"任务完成触发一次定向刷新"替代全局轮询。
