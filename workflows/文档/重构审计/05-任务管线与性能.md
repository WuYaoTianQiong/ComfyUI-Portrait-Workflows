# 05 · 任务管线、实时性与性能

## 0. 结论先行

1. 任务状态没有"状态机"，只有一个**每次调用都反推并覆写**的函数（`routers/jobs.py:74-230`），谁来调、调几次，状态就被重算几次；`GET /api/jobs/{id}` 因此同时是读接口和写接口。
2. 轮询风暴不是"1 秒一次"的量级问题，而是**每次轮询都会拉 ComfyUI 全量队列 + 500 条历史 + 最多 10 次单条历史**（`jobs.py:80-106`）；160 张批量时单次约 3–10 MB ComfyUI 流量、48–158 KB DB 重写，且 1 Hz 定时器与 120 s 前端超时叠加会堆出上百并发。
3. 所有写入都来自"读→改→写"且无事务/版本号：日志里同一个 `prompt_id` 的 `[JOB] item done` 被并发写了 12 次（`_pb_out.log:161-173`），这就是重复入库与锁竞争的现场证据。
4. 修法只有一条主线：**ComfyUI 观察 → 单写者 → DB 唯一真源 → 事件推送**；SSE 比 WebSocket 更适合本项目（单用户、无构建、单向、原生重连）。
5. 落地拆 3 步（只读化/单写者 → SSE 灰度 → ComfyUI 访问层与回流统一），每步单独上线、单独回滚。

## 1. 现状盘点

### 1.1 真实状态流转（DB 字段 vs 反推）

| 状态 | 谁写 | 触发点 | 备注 |
|---|---|---|---|
| `pending` | `create_job`；快照 item 级 | `jobs.py:50`、`175` | 建任务即 pending，items 初始**没有** status 字段 |
| `running` | `update_job_items(status="running")`；快照 item 级 | `comfyui.py:397/456/541`、`faceswap.py:319`、`composer.py:172/288`、`jobs.py:171` | 只要 `/queue` 里出现该 pid |
| `done` | 仅快照 | `jobs.py:134-135` | **只要 pid 在 `/history` 里就判 done**，不看 `status.status_str`/`completed` |
| `error` | 快照 + 提交失败 | `jobs.py:184-188`、`comfyui.py:535`、`faceswap.py:314` | 无 pid 才判错，有 pid 找不到就"保留原状态"（`190`） |
| `cancelled` | 仅 `cancel_job` 的 item 级 | `jobs.py:352-356` | job 级叫 `stopped`，item 级叫 `cancelled`，两套词 |
| `unknown` | 快照兜底 | `jobs.py:206` | 落库后**再无任何代码会再选中它**（监控只选 pending/running，`main.py:35`） |
| `stopped` | 仅 `cancel_job` | `jobs.py:357` | 前端只当终止态，`statusText` 里没有它（`job.js:241`）→ UI 显示原始英文 |

- 状态来源：**没有一处来自 ComfyUI 事件**。ComfyUI 只有 `/queue`、`/history/{pid}`、`/progress`（`services/comfyui_client.py:64-94`）三个快照口，靠"pid 在不在集合里"猜。
- `cancel_job` 先全局 `interrupt()` + `clear_queue()`（`jobs.py:345-347`）：取消任务 A 会杀掉任务 B 正在跑的那张图，因为 ComfyUI 的 interrupt 没有 job 概念。
- 取消后必被"复活"：下一次快照若该 pid 已进 history，`134` 行无条件写 `done`，覆盖 `cancelled`；job 级 `stopped` 反而被 `198` 行豁免，造成"job 已停止、item 全 done"的自相矛盾。
- `batch_stop_flag` 是全局单例（`state.py:4`），`cancel_job` 置位（`jobs.py:347`），只有**下一次批量提交循环结束时**才清（`comfyui.py:539`、`faceswap.py:318`）→ 停止一次之后，紧接着的下一次批量会逐条走"已取消"分支。
- `unknown` 暴露的设计问题：① "无法判定"被当成结论持久化；② 落库即失去刷新资格（7 个 job / 56 个 item 永久卡死，见 §1.6 实测）；③ 前端被迫写特例过滤（`job.js:40`），症状外泄到 UI；④ 根因是状态集合里没有"待核对/观察中"这一类，也没有任何回收路径。

### 1.2 轮询链路与定量

- 前端 1 s：`setInterval(...,1000)`（`job.js:17`）；换脸另有独立 1 s 定时器（`faceswap.js:633`）；页面刷新后 `loadActiveJobs`（`app.js:175`）+ `fsResumeActive`（`faceswap.js:697-703`）会**同时**跟踪同一个换脸任务（job_type=faceswap、items>1 命中 `job.js:34` 条件）→ 2 个 1 Hz 轮询者。
- 前端 5 s：`/api/status`（`app.js:178`）→ 后端又拉一次 `/queue`（`comfyui.py:117`）。
- 前端 30 s：`/api/history_sync`（`app.js:181-186`）+ 后端 30 s 监控（`main.py:47-51`）→ 两套同步时钟并行，`_sync_comfyui_history` 可能在两个线程同时跑。
- 后端 5 s：`job_monitor_loop` 串行刷新最多 20 个活跃 job（`main.py:33-43`），每个 job 都独立重拉 queue/history（无共享缓存）。

单次 `GET /api/jobs/{id}` 成本（160 张批量，实测 items 外推）：

| 项 | 数值 | 依据 |
|---|---|---|
| 到 ComfyUI 请求数 | 2–13 次（`/queue` + `/history?max_items=500` + ≤10 次 `/history/{pid}` + 0–1 次 `/progress`） | `jobs.py:80-106,114` |
| 到 ComfyUI 的 JSON | `/queue` 含 160 条完整 workflow（推断 5–20 KB/条 → 0.8–3 MB）；`/history?max_items=500`（推断 2.5–7.5 MB） | ComfyUI 未运行无法实测，按 ComfyUI 接口结构推断 |
| 返回浏览器 | 48 KB（batch 实测 43 条=12,864 B 线性外推）/158 KB（faceswap 实测 15 条=14,828 B 外推） | 只读查 `提示词收藏.db` 的 `gen_jobs.items` |
| DB 写 | 1 次 `UPDATE` 重写整份 items（48–158 KB）+ 每张新完成图 1 次 upsert + 1 次 SELECT + `inherit_prompt_taxonomy` 4–6 条查询 | `jobs.py:208-214`、`233-317`、`models.py:173-194` |
| 频率（单 tab） | 1 Hz + 换脸叠加 1 Hz + 监控 0.2 Hz ≈ 2.2 次/s | 见上 |
| 合计 | 4.4–28.6 次 ComfyUI 请求/s；100–350 KB/s DB 重写；7–22 MB/s ComfyUI 读取（推断） | 计算 |
| 卡死放大 | 单次最坏 30+25+10×5+3 ≈ 108 s（`comfyui_client.py:66,72`），前端超时 120 s（`utils.js:48-49`）→ 1 s 定时器可堆叠出 ≤108 个在途请求/页；Starlette 默认 40 线程池被占满后，**所有同步端点（含静态文件）一起停摆** | 推断，基于框架默认线程池 |

另外：`fetch_json` 每次 `with httpx.Client(...)` 新建连接（`comfyui_client.py:14,27,42`），无 keep-alive → 每次轮询 2–13 次 TCP 握手，Windows 上 TIME_WAIT 累积。

### 1.3 GET 带副作用的约束违反与具体故障

违反：HTTP 语义（GET 应为安全/幂等）、"唯一写者"原则、以及本项目自己的并发模型（同步端点跑在线程池 `jobs.py` 被多线程并发调用）。

- 写点：`jobs.py:208`（每次 GET 必写）、`164`（每发现一张新完成图写 `gen_history`）、`150`（每轮打印日志）；`_insert_history_for_item` 还会 `inherit_prompt_taxonomy` 写 2 张关联表。
- 同类问题不止 job：`GET /api/history` 列表在 `_enrich_item` 里也会补写 `prompt_params`/`prompt_id` 并强继承分类（`history.py:58,62,66`）——点开画廊就可能悄悄写库。
- 故障 1（多开/双击）：两个 tab 同时轮询同一 job，各自读到旧的 items，各自判定"这张刚完成"，`hist` upsert 幂等但 `inherit_prompt_taxonomy(force=True)` 与 `done_count` 计数不幂等；日志已出现同一 pid 的 12 条 `[JOB] item done`（`_pb_out.log:161-173`，多条还粘在同一行 = 多线程同时写 stdout），启动瞬间 6 个不同源端口同时请求 `/api/jobs/105`（`_pb_out.log:21-26`）。
- 故障 2（监控循环并发）：监控线程与请求线程各自 read-modify-write 整份 items，后提交者覆盖前者 → 进度回跳、`done_count` 抖动、图片入库两次、显存/CPU 尖峰。
- 故障 3（取消竞态）：`batchStop` 之后立刻 `pollJob`（`job.js:273`），快照用旧数据重写 items，可能把 `cancelled` 改回 `running`/`done`。
- 故障 4（前端单例定时器）：`trackJob` 用全局 `jobPollTimer`（`job.js:16`），任务 A 即将完成时启动任务 B，A 的终止分支会 `clearInterval` 掉 B 的定时器（`job.js:58-60`），B 永远"生成中"；`activeJobs` 里 A 也没有被移除，`updateRunBtn` 之后一直禁用（`generator.js:295-300`）。

### 1.4 ComfyUI 侧访问代价

- `/history?max_items=500` 每次全量：返回 500 条完整 prompt+outputs，序列化后数 MB；超时被放大到 25 s（`comfyui_client.py:72`），恰好说明作者知道它慢。它每次只为回答"我这 160 个 pid 完成了没有"这一个布尔问题。
- `get_history_for_prompt` 只在未命中且 ≤10 条时才补查（`jobs.py:98`）——这个 10 条阈值是"避免 160 条全查导致超时"的临时补丁，说明架构上缺"按 pid 精确查询"的正路。
- `get_progress()`（`comfyui_client.py:77-79`）：标准 ComfyUI 的进度走 WebSocket `/ws`，HTTP `/progress` 并非稳定公开端点（**推断**，本机 ComfyUI 未运行无法实测）。若 404，则每次 running 都白送一个 3 s 超时请求，进度条永远走 `pct=-1` 的"30% 假进度"分支（`job.js:119-121`）。
- `_sync_comfyui_history`（`history.py:117-214`）调 `/history` **不带 max_items**（`120`）→ 拉全量历史；对每条图都要 `_get_image_path`（stat）+ `get_image_metadata`（**PIL 打开解码**，`161`、`helpers.py:61-89`）。每 30 s 一次，且可能两个线程同时跑。

### 1.5 数据库并发

- `journal_mode=delete` + 未设 `synchronous`（默认 FULL）+ 未显式设 `busy_timeout`（`models.py:9-12`；sqlite3 驱动默认 5 s，`推断` peewee 透传）。
- 全部端点同步 `def`，跑在 Starlette 线程池（默认 40 线程），peewee 连接是线程本地 → 最多 40 个连接同时打同一个文件；没有连接池上限、没有写队列。
- `journal_mode=delete` 下每次提交要写 journal、fsync、删 journal；`_sync_disk_orphans` 逐文件 `insert`（`history.py:300-313`）、`_sync_comfyui_history` 逐图 upsert（`162-196`）都是自动提交的碎写，与轮询的整行大 UPDATE 抢同一把写锁。
- 具体风险：① 大 UPDATE（48–158 KB）持锁时间长，读请求触发 `database is locked`（现有 `except Exception: pass` 会把它变成"静默丢状态"）；② 丢失更新（见 1.3）；③ Windows Defender 扫描 journal 文件，写放大更明显；④ `init_db` 里 `db.close()`（`models.py:420`）只关当前线程连接，热重启/守护线程连接残留。
- 实测库：3.2 MB、109 个 job、1206 条 history；`status` 分布 `done 71 / error 27 / stopped 4 / unknown 7`，item 级 `unknown 56`、`None 1` → 说明"unknown 落库"不是理论问题。

### 1.6 其他性能点

- 缩略图：缓存键用 `size + st_mtime_ns`（`thumbnail.py:52-56`）设计正确，但 ① 无单飞，画廊 50 张首屏并发 50 次 PIL 解码，与轮询抢 40 线程池；② 响应 `Cache-Control: no-cache` 且无 ETag（`comfyui.py:240`）→ 每次翻页/刷新都重下全部缩略图，缓存等于没有；③ 缓存目录只增不删（`clear` 才清，`comfyui.py:266-279`）。
- `/api/image`：本地命中直接 `FileResponse` + `no-cache`（`comfyui.py:147-154`），同样无 ETag；未命中代理 ComfyUI 后**同步写回 output 目录**（`190-203`）——GET 写盘，且落在 ComfyUI 的输入输出区。
- 画廊 N+1：`list_history` 已批量预取 tags/categories（`history.py:452-457`），但 `history/html` 仍逐行 `Prompt.get_or_none`（`800-803`）；`_enrich_item` 的兜底分支还逐图查库（`94-105`）。
- `_sync_disk_orphans`（`history.py:253-320`）：每 30 s 全量 `iterdir` output 根目录 + 全量读 `gen_history` 的 (filename,subfolder,type)（1206 行）+ 逐文件 stat，无 mtime 水位、无增量。
- `_job_index`（`history.py:218-250`）：模块级 dict + bool，无锁、无失效；两个线程可同时构建（重复全表扫 `GenJob`+`Prompt`），且 `_job_index_built=True` 后永不再更新 → 新完成 job 的文件名永远进不了索引，磁盘兜底逐渐失准。

## 2. 根因分析

1. **没有"状态所有者"**：状态被设计成"随时从 ComfyUI 反推的视图"，于是每个读路径都顺手把视图写回 DB（`jobs.py:208`）。一旦有第二个读者（监控、第二个 tab、换脸面板），就必然并发 RMW。
2. **读接口承担了推进职责**：因为没有后台写者，前端轮询被迫成为"状态推进器"，轮询频率直接等于 DB 写频率和 ComfyUI 拉取频率；为了掩盖延迟又加监控循环，形成"两个写者 + 多个读者"。
3. **ComfyUI 被当成可按需查询的数据库**：没有本地状态缓存/增量水位，只能"全量拉回来再比对"，所以每次轮询成本与队列长度、历史长度成正比，而不是与"变化量"成正比。
4. **前端只有"一个任务"的位置**：`jobPollTimer` 单例（`job.js:5,16`），而 UI 允许单图/批量/换脸/组合并发提交 → 用定时器单例硬扛多任务，靠清定时器"解决"，产生漏轮询与按钮卡死。
5. **取消是全局开关而非任务属性**：`batch_stop_flag` + ComfyUI `interrupt` 都没有 job_id（`state.py:4`、`jobs.py:345`），所以取消必然误伤、且残留置位影响下一次提交。

## 3. 统一机会清单

> 影响文件用简写：J=`routers/jobs.py`、C=`routers/comfyui.py`、H=`routers/history.py`、F=`routers/faceswap.py`、M=`main.py`、S=`services/comfyui_client.py`、T=`services/thumbnail.py`、G=`static/job.js`、FG=`static/faceswap.js`、P=`static/generator.js`。

### U1 状态机显式化 + 取消归属到 job（S）
现状：状态由快照反推并落库，`unknown`/`stopped`/`cancelled` 三套词，取消是全局 Event。
目标：DB 唯一真源，固定 6 态 `pending/running/done/error/cancelled`（`stopped` 并入 `cancelled` 或保留为 `cancel_requested` 布尔列）+ `seq`/`updated_at` 版本号；`unknown` 只存在于内存的"待核对"标记，永不落库；取消写 `GenJob.cancel_requested`，`interrupt` 仅当 running pid 属于该 job。
最小改法：新增 `services/job_state.py`（`allowed_transitions` + `apply(job_id, patch, expect_seq)`）；`J` 拆成 `read_snapshot()`（纯读）与 `refresh_job(job_id)`（唯一写者）；`cancel_job` 改为 `cancel_requested=True` + 只对该 job 的 pid 调 interrupt。
影响：J/M/F/C/G；风险：前端 `unknown` 过滤与 `stopped` 判断要同步改（`G:40,58,241`），否则旧数据看不见；工作量 S。

### U2 单一事件通道：SSE（S/M）
选型：**SSE**。理由：单向推送足够（取消仍走 POST）；`EventSource` 原生断线重连 + `Last-Event-ID`，无构建工具零依赖；`uvicorn --reload=False` 单进程，内存 pub/sub 即可；WebSocket 要自己写心跳/重连/多路复用，还会让"取消/提交"与推送两套协议并存。约束：HTTP/1.1 同源默认 6 连接，**多任务必须复用一条流**，不能每个 job 一个 EventSource。
最小设计：
- 端点 `GET /api/jobs/{id}/events`（单任务）与 `GET /api/jobs/events?ids=1,2`（多任务，前端默认用它）；`text/event-stream`，`retry: 3000`。
- 事件：`snapshot`（首帧/重连，完整 job + `seq`）、`state`（job 状态变更）、`item`（单条增量：`{index,status,images,error}`）、`progress`（仅 running：`{pid,progress,max,current_node}`，可直接来自 ComfyUI WS 或 2 s 采样）、`end`（终止态后发一帧再关闭）；每帧 `id: <seq>`，注释帧 `: ping` 每 15 s。
- 断线重连：每 job 保留 100 条环形缓冲；`Last-Event-ID` 命中则补发增量，未命中发 `snapshot`；`seq` 由单写者递增，天然去重（前端 `seq <= lastSeq` 丢弃）。
- 灰度切换：前端 `trackJob` 里 `if (window.PB_SSE !== false && window.EventSource)` 先连 SSE，3 s 内无首帧或 `onerror` → 本会话永久降级到现有 1 s 轮询；`GET /api/config` 增加 `sse:true` 能力位。服务端用**同步生成器**（`def gen(): while True: yield q.get(timeout=15)`），Starlette 会在线程池迭代，与现有同步端点同构，不需要先 async 化；单用户 1–2 条连接占 1–2 个线程，可接受。
- 影响：J/M、新增 `services/job_events.py`、G/FG/P；风险：SSE 连接与线程池/关停（lifespan 要通知断流），DevTools 里每个流占一条连接；工作量 S（后端）～M（前端灰度）。

### U3 ComfyUI 访问层（S/M）
现状：每次新 `httpx.Client`；每次 `/queue` + `/history?max_items=500` + ≤10 单条 + `/progress`。
目标：一个 `ComfyAdapter` —— ① 单例 `httpx.Client`（keep-alive）；② `/queue` 全局缓存 TTL 1 s + single-flight（一次刷新喂所有 job）；③ 按 `prompt_id` 精确 `/history/{pid}`，终态缓存（完成后 history 不变，LRU 2000）；④ 删掉 `max_items=500`；⑤ `get_progress()` 降级为"仅 running 时 2 s 一次的可选装饰"，取不到就不显示百分比，**不要**为进度条接 ComfyUI WebSocket。
刷新节奏由状态决定：有 running → 1 s；只有 pending → 2 s；无活跃 job → 0 次（纯事件驱动）。
影响：S/J/M/H；风险：`/queue` 全局缓存会让两个 job 的 running pid 共享同一份，需要注意"running 只有队首一个"的语义；工作量 S。

### U4 DB 并发收敛（S）
现状：`journal_mode=delete`、无 WAL/busy_timeout、40 线程各建连接、碎写与整行大写互抢。
目标：`journal_mode=WAL` + `synchronous=NORMAL` + `busy_timeout=5000` + `foreign_keys=1`；**所有 job/状态写入走单写线程**（`queue.Queue` + 1 个 daemon），读走只读连接；线程池上限降到 8–10（`anyio.to_thread.current_default_thread_limiter().total_tokens=8` 或 uvicorn `--limit-concurrency`）。
最小改法：`models.py` pragmas 加 3 项；新增 `services/job_writer.py`；`J` 的 `refresh_job` 只 enqueue 不直写；`journal_mode=WAL` 在 `init_db` 里显式 `PRAGMA` 并打印确认。
影响：`models.py`/J/M；风险：WAL 会在 DB 旁生成 `-wal/-shm`，备份/同步脚本要包含；老库切换需一次 checkpoint；工作量 S。

## 4. 明确不建议做的事

- **不要**在 `GET /api/jobs/{id}` 里继续写库，也不要靠"加锁/5 s 节流/去重表"给它续命——那是把一个架构错误局部优化成更难查的架构错误。
- **不要**上 WebSocket、Redis、Celery、消息队列、多进程 worker：单用户本机工具，收益为零，故障面翻倍。
- **不要**为了进度条去订阅 ComfyUI 的 `/ws`（还要处理重连、多客户端、事件噪声）；进度是锦上添花，状态正确才是主线。
- **不要**第一步就拆 `gen_jobs.items` JSON 成 `job_items` 表（L 级，且会把 SSE 增量字段绑死在表结构上）；先上版本号 + 单写者，拆表可以以后独立做。
- **不要**让前端直连 ComfyUI（会绕过图片代理、统一状态与 CORS 约定）。
- **不要**把 `job_monitor_loop` 继续写成"async 函数里跑同步 HTTP/DB"（`main.py:30-53` 已阻塞事件循环）；要么 `to_thread`，要么独立线程——但不要因此把所有端点 async 化（见 §5）。

## 5. 与其他分报告的交叉点（可能冲突）

1. **与"后端/API 现代化"报告**：若主张"全部端点改 `async def` + `httpx.AsyncClient`"，顺序上必须先做 async 化再做 SSE（否则 SSE 生成器要返工）；我建议 SSE 先用同步生成器上线，async 化单独立项，两者不要绑在一个 PR。
2. **与"数据库/模型"报告**：若主张拆 `job_items` 表，与 U1 的"版本号 + 单写者"是最小路径相冲突（拆表是 L、且会推迟第 2 步）。可接受折中：本期只加 `version`/`updated_at` 列，拆表另开。
3. **与"前端双渲染/HTMX"报告**：若主张任务进度也走 HTMX SSE swap：冲突且不可行——`static/vendor/` 只有 `htmx.min.js`（无 `sse` 扩展），HTMX 2 的 SSE 需要额外扩展文件，而本项目"无构建、手工放 vendor"的约束下不建议新增。任务面板应保留 JS 渲染，HTMX 只管列表。
4. **与"状态持久化"报告**：若主张把 `activeJobs`/当前任务写进 localStorage 以便刷新恢复，与"服务端唯一真源"直接冲突；刷新恢复应统一走 `/api/jobs?active=1`，localStorage 只保留 UI 折叠/选中态。
5. **与"日志与错误处理"报告**：U5 的验收依赖把 `except: pass` 改成"计数 + 日志"（`history.py:209,314`、`jobs.py:105-106`、`comfyui.py:201-203`）；若他们只做结构化日志、不处理静默吞异常，增量同步是否漏图将无法验证。
6. **与"缩略图/图片服务"报告（若有）**：U7 的 `immutable` 缓存会与 `main.py:148` 的 `/api/* no-store` 兜底冲突，需要他们同意"图片类端点显式缓存、数据类端点 no-store"的分层约定。
