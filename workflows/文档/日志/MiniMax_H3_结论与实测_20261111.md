# MiniMax H3 结论与本地实测（2026-11-11）

> 时序记录，只增不改。上游部署与 12G 极限首测见 `踩坑日志_2026-06至10.md` 三十节（2026-08-09~10）。
> 本轮回答四个问题：① H3 之后有没有新视频模型；② 现有两个工作流有没有被优化；③ 最高能出什么质量；④ 最长几秒；并附 Dials 小 LoRA 的实测。

---

## 一、模型侧结论（2026-11-11 核查）

| 项 | 结论 |
|---|---|
| **视频模型** | **仍是 MiniMax H3（2026-07-31）**，官方发布日志到 2026-11-10 为止**没有** H4 / H3.5 / H3 Max |
| **Hailuo 线** | 最新仍是 `Hailuo 2.3 / 2.3-Fast`（2025-10-28），2026 年无新条目 |
| **2026-11-10 的 H3-Image** | 是**图像**模型（H3 去掉音频分支的 33.1B DiT + Qwen3-VL-32B 文本编码器），不是视频；6 步 CFG1、直出 16MP、16 张参考图；**ComfyUI 需 v0.45.0**；最小可用权重组合约 **29.4 GB**（W4A8 12.5G + NVFP4-AWQ 15.7G + VAE 1.2G）→ **12G 卡不可行**，不接入 |
| **H3 生态增量（对现有工作流有用）** | ① `ComfyUI-Dials`（2026-11-06）：14KB 滑块调运动/氛围，已装并实测（见第五节）；② `Viggle Remake`（11-04）：两个 H3 LoRA 做视频重拍；③ Pika 把 H3 蒸到 6 步（需 Pika LoRA）；④ ComfyUI 已吸收 H3 快速放大路径 |

**一句话：视频底座没有换代，不需要迁移；可用的增量是"小 LoRA 控制"而不是"换模型"。**

## 二、现有两个工作流的真实参数（2026-11-11 逐节点核对）

文件：`通用工作流/MiniMax_H3_文生视频_官方原版.json`（20 节点）、`通用工作流/MiniMax_H3_图生视频_官方原版.json`（23 节点）

| 项 | 现有文件实际值 | 官方模板默认值 | 结论 |
|---|---|---|---|
| 分辨率 | `ResolutionSelector` = **0.4 MP**（文生 16:9 → 864×480；图生 1:1 → ~640×640） | 1344×768（≈1.03 MP） | **被降配 60%，不是优化** |
| 时长 | `PrimitiveFloat` = **5 秒**（124 帧） | 5 秒 | 一致 |
| 步数 | `BasicScheduler` = **20 步** / simple，采样器 `res_multistep` | 20 步 | 一致 |
| 帧率 | `CreateVideo` = 24 fps | 24 fps | 一致 |
| 文本编码器 | `qwen3vl_32b_minimax_h3_nvfp4_awq`（14.61 GB） | 同 | 一致 |
| 扩散模型 | `minimax_h3_fl2va_pruned_int8_convrot`（19.53 GB） | 同 | 一致 |

所以：**两个工作流自部署以来没做过画质向的改造，唯一偏离官方的就是把 0.4 MP 写死了**（推测是当初为在 12G 上稳妥跑通而调低）。
它们现在的默认档只用了这台机器约 **40%** 的可行能力。

## 三、能出什么质量、最长几秒（12G 能力地图）

2026-08-09~10 全自动极限测试（pynvml 监控显存峰值，见三十节）与 2026-11-11 复核：

| 分辨率 | 最长可跑 | 实测耗时 | 显存峰值 | 备注 |
|---|---|---|---|---|
| 1344×768（1.03 MP） | **10 秒**（243 帧） | **21 分钟** | 12004 MB (98%) | 768P 硬上限，贴边 |
| 1344×768 | 12 秒 / 15 秒 | — | 99% → OOM | 采样阶段炸，25s 内报错 |
| 1216×672（0.82 MP） | 8 秒（未探 10s） | ~10 分钟 | 95% | 平衡点 |
| 1056×608（0.64 MP） | **15 秒**（360 帧） | ~15 分钟 | 95% | 时长最宽 |
| **864×480（0.41 MP）** | 15 秒+ | **5 秒档 = 159.6 秒**（2026-11-11 实测） | — | 起步安全区 |
| 832×480 / 56 帧（2.3 秒） | — | **50~53 秒**（2026-11-11 实测） | — | Dials 测试用档 |

**速度复核**：864×480/124 帧今天实测 159.6 s；按像素与帧数折算，2026-08 的 1056×608/124 帧 = 256 s，两者一致 → **0.38.2 → 0.41.3 的内核升级没有带来 H3 提速**。

**官方规格上限**（权重本身支持）：2K 分辨率、**15 秒**、24 fps、原生立体声。12G 上"2K"与"15 秒"不可兼得，实际是"1344×768×10s"或"1056×608×15s"二选一。

**画质分层判断（同提示词同种子）**：
- 864×480：能看清人脸结构与服装层次，但面部细节在 1:1 查看时明显发软，适合"看动作/看构图"；
- 1056×608 / 1344×768：面部与发丝可用，接近"手机拍摄"观感，是这台机器真正能交付画质的下限档位；
- 无论哪档，**都建议配合 SeedVR2 或后续放大**再用于成片，原生直出不作最终交付。

## 四、改法（**2026-11-11 晚已落地并验证**）

1. 两个工作流的 `ResolutionSelector` 已从 **0.4 MP → 1.0 MP**（时长/步数/其他参数未动），备份 `*.json.bak_20261111`；
2. **验证结果**：1312×736 / 124 帧 / 20 步 = **414.6 秒（6 分 55 秒）**，✅ 正常出片 → 新默认可用，但比原 0.4 MP 档（159.6 秒）慢 **2.6 倍**；
3. 需要长片时再手动切 `1056×608 / 15 秒`（约 15 分钟），不要直接上 768P+15s（必 OOM）；
4. 跑之前关掉浏览器等占显存的程序，峰值 95~98% 时极容易挤爆；
5. 运动可控直接在 UNETLoader 后插 `DialsApplyDial`（见下节），比改提示词稳定。

> 回退：把 `ResolutionSelector` 的 megapixels 改回 0.4，或直接用备份文件覆盖。

## 五、Dials 运动滑块实测（2026-11-11 新增）

环境：`ComfyUI-Dials`（V3 节点接口，0.41.3 支持），滑块放 `models/loras/dials/`；
测试条件：832×480 / 56 帧 / 20 步 / 同种子 1001 / 同一提示词（"缓慢转头并向前一步"）。

| strength | 帧间平均差 | 相对基线 | 画面亮度 | 观感 |
|---|---|---|---|---|
| −2 | 1.73 | **0.47×** | 84.3 | 近乎冻结；构图与基线不同 |
| −1 | 1.89 | 0.51× | 77.1 | 同上，接近静止 |
| 0 | 3.67 | 1.00× | 70.8 | 基准 |
| **+1** | 5.03 | **1.37×** | 50.8 | 场景人物保持、动作明显加强，但整体变暗 |
| +2 | 24.10 | **6.57×** | 58.2 | 严重过冲：人物重排、动作失控、偏离提示词 |

结论：
- 滑块**确实有效且幅度巨大**，但**非线性**（+1 仅 1.37×，+2 直接 6.57×，官方标称 2.7×）；
- 负向很快饱和（−1 与 −2 差别很小）；
- 强度开大时**不只是"运动变多"**，构图、亮度、人物都会一起漂移；
- **实用区间 0 ~ +1**；+2 当作"换镜头"工具而不是"加强运动"；
- 每条 832×480/56 帧耗时 50~53 秒（首次含加载 91.5 秒）。
