### 5. ⚠️ 2026-10-05 重要更正：EasyCache 0.5 档**不建议使用**

> 本节 2 的结论（"EasyCache 高收益"）建立在一个**不够敏感的指标**上（整图平均像素差、全图高频能量）。改用**平坦区局部噪声**（取基线图最平坦 15% 的块测局部标准差）复测后，结论必须修正：**EasyCache 0.50 会明显变脏，肉眼可见成块噪点。**

| 配方 | 热态耗时 | 提速 | 平坦区局部噪声（基线 0.69） | 判定 |
|---|---|---|---|---|
| 基线（无缓存） | 28.2s | 1.00× | 0.693 | — |
| EasyCache 0.10 | 30.3s | **1.00×**（白改画面） | — | ✗ 无用 |
| EasyCache 0.20 | 24.0s | 1.17~1.27× | 1.06（+53%） | ⚠️ 边际 |
| **EasyCache 0.50（原先固化）** | 19.95s | 1.53~1.56× | **2.64~2.67（+281%~294%，两种子一致）** | ❌ **弃用** |
| EasyCache 0.70 | 18.2s | 1.67× | 12.9（+1000%+级） | ❌ 更差 |

**机理**：EasyCache 跳步时并非复用上一步结果，而是用 `x + 缓存差分` 做**一阶近似**（源码 `apply_cache_diff`）；而本配方第二段是 **`dpmpp_2m_sde`（SDE 随机采样：每步先加噪、再由模型抹除）**，模型被跳过 → 加进去的噪声抹不掉；第一段残噪还会被 `LatentUpscaleBy 1.7` 放大后再交给只有 6 步的第二段，洗不干净。

**处置（已完成）**：`MoodyZIT_V13_双程采样_EasyCache提速_文字渲染.json` 里的 EasyCache 节点已改为 **默认 bypass（mode=4）+ 阈值 0.2**，节点标题注明"实测 0.5 会明显脏"。**默认出图＝干净基线**，想试按 `Ctrl+B` 启用。原 `MoodyZIT_V13_Visual_...` 文件自始至终未被改动。（2026-10-05 清理：该 EasyCache 变体已归档到 `workflows\历史工作流\`，作为"为什么弃用 EasyCache"的实物证据；主力仍在顶层原位。）

**方法论教训（以后测画质必须遵循）**：① 指标要看**平坦区局部噪声**，而不是整图均值（整图块级 std 只差 +0.5%，完全看不见问题）；② 每档至少**两个种子**，避免均值掩盖个别坏样本；③ ~~对照组必须同种子~~ → **当晚更正**：本机同种子出图**偶发**会有 ~12/255 的假差异（4 次真实执行里 1 次，见三十三节），"同种子像素对照"这条判据不可靠 —— **只信分布型指标**（底噪：基线 0.678~0.703 vs EasyCache 0.5 的 2.206）。

### 3. nunchaku 是什么

**一句话：把扩散模型压成 4-bit 并配套专用推理内核的加速引擎**（MIT HAN Lab，SVDQuant，ICLR 2025 Spotlight）。在 ComfyUI 里以插件 `ComfyUI-nunchaku` + 专用加载器节点出现（`NunchakuZImageDiTLoader` 等），**替代原生 `UNETLoader`**。

核心思想（SVDQuant）：扩散模型直接量化到 4-bit 会因**离群值**崩画质，于是把离群值"吸收"进一个低秩分支：

```
原始权重 W ≈ qweight(4-bit) + wscales + proj_down / proj_up（低秩 fp16 修正）
```

收益：Z-Image Turbo **11.46GB(bf16) → 3.91GB(NVFP4)**；在 Blackwell（5070）上走 fp4 张量核心。

### 4. 权重选型与下载（实测）

### 6. 为什么挂不上 LoRA：5 层内部接口不兼容

**LoRA 在 nunchaku 上不是"加法"而是"结构性合并"**（普通模型 `W' = W + s·up@down`；量化模型必须把 LoRA 的 down/up **concat 进** `proj_down/proj_up`，见 `apply_lora_to_svdq_linear`），因此它必须深度插进 ComfyUI 的权重装载/补丁内部流程——而这层正是新版改动最大的地方：

| 层 | 位置 | 0.31.0（现在） | 0.38.2 |
|---|---|---|---|
| 1 | `fuse_to_svdquant_linear` 的 `kwargs.pop("torch_dtype", weight.dtype)`（Python 会先求值默认参数，惰性 Linear 下 weight 为 None） | ❌ 崩 → **已修** | ❌ 同 → **已修** |
| 2 | `ModelPatcher` 新增 `fast_disk`/`pinned`，`clone()` 会传给子类 | ✅ 无此问题 | ❌ `TypeError` → **已修** |
| 3 | 权重装载设备：`proj_down` 还在 CPU、LoRA 张量已在 GPU → `torch.cat` 失败 | 未走到 | ❌ → **已修**（单元测试通过） |
| 4 | **LoRA 键名**：ComfyUI 打在 `.weight`，nunchaku 只认 `.qweight` | ❌ `AssertionError` ← **当前卡在这** | ✅ 键名映射能对上 |
| 5 | 卸载路径 `SVDQV4A4Linear` 缺 `weight_function` → 随后**进程级原生崩溃**（非法内存访问） | 未验证 | ❌ 崩过一次 |

**两个值得记住的排查发现：**
1. **`torch.ops` 会骗过"属性存在性"检测**：它对任意属性名都返回 torch 代理对象，所以"三个特征属性都在"的判断会命中假目标。你机器上 `ComfyUI-QwenImageLoraLoader` 自带的那份"Z-Image/SVDQ lazy Linear 兼容"补丁就因此打到了 `torch.ops` 上（启动日志原文：`Patched fuse_to_svdquant_linear in torch.ops`），**真模块从未被修补**。正解是只认真正的 `ModuleType` 并用 `__dict__` 直取属性。
2. **该 bug 与本次升级无关**：回退到 0.31 后同样在**第 1 层**崩（同一行同一错误），说明这条 Z-Image 量化路径在升级前就不可用；0.38.2 只是**额外**引入了第 2/3/5 层。

## 三十三、2026-10-05 深夜 本机出图「同种子像素对照」判据更正实测

> 起因：用户肉眼指出 EasyCache 0.50 出图"底噪大、成块噪点"。我先前用**同种子逐像素差**判画质，结论一度与肉眼相反；这一晚把**判据本身**也验了一遍 —— 发现它是"偶发假阳性"的来源，并因此撤回了三十二节"升级改变画面"的结论。

### 1. 决定性实验：同图、同种子，反复跑

同一 API 图（V13 fp8 + momoka LoRA + 双程）、**seed 固定 510001**、第二段固定 `seed+1`，反复出图（脚本里 `noise_seed` 全部由 seed 显式派生，**无随机源**）：

| # | 何时 / 状态 | 是否真执行 | 平均差（vs #1） |
|---|---|---|---|
| 00001 | 进程 P1 **重启后首跑** | 41.5s ✓ | — |
| 00002 | P1 **闲置约 7 分钟后再跑** | 32.6s ✓ | **12.15/255（77.4% 像素 >2）** |
| 00003 | **重启后新进程 P2 首跑** | 42.3s ✓ | **0.00/255（逐像素完全一致）** |
| 00004 | `/free` **强制卸载模型后再跑** | 37.6s ✓ | **0.00/255（逐像素完全一致）** |
| （第 3 次同种子提交） | 紧接 00003 之后 | ✗ **0.01s ＝ 命中节点缓存** | 未产出新图 |

**结论（与我的初判不同，已更正）**：
1. 本机流水线**基本是确定性的**：4 次真实执行里 **3 次逐像素完全相同**，且包含**跨重启**与**强制卸载重载** → "权重重载 / 随机数 / 换进程导致画面变化"这些猜测**都不成立**；
2. 但**偶发**会出现一次约 **12.15/255** 的偏移（`#2` 那次，之后三次都复现不出来），**原因未查明**；**AIMDO 动态显存**（12GB 卡上会做权重流式换入换出）是唯一"内部状态随时间变化"的组件，列为首要嫌疑；
3. 因此**"同种子像素对照"不能当判据**——不是"必然不可复现"，而是"**偶尔会给你一个假的 12/255 差异**"，而真差异往往也正好在这个量级，无法区分。

### 2. 关键对照：分布型指标（底噪）完全不吃这类偏移

"平坦区局部噪声"＝各自最平坦 15% 的 32px 块：

| 配置 | 底噪 | 备注 |
|---|---|---|
| 0.38.2 基线 第1次 | **0.678** | |
| 0.38.2 基线 第2次（同种子） | **0.700** | 像素差 12.15，底噪几乎不动 |
| 0.38.2 基线（首次升级那轮） | **0.703** | |
| 0.31 基线 | **0.700** | **跨版本同样稳** |
| **EasyCache 0.50** | **2.206** | **＝基线上限的 3.1 倍** |

**三个推论：**
1. **EasyCache 0.5「脏」成立且更硬**：3.1 倍，远超偶发偏移（此前两种口径：按基线最平坦块掩膜算 2.64、"自身最平坦块"口径算 2.21，都指向同一结论）—— **用户肉眼是对的**；
2. **三十二节「升级会让画面轻微变化」撤回**：那个差异（9.66~12.35/255）与"同版本下偶发一次"的 12.15/255 无法区分，**升级对画面无可证实影响**（要坐实，需在 0.31 / 0.38.2 上各做一次「重启后首跑」的严格对照）；
3. 反向也成立：**不能用像素差证明"某改动无害"**（偶发偏移会淹没真差异），只能用分布型指标（底噪、p95/最大值、多种子统计）。

### 3. 以后怎么做（新判据）

| 场景 | ❌ 错误做法 | ✅ 正确做法 |
|---|---|---|
| 判断改动是否伤画质 | 同种子逐像素差；整图均值/全图高频能量 | **平坦区底噪 + p99/最大值**，≥2 个种子，与"重复出图基线带"比 |
| 想复现同一张图 | 只固定 seed，并假定必定一致 | **通常一致**（跨重启、强制卸载重载均已验证逐像素相同），但**偶发**偏 ~12/255；要 100% 像素级复现，需固定/关掉 AIMDO 动态显存状态（并复测速度代价） |
| 对比两版 ComfyUI | 同种子像素差 | 底噪 + 多次热态耗时，并接受"像素对照会有偶发假差异"这一前提 |

### 3. SeedVR2 超分：3B → 7B 的显存调优

**症状**：12G 卡上 7B + 4K 直接 OOM。
**根因**：原工作流 `blocks_to_swap=8` 是 3B 的配置；7B 需要 36。

官方（插件 README）显存分档：**≤8GB**＝GGUF Q4 + BlockSwap + VAE tiling；**12–16GB**＝FP8 模型 + BlockSwap 或 VAE tiling（按需）；**24GB+**＝FP16。

**OOM 四招（按序）**：① 用 3B 跑 4K；② `offload_device=cpu` + `blocks_to_swap=36`(7B) / `32`(3B) + `swap_io_components=True`；③ VAE `encode/decode_tile_size` 1024→512 或 256（overlap 同比减半）；④ 降目标分辨率。

**本机实测（7B-Q4 + blocks 36 + swap_io + tile 512）**：4K **约 50s/张**。
**为什么这么快**：`cache_model=True`（权重免磁盘重载）+ **Q4 4bit 计算量小** + `sageattn_2`。**注意**：BlockSwap 的 CPU↔GPU 传输**每次都做**，缓存省的是"磁盘→内存"。

**优化项（按收益排序）**：`blocks_to_swap` 36→24/16（最大提速项，代价吃显存）；`attention_mode` → `sageattn_3`（50 系）；`torch.compile`（README 称 DiT 20-40%，但**首次编译慢、占内存，12G 上未必划算**）；VAE `cache_model=True`；tile 512→1024（吃显存）。
**质量项**：`color_correction=lab` 已是最优；高分辨率有伪影时试 `input_noise_scale` / `latent_noise_scale` **0.01~0.05**；`7B_fp8_e4m3fn_mixed_block35_fp16` 比 Q4 高一档（需下 5-6G）。
**Q8 vs fp8**：官方把 `3b_fp8_e4m3fn` 与 `3b-Q8_0` **同标 "good quality"**（Q8 理论略优但肉眼难辨）；**50 系有原生 fp8 → 留 fp8 更快**。
**8K 结论**：引擎支持任意偶数分辨率（`resolution` 上限 **16384**），但档位节点 `SeedVR2ResolutionPicker` 只到 6K；12G 下 **6K 已是极限区间**，8K 极可能 OOM → **实用路线：出 4K 再用放大模型 2x**。

### 6. SeedVR2 分辨率真相：**档位的"K" ≠ 输出尺寸的"K"**（2026-10-14 深挖）

**触发**：用户按 4K 档出图，发现只有 3072×4096，怀疑"输出被偷偷降级"。

**根因（源码级）**：工作流把分辨率选择器的**同一个值同时接到 `resolution` 和 `max_resolution`**：

```
ResolutionPickerPlus.resolution → SeedVR2VideoUpscaler.resolution      （＝目标【最短边】）
ResolutionPickerPlus.resolution → SeedVR2VideoUpscaler.max_resolution  （＝【任一边】的上限）
```

插件 `SideResize`（`src/data/image/transforms/side_resize.py`）是**两步执行、后者优先**：

| 步骤 | 代码位置 | 行为 |
|---|---|---|
| ① | 第 62 行 | 先把**短边**拉到 `resolution`（自动保持比例）→ 3:4 图变 4096×5461 |
| ② | 第 65~74 行 | 若**任一边** > `max_resolution` → 整体等比缩小（`scale = max_size / max(h,w)`）→ 5461 > 4096 → ×0.75 → **3072×4096** |

源码原文：`resolution` = "Target resolution for the **shortest edge**"；`max_resolution` = "Maximum resolution limit for **any dimension**（0 = no limit）"。

**各档位真实输出（3:4 输入）**：

| 档位 | 现状输出 | 像素 | 解锁 `max_resolution` 后 | 像素 | 12G |
|---|---|---|---|---|---|
| 2K (2048) | 1536×2048 | 3.1 MP | 2048×2731 | 5.6 MP | ✅ |
| **4K (4096)** | **3072×4096** | **12.6 MP** | **4096×5461** | **22.4 MP** | 现状 ✅ ／ 解锁后 **❌ 实测 OOM** |
| 6K (6144) | 4608×6144 | 28.3 MP | 6144×8192 | 50.3 MP | ❌ |

> ⚠️ **两个 "K" 的定义不同，这是本工作流最易误读的点**：**行业标准按长边**（4K = 3840/4096）→ 3072×4096 的**长边正好 4096，即 4K**，像素（12.6 MP）还超过标准 4K UHD（8.29 MP）**1.52 倍**；**而插件档位按短边** → 短边 3072 只算 3K。所以"**4K 档**"和"**4K 图**"是两件事。

**实测：解锁单边限制后 OOM（2026-10-14）**：把 `max_resolution` 改由 `INTConstant = 0` 独立供给（＝不限制），4K 档得到 4096×5461（22.4 MP，此时 `blocks_to_swap` 已给到 36）→ **直接爆显存**。
**结论**：**12G + 7B-Q4 的硬天花板＝长边 4K（3072×4096 ≈ 12.6 MP）**。这不是调参问题——`blocks_to_swap` 只能省**权重**，**激活值 + attention 中间量省不掉**（插件未提供 DiT 侧分块推理）。横图更危险：16:9 解锁后＝4096×7282（29.8 MP），几乎必爆。

> 📏 **数据更正**：本会话早前口述"6K 档 latent 面积比 4K 档大 56%"——**错**。边长 1.5 倍 → 面积 **2.25 倍（+125%）**（表内 `384×512 → 576×768` 的数值本身正确，仅文字说明算错）。

### 3. ⚠️ 坑①（致命）：位置式 widget 映射把被 link 接管的槽位错位 → `batch_size=864`

**现象**：三底模**全部 OOM**（`KSamplerAdvanced: Allocation on device`），显存峰值冲到 10.5~11.7GB；随后**整机卡死**。

**根因**：`EmptyLatentImage` 的 `widgets_values = [864, 1248, 1]`（宽/高/批次），而 `width`/`height` 已被 `ResolutionSelector` 接管（转为输入）。朴素的"按顺序取 `widgets_values`"转换在遇到被 link 占用的 `width` 时 `continue` 了、**却没有推进下标**，于是 `batch_size` 读到了下标 0 的 **864** → **一次排队生成 864 张 1.13MP 图**。

**修复**：
1. **优先用 `widgets_values_named`**（其键名与 `/object_info` 的输入名严格一致，本工作流 12 个节点**全部具备**该字段）做映射；
2. 位置式兜底分支必须遵守：**被 link 占用的 widget 槽位照样要吃掉一个下标**；
3. 提交前加断言：`batch_size ∈ [1,4]` 且 面积 ≤ 3MP，否则拒绝提交。

**教训 → 补充 §8 的「四条坑」为第五条**：
⑤ **`widgets_values` 是"所有控件"的位置序列，包含已被转为输入的控件**（保留其最后一次手动值作为回退值）。**不要把被链接的输入从下标序列里剔除**；稳妥做法是优先走 `widgets_values_named`。

### 4. 坑②：LoraManager 空 `loras` 触发 `bad_linked_input`

**报错**：`{"node_errors":{"168":{"errors":[{"type":"bad_linked_input","message":"Bad linked input, must be a length-2 list of [node_id, slot_index]"}]}}}`

**根因**：`Lora Loader (LoraManager)` 的 `loras` 输入类型是自定义 `LORAS`，值为 `[]`；ComfyUI 校验时**凡 `isinstance(val, list)` 就按 link 处理**，`len != 2` 即报错。

**修复**：该节点 lora 列表为空（纯直通）→ 将节点加入跳过表，并把它的**输出槽位按顺序映射回"已连接 inputs"的来源**（`MODEL ← UNETLoader`、`CLIP ← CLIPLoader`）。
⚠️ **注意**：LoraManager 的 `clip` 输入在 `/object_info` 里**不存在**（前端动态添加，同 §8 坑③），所以跳过时的位置映射必须按**工作流里实际已连接的 `inputs` 顺序**配对 outputs，**不能按 `object_info` 的定义顺序**。

### 5. 坑③：监控方式 —— 不要用 `nvidia-smi` 高频采样

- **不要**用 `subprocess` 每 0.25s 调一次 `nvidia-smi`（= 每秒新建 4 个进程），叠加坑①会把 32G 机器直接拖死。
- **正解**：同进程轮询 ComfyUI 自己的 `GET /system_stats`（`urllib`，每 2s 一次，**零进程创建**），取 `devices[0].vram_free` / `system.ram_free`。
- ⚠️ **单位是字节，不是 MB**（第一版按 MB 比哨兵值，读数全废）。
- 峰值占用 = `vram_total − min(vram_free)`。
