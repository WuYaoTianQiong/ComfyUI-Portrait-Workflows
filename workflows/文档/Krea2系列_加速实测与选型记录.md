# Krea2 系列工作流 · 加速实测与选型记录

> 记录日期：2026-10-18
> 目的：搞清楚「双程采样 + 潜空间放大」到底值不值、超分怎么配、哪些工作流有真加速空间。
> 全部为本机实测，非估算。对比图见 `文档/加速实测对比/`（1~11 号）。

## 1. 核心结论

1. **第二程不是"白跑"，但也不省时间**。同输出尺寸下单程直出与双程耗时基本持平（差 0.8~4s）——第二程在 2.25 倍像素上跑 4 步，成本接近首程。
2. **单程直出画质更好**。第二程 = 1.5 倍潜空间 bicubic 插值 + 4 步 denoise 0.39，等于"再插值一次 + 再加一次噪"，会磨掉首程长出的高频细节。
3. **PornMaster_Krea2V25 慢的真凶是显存**：fp8 权重 12.5GB > 11.9GB 可用显存，每步都在搬权重。换 int4（7.7GB）快 1.8~2 倍。
4. **4K 超分是最大单项开销**（41~45s），是 2K 档（13~14s）的 3 倍；而 2K 档对 2MP 级源图只有 1.02 倍放大，基本只买"纹理重构"。
5. **MoodyZIT_V13 不能照搬这套优化**：它第一程 `return_with_leftover_noise=enable`，故意返回带噪 latent 给第二程，砍掉第二程会满屏彩色雪花。
6. **Flux2Klein9B 换衣没有安全加速空间**：4 步已是最低、没有第二程、主图分辨率直接等于成品分辨率。局部裁切采样实测能快 64%（23.2s → 8.3s），但会产生"画中画"崩坏，不可用（第 5 节）。

> **适用范围**：以上结论基于「单人特写/中景 + 浅景深 + 无文字」这一类提示词（id=1043 雨夜电话亭）。
> 多人同框、复杂道具、文字渲染等场景下，第二程在高分辨率重新组织构图可能反而更稳，
> 建议保留归档的双程工作流作为 A/B 对照再下结论。

### 2.3 SeedVR2 7B Q4_K_M 超分

| 档位 | 输出 | blocks_to_swap=24 | blocks_to_swap=8 |
|---|---|---|---|
| 2K | 1364x2048 | 14.0 s | **12.6 s** |
| 4K | 2730x4096 | **41.4 s** | 42.4 s |
| 1MP 源 → 2K | 1364x2048 | — | 14.2 s |
| 1MP 源 → 4K | 2730x4096 | — | 42.4 s |

- `resolution` 是**长边**。2K 档 = 长边 2048。
- 4K 是 2K 的 3 倍耗时（像素 4 倍），blocks_to_swap 在 4K 下几乎无影响（已 compute-bound）；2K 下 24→8 省 1.4s。
- 分辨率下拉在 `ResolutionPickerPlus`，`resolution` 与 `max_resolution` 同源，切档自动同步，**不需要单独建 2K 工作流**。

**放大倍数决定观感**（图 5/6）：

| 源 → 目标 | 倍数 | 结果 |
|---|---|---|
| 1MP (800x1200) → 4K | 4.1x | 皮肤塑料化、磨皮感、唇/杯盖边缘发虚 |
| 2.16MP (1200x1800) → 4K | 2.3x | 自然，唇纹/皮肤纹理保留 |
| 2.16MP → 2K | 1.02x | 尺寸几乎不变，只买纹理重构 |
| 1MP → 2K | 1.7x | 尺寸与观感都划算 |

**建议**：4K 前首程 ≥1.5~2MP；1MP 图停在 2K。

### 2.6 生成 + 超分：合并 vs 分开

| 方式 | 组成 | 总时间 |
|---|---|---|

## 3. 单程 vs 双程：1:1 差异在哪

同提示词、同 seed、同为 1128 宽（图 10/11）：

| 观察点 | 双程 8+4 | 单程 8 步 |
|---|---|---|
| 发丝 | 糊成一团 | 一根一根分开 |
| 头发上的雪晶 | 连成块 | 有独立形态 |
| 裙摆边缘 | 有 latent 插值的波纹/锯齿 | 干净 |
| 皮肤 | 二次加噪的细碎噪点 | 更平滑 |

**机理**：第二程的 latent 放大是 bicubic 插值（不产生新信息），再用 denoise 0.39 重采样 4 步；这一步既会"再糊一次"，也会"再加一次随机纹理"，因此高频细节被稀释。

**但**：双程并非一无是处——它用 4 步在 2.25 倍像素上"重新组织构图与大形"，对复杂构图偶尔更稳。所以归档而非删除。

## 5. Flux2 换衣为什么没有优化空间

结构上它已经是最简形态：4 步单程、没有第二程、没有 LoRA 链、没有额外控制网。

```
主图(全尺寸) → VAEEncode → ReferenceLatent 图1 ┐
参考图(1.5MP) → VAEEncode → ReferenceLatent 图2 ├→ CFGGuider(cfg=1) → SamplerCustomAdvanced(4 步) → VAEDecode
                                               ┘
主图(原尺寸) ────────────────────────────────→ ImageCompositeMasked(保留区贴回原图)
```

**为什么动不了**：

1. **步数已到底**：Flux2 Klein 是 turbo 蒸馏模型，4 步是它的设计下限，往下（3 步）通常崩结构。
2. **没有第二程可砍**：只有一次采样，不存在"双程冗余"。
3. **主图分辨率 = 成品分辨率**：`ImageResizeKJ` 保持原尺寸，`ImageCompositeMasked` 要用它做 destination（保留区按像素贴回原图）。降主图分辨率 = 保留区变糊，直接废掉"换衣但保人"的核心价值。
4. **参考图分辨率影响图案还原**：`ReferenceLatent` 是把参考图 latent 拼进注意力序列，token 数 ∝ 像素。1.5MP → 0.7MP 省 3.2s，但衣服花纹的还原精度会下降（越细的图案越明显）。
5. **显存不是瓶颈**：UNET 9GB + TE 8.3GB 是分时占用，不像 V25 fp8 那样每步搬权重。

**所以它只有三条路，且都不是"免费加速"**：

| 手段 | 收益 | 代价 |
|---|---|---|
| 参考图 1.5 → 0.7MP | -14%（3.2s） | 图案还原精度下降 |
| 主图降到 1.2MP | -23%（5.4s） | 成品分辨率与保留区清晰度下降 |
| 主图 + 参考图同时降 | -38%（8.8s） | 两者叠加 |

### 5.1 主图分辨率的影响（输出强制 = 输入）

同一张 1200x1800 主图，只改采样/输出尺寸：

| 主图 = 输出 | 像素 | 耗时（热） | 相对 2.16MP |
|---|---|---|---|
| 1200x1800 | 2.16MP | 23.2 s | — |
| 1024x1536 | 1.57MP | 20.3 s | -13% |
| 896x1344 | 1.20MP | 16.0 s | -31% |
| 768x1152 | 0.88MP | 12.8 s | -45% |
| 640x960 | 0.61MP | 11.9 s | -49% |

**成本模型**：约 `8 s/MP + 6 s 固定开销`。固定部分是参考图（1.5MP）的 VAE 编码 + 模型调度 + 解码，不随主图变小。所以 768→640 只再省 0.9s，收益衰减。

**质量**：输出 = 采样分辨率，像素少就是糊。1:1 看（图 14），768 版的睫毛、皮肤纹理、发丝明显软化。

**用超分补回来划算吗？**（图 14/15）

| 路线 | 时间 | 输出 |
|---|---|---|
| 原尺寸采样 | 23.2 s | 1200x1800 |
| 768 采样 + SeedVR2 2K | 12.8 + 14 = **26.8 s** | 1364x2048 |
| 896 采样 + SeedVR2 2K | 16.0 + 14 = **30.0 s** | 1364x2048 |

**都更慢**。而且 SeedVR2 会按真实照片分布重绘人脸，与"换衣要保人"的目标冲突。

**结论**：「输出强制 = 输入主图分辨率」是合理设计。只有一种情况值得降：**输入本身就是超大图（≥3MP），而目标输出本来就小**（只发社交）——这时降采样省的是真时间（成本 ∝ 像素，8.6MP 推算约 75s → 降到 2.16MP 只要 23s），并且不需要再超分。

---

**唯一有潜力的真加速：已实测，结论是不可用**（图 12/13）。

做法：`ImageCrop` 裁出躯干区域 → 只对该区域 4 步采样 → `ImageCompositeMasked` 按坐标贴回原图；latent 与参考图 1 都用裁切图。

| 方案 | 采样区域 | 耗时（热） | 相对全图 |
|---|---|---|---|
| 全图 | 1200x1800（2.16MP） | 23.2 s | — |
| 裁切 800 | 800x800（0.64MP） | 10.7 s | **-54%** |
| 裁切 640 | 640x640（0.41MP） | 8.9 s | **-62%** |
| 裁切 512 | 512x512（0.26MP） | 8.3 s | **-64%** |

**速度确实降了 2.2~2.8 倍，但画面废了**：贴回后出现"画中画"——裁切区里生成的是一个**完整的独立小人 + 自造背景**，贴回原图后像"画面中间嵌了一块小屏幕"。裁切越小越明显，512 版还有明显矩形硬边。

**根因**：Flux2 的 `ReferenceLatent` + 4 步采样是**整图生成语义**，不是局部重绘语义。裁掉上下文后模型不知道"这是一个更大画面的一部分"，只会按"整张图"重新构图。

**要避免崩溃，裁切框必须包含完整人物 + 周边环境**（约 900x1500 = 1.35MP），此时相对 2.16MP 只省 37%，还要处理边缘融合与尺度一致性——收益不足以抵消风险，4 步蒸馏下拼接接缝也很难控。

**结论**：局部采样这条路走不通。

**结论**：保持原样最稳。追质量就别降参考图；追速度的收益上限只有 8.8s，不如去优化别的环节（它单张 23s，已是 4 步蒸馏的下限）。

## 6. MoodyZIT_V13 为什么不能照搬

它的第一程 `return_with_leftover_noise=enable` 且 `end_at_step=12 < steps=17`：**故意只跑部分步数，把带残留噪声的 latent 交给第二程**。

- 直接解码第一程 → 满屏彩色噪点（图 9 中）
- 补齐 12 步完整采样 → 正常，但耗时 22s（640x960），加 2K 超分共 37.1s，与双程 36.5s 打平
- `cfg 3→1` 省 40%，但内容会变（杯子/内搭/道具都换，图 8），不可取

**结论**：ZIT 的结构本身合理（双程比同尺寸单程快 7.7s），没有 Krea2 那种"第二程冗余"。想更快只能降输出尺寸（640x960 → 512x768 约省 30%）。

## 8. 推荐出图流程

```
① 出候选：megapixels=1.0（752x1336，约 8s/张），同 prompt 多跑几个 seed
② 挑图：只对选中的处理
③ 出成品：
   - 要 2K：SeedVR2 下拉切 2K（约 14s）
   - 要 4K：先把 megapixels 提到 2.16 重出一张，再切 4K（约 63s 总计）
④ 需要更细皮肤/发丝：SeedVR2 已经能补，不必再叠 codeformer（叠了容易改脸）
```

核心原则：**超分比采样贵，只对选中的图跑**；分辨率预算花在首程，超分只做 2~2.5 倍。

## 9. 坑位

1. **UI 工作流的 `widgets_values` 与 `widgets_values_named` 可能不一致**。
   `PornMaster_Krea2V25_文生图_双程采样_8加4步_13节点.json` 的提示词在 `widgets_values` 里是空串，内容只存在于 `widgets_values_named`——用 API 提交会得到空提示词（跑出随机建筑图）。打开工作流时先确认提示词框有内容。

2. **`ResolutionSelector` 的实际输出不等于名字**。
   9:16 + 1MP → 752x1336；9:16 + 2.16MP → 1128x2008；2:3 + 2.16MP → 1232x1840。都以实测为准，别按名字推。

3. **`EmptyLatentImage` 里显示的宽高只是占位值**，实际由 `ResolutionSelector` 驱动，改分辨率请改 megapixels。

4. **上传到 ComfyUI 的图必须落在 `input` 目录**（本机为 `F:\ComfyUI_Migration\input`），`LoadImage` 只认这里。

5. **ComfyUI 对完全相同的 prompt 会命中缓存**（0.0s 返回旧图）。做耗时对比时必须换 seed 或换参数，否则测出来是缓存时间。

6. **工作流副本改完要重新校验连线**：bypass（mode=4）会把同类型输入直通到下游，但前提是上下游类型一致（LATENT→LATENT）。KSampler/LatentUpscaleBy 都满足。

## 11. 一句话总结

这一轮没有"变魔术式提速"：Krea2 的瓶颈是**第二程的插值+二次加噪**（换来画质）与**512MB 级的显存溢出**（V25 fp8），超分的瓶颈是**档位选错**。真正省时间的地方是「少对废图做超分」，不是把采样压到极限。
