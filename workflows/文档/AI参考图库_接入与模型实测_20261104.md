### 1.1 数据规模与结构（2026-11-04 实测）

**条目**

| 文件 | 条数 | 备注 |
|---|---:|---|
| `data/pose-zh.json` | 1,439 | 4 体系 / 26 分类 / 5 角度 |
| `data/costume-zh.json` | 1,407 | 8 分类，含内衣・睡衣 199、性感穿搭 140 |
| `data/portrait-zh.json` | 1,499 | 正脸参考 893 / 造型氛围 606 |
| `data/costume-anime-zh.json` | 440 | **外链**，`缩略图/原图` 指向 `charadb-2fi.pages.dev` |
| 合计 | **4,785** | 其中**本地 4,345** 条，440 条为远程热链 |

**图片**

| 目录 | 文件数 | 体积 | 内容 |
|---|---:|---:|---|
| `img` | 5,784 | 1,063MB | pose 原图 `.png`（1,439，直接在 `img/` 根） + costume/portrait/depth 的 `.webp`（子目录） |
| `thumbs` | 5,784 | 65MB | pose 缩略图 `.jpg`（1,439，直接在 `thumbs/` 根） + costume/portrait/depth 的 `.webp` |
| `img/depth` + `thumbs/depth` | 各 1,439 | — | 深度图与 pose id **100% 一一对应**（实测缺失 0），但 **JSON 里没有该字段**，必须按 `img/depth/{id}.webp` 派生 |
| 合计 | 11,568 个文件 | ≈1.13GB | 注意：`5,784` 是**单个目录**的文件数，不是图片总数 |

**结构坑（接 atelier 前必须知道）**

1. **扩展名不对称**：`pose` 是 `thumbs/{id}.jpg` + `img/{id}.png`；`costume` / `portrait` 是 `thumbs/{lib}/{id}.webp` + `img/{lib}/{id}.webp`。→ 只能用 JSON 的 `缩略图` / `原图` 字段，**禁止拼扩展名**。
2. **JSON 是中文键，四库字段互不相同**：`pose` 有 `体系/姿势编号/分类/姿势名称/角度`；`costume` 有 `分类/服装名称/标签[]/关键词/预览图`（`预览图 == 原图`）；`portrait` 有 `分区/发长/发型名称/标题/宽/高/精选/热门`。没有统一的 `prompt_zh/prompt_en/tags`。
3. **`检索` 字段是预拼好的全字段检索串**，直接子串匹配即可，不用自己拼索引。
4. **id 全局唯一**：四库内部无重复、跨库无交集（实测），`{library}/{id}` 可作路由键。
5. **敏感名单上游定义在** `src/api/gallery.ts:13-14`：`NSFW_POSE_SYSTEMS = {全身单人・性感系, 双人缠绵}`、`NSFW_COSTUME_CATEGORIES = {内衣・睡衣, 性感穿搭}`。`泳装・度假` 不算敏感；`portrait` 库上游**不标**敏感。
6. **根目录入口是 junction**：`workflows\ai-pose-gallery-zh` → `F:\ComfyUI_Migration\custom_nodes\ai-pose-gallery-zh`。别用 `<library_root>/../custom_nodes/...` —— 实测该路径**不存在**；跨卷 junction 上 `exists()` 会抛 `WinError 448`，需用 `_resolve_if_reparse`。

## 3. 模型与步数实测

同一组人像/服装/白模躺姿、同一提示词、同一种子，只改步数。

| 方案 | 4 步 | 6 步 | 8 步 | 结论 |
|---|---|---|---|---|
| Flux2 Klein 9B turbo（三图） | 30.2s | **34.2s** | 42.1s | 6 步甜点；8 步更锐但构图收紧 |
| Nunchaku fp4（2509 Lightning） | **48.2s** | 50.7s | 58.3s | 4–6 可用；8 步脸漂移 |
| Qwen 2509 GGUF + Lightning LoRA | **54.2s** | 崩（头部错位） | 部分恢复但仍扭曲 | 只能 4 步 |
| Qwen 2.1 turbo（三图） | — | — | 8 步 32.4s / 12 步 16.1s | 12 步最好，仍是草稿级 |

文生图补充测试：

| 工作流 | 测试点 | 结论 |
|---|---|---|
| Qwen21 长中文提示词 | 16 / 24 / 32 / 40 步（28 / 30 / 40 / 48s） | 32 步默认合理；24 步可省时间；16 步手持物与背景偏糊 |
| Flux2 单图编辑 | 4 vs 6 步（均 18.1s） | 无可见差异，保持 4 |
| Flux2 双图换衣 | 4 vs 6 步（22.1 / 26.1s） | 6 步略锐但多 4 秒，保持 4 |

**通用结论**

- 蒸馏模型（Lightning / turbo）的步数是训练点，不是“越高越好”；超出会崩或漂移。
- 清晰度指标不能单独作为质量判据（2509 的 6 步指标最高但画面是崩的）。
- 步数结论只对同模型有效，不能推广到 Krea2（8 步）、ZIT（17/11 双程）等其它工作流。

### 3.1 四图参考实测（2026-11-04，Flux2 Klein 9B turbo 6 步）

目的：确认「在现有三图工作流上加第 4 张参考」是否有代价、是否真的生效、以及接法对结果的影响。

**接线方式**（`#1/#2/#3` 之后追加一路，其余不动）：

```
#78 LoadImage(第4张) → #79 ImageScaleToTotalPixels(1.0MP) → #80 VAEEncode
   → #81 ReferenceLatent(cond=#65)  → CFGGuider.positive
   → #82 ReferenceLatent(cond=#68)  → CFGGuider.negative
```

**同源素材**：人像 `f71f980dde3`（短发・标准款）、服装 `SPR-0001`（象牙白荷叶边针织 + 牛仔迷你裙 + 大衣 + 白短袜 + 白运动鞋）、姿势 `full_single_P015_front`（站立・对立式平衡・手扶腰）；输出尺寸由人像图决定，成品 874×1090。

| 组 | 参考数 | 第 4 张内容 | 种子 | 执行耗时 | 结果 |
|---|---|---:|---:|---:|---|
| A | 3 | — | 42 | 42.8s | 基准：人像/服装稳定，姿势偏随意 |
| A | 3 | — | 777 | 35.4s | 基准：姿势（手扶腰）贴合更好 |
| B | 4（链尾） | 同姿势斜侧（无冲突） | 42 | 41.1s | 与 A 无明显差异 |
| C | 4（链尾） | `AUT-0003`（橄榄绿针织+皮裙+黑裤袜+麂皮靴，**与图2 冲突**） | 42 | 41.9s | 上衣/裙跟图2，**鞋袜被换成图4 的黑裤袜+麂皮靴**，多出丝巾与小挎包 |
| C | 4（链尾） | 同上 | 777 | 42.3s | 同上，跨种子稳定复现 |
| D | 4（**链首**） | 同上 | 42 | 49.5s | **图2 服装几乎被压制**：整体变成图4 的橄榄绿针织 + 棕皮裙 + 黑裤袜 + 靴 |

**结论**

1. **第 4 条 `ReferenceLatent` 本身没有代价**：不劣化、不明显变慢（41–50s vs 35–43s，落在同模型噪声区间）。
2. **第 4 张确实生效**，不是“接上去被忽略”。
3. **顺序决定权重**：接链尾 = 部件级补充；插链首 = 覆盖前序参考。
4. **语义重叠会产生部件级混搭**（上衣跟图2、鞋袜跟图4），跨种子可复现；这不是崩坏，但不可控，必须靠使用约束规避。
5. 对"角色设定集"这种与图1 争身份的用法风险更高，不建议作为第 4 张。

**用法约束**：第 4 张只补 `#1/#2/#3` 未覆盖的维度（鞋/包/配饰、场景光线、氛围质感），接链尾，不放第二套完整服装或第二张人像。

## 4. 输入与构图约束（踩坑记录）

| 问题 | 现象 | 处理 |
|---|---|---|
| 人像用脸部特写 + `ReferenceLatent` | 构图被压成大特写，姿势丢失 | 全身模式去掉人像像素参考，仅保留语义编码 |
| 姿势图大面积留白（躺姿/横姿） | 姿势信号被稀释，输出站姿 | 姿势图先裁到内容边界（`PoseTrimWhitespace`） |
| 深度图渐变背景 | 四角取色失效，等于没裁 | 节点改为亮度阈值兜底（渐变背景自动识别） |
| 2509 Lightning LoRA 加步数 | 6 步头部崩坏 | 锁定 4 步、cfg 1.0 |
| Qwen 2.1 三图 | latent 跟随第一张参考 | 姿势必须放第一张，才会跟姿势 |
| Q4 GGUF 文本编码器 | `mat1/mat2` 维度不匹配 | Qwen Image Edit 需要 mmproj 视觉投影，Q4 GGUF 不可用 |
| 安全模式 | 只隐藏 UI，接口仍返回全量 4,785 条 | 接 atelier 时必须做后端过滤（名单见 §1.1 第 5 条） |

**自动裁边节点**：`F:\ComfyUI_Migration\custom_nodes\comfyui-pose-trim`
（按背景色 + 容差取内容边界；渐变背景回退到亮度阈值）。

## 5. 与 atelier 融合的建议

**不建议 fork 这个 React 合成台**。atelier 是 Vue + FastAPI，长期应以 atelier 为唯一生产入口；画廊退化为“数据与素材层”。

推荐分层：

```
参考图库（只读数据）  ←  gallery 的 data/*.json + thumbs/img/img/depth（junction 路径）
        ↓ 适配层
atelier 后端（新增 reference_library service + router + recipe_prompt）
        ↓
atelier 前端（/reference 参考库页 + 出图面板）
        ↓
现有生成链路（editor 三角色注入 + 任务队列 + 画廊归档）
```

> 三合一拼图（Canvas 1800×1200 导出）**不进本期**：atelier 出图直接吃三张原图，拼图只有“素材带走”用途。

落地顺序（v0.3 裁剪版，详见融合计划 §4）：

1. **M1 只读参考库**：列表、中文检索、facet 筛选、白模/深度切换、缩略图走上游 `thumbs/`；敏感分类在后端按配置过滤。
2. **M2 三图出图**：移植画廊 `buildRecipePrompt`（`src/services/aiGenerator.ts:155`）+ 直接复用 atelier 已有的 `/api/editor/faceswap/batch`（三角色 `target/ref1/ref2`、绝对路径素材、`cross/zip` 批量、任务队列），不新写注入与提交。
3. **M3（可选）单条转提示词**：写 `prompts`（`【类型】\n正文`，`note=ref:{library}/{id}`），**不做批量**——`prompts` 只有 355 条，是 composer 的随机池，批量导入会把它稀释 13 倍。
4. **不做**：收藏表、批量随机（`editor` 的 `cross/zip` 已覆盖）、拼图导出、云端协议、退役 React 台（留作上游契约对照）。

需要坚持的边界：

- **上游仓库保持零修改**，翻译/分类等覆盖数据放外部（如 `参考库覆盖/`），由适配层合并；
- 画像素材走路径引用，不复制进 atelier 库，避免 1.13GB 双份；
- 安全模式的判定规则（体系/分类名单）放配置，别写死在前后端两处；
- 生成工作流继续放在 `workflows/` 根目录，工作室与 atelier 共用同一份 API 契约；
- **atelier 是唯一生产入口**，React 台只作上游契约变化的对照物，不投入新功能。
