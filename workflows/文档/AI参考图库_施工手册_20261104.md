## 0. 先看这个：开几个、什么顺序、什么时候开下一个

**总共 6 个会话，分 4 个波次，同一时间最多 3 个。**

```
① 开【会话 1】
      ↓ 它先做骨架，交 commit「接入骨架与契约」
② 骨架 commit 到手后：同时开【会话 2】【会话 3】（会话 1 继续跑它的 M1 后端，别打断）
      ↓ 等 1、2、3 三个都交付（各自有 commit + 验证结果）
③ 同时开【会话 4】【会话 5】
      ↓ 等 4、5 交付
④ 开【会话 6】收尾（全量回归 + 文档回写）
      ↓ ci 全绿、文档勾选完成 → 结束
```

**三条铁律**

1. **同一波次不超过 3 个会话**。本机单 GPU、单 SQLite、单 8656 端口，冲突比算力更容易出事。
2. **不要两个会话改同一个文件**（每个会话的白名单见各自小节）。跨波次交接前必须有 commit。
3. **只有会话 4 可以真的出图**（提交 `/prompt`）。其它会话验证一律 `dry_run=true` 或只跑单测。

## 8. 提交与推送（分批次）

- **每个会话自己 commit**（消息见各节末尾），**不要 push**。
- **每个波次结束由你 push 一次**，这样 GitHub 上是"一批一批"的记录，出问题也好回滚：

| 时点 | 你执行 | 预期 GitHub 上新增 |
|---|---|---|
| 会话 1 骨架完 | `git push` | 接入骨架与契约 |
| 波次 B 结束（1/2/3 交付） | `git push` | 参考库只读服务、参考图库页面、上传端点 |
| 波次 C 结束（4/5 交付） | `git push` | 三图出图+第四张、参考板导出 |
| 会话 6 结束 | `git push` | 单条转提示词、收尾回归 |

- 若某个会话搞砸了：`git log --oneline -5` 找到它之前那个 commit，用 `git reset --hard <commit>` 回滚（**先确认没有别的会话正在写文件**）。

## 9. 常见状况

| 现象 | 处理 |
|---|---|
| 两个会话都要改 `app/main.py` | 说明白名单没遵守，让后开的那个停下，等前一个 commit 后再做 |
