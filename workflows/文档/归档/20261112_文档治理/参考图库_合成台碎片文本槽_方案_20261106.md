# 参考图库 · 合成台碎片文本补充方案（2026-11-06 · 修订版 v3）

> 目的：让 `/reference?tab=studio` 在保留三槽图片能力的前提下，**八类提示词碎片都可以用文本补充**，
> 每类可填可不填；图片槽可空可填，文字既能替代空槽、也能在图片存在时作为额外特征补充。
>
> **修订说明（v3）**：按用户 2026-11-06 拍板修正需求口径——v2 的"三槽切文本、文字替代图片"只覆盖了一半，
> 真实需求是"八类碎片可补充、替代/补充双态"。同时纳入审核结论：C5 第 4 张隐藏已实现不再是待办、
> 图号错位升级为 P1 前置验证、画风技术碎片与画风预设互斥、碎片池需 NSFW 启发式过滤。

## 一句话结论

需求不是"三槽切成文本框"，而是"**三槽图片照常 + 八类碎片文本补充**"：
槽空时文字替代（句式替换），槽有图时文字只作额外特征追加（图片主句保留）。
因此 v2 的三处判定修正仍然需要（替代态会触发），但范围收窄；图号错位是**既有缺陷**，
必须在 P2 之前先验证并修掉，不能留到验收阶段再发现。

## 0. 需求口径（v3 核心修正）

### 0.1 用户拍板的语义

- 八类碎片都可以用文本补充，任何一类可空。
- 三槽图片：可空、可填；文字既能替代空槽，也能在图片存在时作补充。
- **补充态下：图片主句保留，文字只作额外特征补充**（用户原话）。

### 0.2 八类碎片与槽位的对应关系

| 碎片类型 | 归属 | 说明 |
|---|---|---|
| 人物面部 | 人像槽 | 替代或补充人像描述 |
| 人物身材 | 人像槽 | 替代或补充人像描述 |
| 人物服饰 | 服装槽 | 替代或补充服装描述 |
| 姿态动作 | 姿势槽 | 替代或补充姿势描述 |
| 拍摄视角 | 纯修饰 | 无对应槽，始终追加 |
| 场景环境 | 纯修饰 | 无对应槽，始终追加 |
| 光影色调 | 纯修饰 | 无对应槽，始终追加 |
| 画风技术 | 纯修饰 | 与画风预设互斥（见 §5.4） |

### 0.3 替代态与补充态

| 状态 | 判定 | 渲染方式 |
|---|---|---|
| 替代态 | 对应槽无图，且该类碎片有内容 | 用文本版句式替换图片版主句（§5.1） |
| 补充态 | 对应槽有图，且该类碎片有内容 | 图片主句保留，文字作"额外体现"追加（§5.2） |
| 空态 | 槽无图、也无碎片 | 该槽不参与出图（沿用现有裁剪） |
| 纯修饰 | 拍摄视角 / 场景环境 / 光影色调 / 画风技术 | 始终追加，插在"补充要求"之前（§5.3） |

全局约束不变：**至少保留 1 张图**；三槽全空（0 图）交给 `/composer`（§3 C1）。

## 2. 现状盘点

| 页面 | 本质 | 产物 | 关键代码 |
|---|---|---|---|
| `/prompt` | 提示词库 CRUD，碎片只是**筛选维度** | 提示词记录 | `app/routers/prompts.py`、`views/PromptView.vue` |

- **Studio 提示词不是标签堆**，是强约束 bullet 句，由 `recipe_prompt.build_recipe_prompt()` 生成。
- **空槽已支持裁剪**：`_trim_unfilled_slots()` 删空槽的 `LoadImage` + `images.image_N` 键，并按真实图号重写 `index_map`。
- **第 4 张已在无 `extra` 工作流下隐藏**：`useReferenceRecipe.ts:1752` 的 `supportsExtraSlot` 按 `workflow.slots` 判定，
  `ReferenceStudioTab.vue:855-856 / 893-894` 整块不渲染。Qwen21 的 `slots` 不含 `extra`，入口当前就是隐藏的。

### 唯一工作流的真实结构（必须记住，标题是错的）

`图库专用_Qwen21+VNCCS_三图_25步_单人.api.json`，11 个节点：

| 节点 | 类型 | 标题 | 真实角色 |
|---|---|---|---|
| 1 | LoadImage | 图3：姿势参考 (Pose) · 深度图 | **image_1 = 姿势** |
| 2 | LoadImage | 图1：人像参考 (Portrait) | **image_2 = 人像** |
| 3 | LoadImage | 图2：服装参考 (Costume) | **image_3 = 服装** |
| 7 | LoraLoaderModelOnly | VNCCS 姿势 LoRA（QI2 v1.1，必须 1.0） | 姿势专用 LoRA |
| 8 | TextEncodeQwenImage21 | 正向提示词 | `prompt` / `negative_prompt` / `images.image_1..3` / `resolution=1024`，输出 positive + negative + latent |
| 9 | KSampler | 25 步 · cfg 2.5 | `positive=["8",0]` / `negative=["8",1]` / `latent_image=["8",2]` |

**标题里的「图N」与 `image_N` 编号是错位的**：姿势是图1、人像是图2、服装是图3。
`loadimage_role()` 只认角色关键词、`_build_index_map()` 只信 `image_N` 键——这是对的，不要"顺手修正"标题。

**latent 来自 node8 的第三输出**，不依赖 LoadImage；`resolution=1024`，实测输出 896×1184（3:4，与姿势图比例一致）。

## 3. 硬约束

### C1 至少留 1 张图（唯一不可绕过的约束）

`create_reference_recipe` 里 `total == 0` 直接 400（文本补充不计入 `filled`）。
三槽全文本 = 文生图，引导去 `/composer`。

> **P0 已实测（2026-11-06，结论更新）**：删掉 3 个 LoadImage 与 `images.image_1..3` 后，
> ComfyUI `POST /prompt` 返回 HTTP 200，状态 success，95.6s 出 1024×1024 非退化图。
> 即 **0 图在 ComfyUI 层技术可行**（node8 latent 来自 `resolution=1024`，不依赖图片）。
> 产品仍保持"至少留 1 图"：0 图与 `/composer` 功能重叠，且本次 0 图实验用的是工作流默认提示词，
> 带 Studio 提示词的 0 图场景未验证。详见 §11。

### C2 可空槽：Qwen21 任意槽

依据 `文档/参考图库_合成台工作流实测矩阵_20261106.md`：Qwen21 的 7 种非空组合全部 done。
因此后端按工作流探测一次、返回可空槽位数组（当前恒为 3 个），前端只用来做"至少留 1 图"校验与未来扩展。

### C3 替代态会静默改变 3 处既有判定（P2 前置必改）

现有代码用"槽位是否有图"承载业务语义。**替代态**让"没图但有文本"成为合法状态，三处判定会出错。
补充态（槽有图）不受影响，修正范围只限替代态。

| # | 位置 | 现有逻辑 | 替代态后果 | 修正 |
|---|---|---|---|---|
| C3-1 | `create_reference_recipe` | `if body_mode == "costume" and not filled["costume"]: body_mode = "bare"` | 服装槽用文字 → 被判素体，提示词写「不穿任何服装」 | 条件补 `and not costume_text` |
| C3-2 | `build_recipe_prompt` | `faceless = not portrait and bool(costume and pose)` | 人像槽用文字 → 误判无脸，抹掉描述的脸 | 改为 `not (portrait or portrait_text)` |
| C3-3 | `build_recipe_prompt` | `is_pair = pose.id.startswith("pair")` | 姿势槽用文字 → 双人语义丢失 | **先禁止姿势文本选双人**（用户 2026-11-06 拍板）；将来再做显式"人数"开关 |

> C3-3 的落地口径（已拍板）：姿势槽切文本时，若当前姿势库选择是 `pair*` 双人组，
> UI 直接禁止提交替代态并提示"姿势文本暂不支持双人，请保留姿势图或换单人姿势"；
> 后端对 `pose_text` 非空且请求带双人语义的输入做防御性 400。补充态（姿势图仍在）不受影响。

> C3-1 的背景注释值得保留：缺服装时 Qwen 会自由发挥（实测连续出裸体），
> 所以这条兜底不能删，只能扩成"既无服装图也无服装文本"。

### C4 碎片文本长度不受控

实测 `atelier/data/prompts.db`：**355 条提示词 → 2175 条去重碎片**，单条最长 783 字，
八类分布：人物面部 292 / 人物身材 224 / 人物服饰 280 / 姿态动作 295 / 拍摄视角 307 / 场景环境 282 / 光影色调 235 / 画风技术 260。

处置：单槽软上限 2 条碎片；UI 显示字数；不静默截断。

### C5 第 4 张上传块（已实现，不再列为待办）

工作流只有 3 个 `LoadImage`，`total > input_count` 会 400。
前端 `supportsExtraSlot` 已按 `workflow.slots` 隐藏整块，Qwen21 的 slots 不含 `extra`。
**P1 只需回归确认，不实现**；若用户要求从"隐藏"改成"禁用并说明"，再单列。

### C6 姿势替代态的质量与画幅风险

- 工作流挂了 `VNCCS 姿势 LoRA`（weight 固定 1.0），专为姿势/深度图训练。姿势槽切纯文本后 LoRA 仍在作用但**没有骨架输入**，姿势还原会明显退化。
- **画幅也会变**：node8 的 latent 来自 `resolution=1024`，实测 896×1184 正是姿势图的 3:4 比例；删掉 `image_1` 后，比例改由剩余第一张图（人像）决定，可能不是 3:4。
- 处置：D9 排在最后 + UI 提示；P2 验收必须记录输出尺寸变化。

### C7 图号错位（P0 已实测：当前组合未错位，不前置改压缩序号）

`_build_index_map()` 按 `images.image_N` 的 N 写"图N"，且**裁剪后不压缩重排**。

- 现有空槽会触发：人像图 + 服装图、姿势空时，提示词写"图2人物 / 图3服装"，而模型只收到 2 张图。
- 文本替代态的典型用法（保留人像、服装/姿势用文字）会保留 `image_2`、删 `image_1/image_3`，提示词仍写"图2中的人物"。

**P0 实测结论（2026-11-06，证据见 §11）**：

- 组合「人像图 + 服装图、姿势空」真实出图 1 张（job 241，205.5s，928×1152）。
- ComfyUI history 实证：裁剪后 node8 只含 `images.image_2=["2",0]`、`images.image_3=["3",0]`，`image_1` 缺失。
- 提示词写「2 张参考图 / 图2中的人物 / 图3中服装」，输出人脸与发型来自人像图、8 件服装单品全部来自服装图，
  **无互换、无串位**；主控独立图像复核与子代理盲测结论一致，`verdict=no_mismatch`。

**处置（v3 修订）**：

1. **不再把 `_build_index_map()` 压缩重排作为 P2 前置必改**——当前唯一的 studio 工作流在"稀疏 image_N"下按图号语义工作正常。
2. 仍保留观察项：只保留单张 `image_2`（人像替代 + 服装/姿势都替代）的组合**未实测**；
   P2 验收时必须补这一组，若出现反例再改压缩序号。三图齐全时压缩序号与原行为一致，改动风险可控。
3. 不改 `_build_index_map()` 现有行为，避免无必要地动已验收的 896×1184 基线。

### C8 碎片池没有 NSFW 过滤

`prompts` 表**没有 nsfw 字段**，`_get_fragment_data()` 也不过滤。
安全模式开启时，碎片池仍会显示敏感碎片。

处置（用户拍板）：按 `tags` / `note` 关键词做启发式过滤，关键词表参考参考图库现有的 NSFW 分类口径；
在文档与 UI 上如实标注"无法保证全覆盖"。

### C9 碎片自带 `negative_prompt`（机会点）

`prompts` 表字段含 `negative_prompt`。P1 的负向除了用户手填，可以考虑从所选碎片带出；
本轮先不做，列为待观察（§10）。

## 4. 数据契约

### 4.1 前端状态

**P1（补充态）**：三槽图片不变，只新增一个 8 类碎片表，所有类都作为"补充"：

```ts
export interface SelectedFragment { type: FragmentType; content: string }

export interface RecipeTextFragments {
  人物面部: SelectedFragment[]
  人物身材: SelectedFragment[]
  人物服饰: SelectedFragment[]
  姿态动作: SelectedFragment[]
  拍摄视角: SelectedFragment[]
  场景环境: SelectedFragment[]
  光影色调: SelectedFragment[]
  画风技术: SelectedFragment[]
}
```

- P1 不引入 `RecipeSlotMode`；槽位仍沿用现有 `RecipeSlotState<T> { items: T[] }`。
- 8 类碎片全部可空；同类多碎片槽内拼接，不参与笛卡尔积维度。
- 提交时按归属编译：面部/身材 → `portrait_text`，服饰 → `costume_text`，姿态 → `pose_text`，后四类 → `modifier_fragments`。
- 持久化沿用 `pb.reference_studio_v1`，扩展 `textFragments: RecipeTextFragments`（存 `{type, content}` 全文）；
  体积预估 8 类 × 2 条 × 783 字 ≈ 12KB，可接受。

**P2（替代态）新增**：`RecipeSlotMode = 'image' | 'text' | 'empty'`；`mode='text'` 时该槽的对应类碎片作为替代文本；
持久化再扩 `portraitMode` / `costumeMode` / `poseMode`。

### 4.2 后端提交体

`RecipeRequest` 新增可选字段，缺省走旧逻辑：

| 字段 | 类型 | P1 语义（补充态） | P2 语义（替代态） |
|---|---|---|---|
| `portrait_text` | `str` | 人像补充文本（槽有图时追加） | 槽无图时作为人像主描述 |
| `costume_text` | `str` | 服装补充文本 | 槽无图时作为服装主描述 |
| `pose_text` | `str` | 姿势补充文本 | 槽无图时作为姿势主描述 |
| `modifier_fragments` | `str` | 修饰层渲染结果（视角/场景/光影/画风，多行 `• 类型：内容`） | 同左 |
| `negative_prompt` | `str` | 真负向（透传 `FaceswapRequest.negative_prompt`，字段已存在） | 同左 |

**P1 只做补充**：`*_text` 只在对应槽有图时生效；槽无图 + 文本 → 400（P2 才开放替代）。
前端不需要传 mode 字段，P1 也不会传。

校验规则：

- 【P1】某槽 `*_text` 非空但该槽无图 → 400，文案"该槽文本替代尚未开放，请先选择参考图或清空文本"。
- 【P1】`body_mode='bare'` 且给了服装图或服装文本 → 400。
- 【P1】所有槽无图 → 400（等价现有 `total == 0`）。
- 【P1】补充态不改变 `filled`、不改变裁剪。
- 【P2】某槽同时给 `*_id` 与 `*_path` → 400（沿用现有优先级规则，不猜）。
- 【P2】文本替代槽不计入 `filled`，仍交给 `_trim_unfilled_slots` 裁剪（**不加新分支**）；三槽全无图 → 400。

### 4.3 工作流能力字段（降级为可选）

## 5. 提示词渲染规则

### 5.1 替代态（槽空 + 文本）

| 槽 | 文本版 |
|---|---|
| 人像 | `• 人物：一位 {人物面部碎片}；{人物身材碎片}。肤色与质感按风格要求呈现。` |
| 服装 | `• 服装：人物穿着 {人物服饰碎片}，颜色、款式、面料与配饰以文字描述为准。` |
| 姿势 | `• 姿势：{姿态动作碎片}。保持重心、胯部朝向、肩线、手臂位置与膝盖弯曲的自然关系；不要军姿，不要 T-pose，不要双脚并拢。` |

### 5.2 补充态（槽有图 + 文本）：图片主句保留，文字只作额外特征

| 槽 | 图片主句（保留） | 追加的补充分句 |
|---|---|---|
| 人像 | `• 人物：图N中的人物，保持其脸型、五官、发型（X）和发色一致。{肤色句}` | `；在保持一致的基础上，额外体现：{人物面部碎片}；{人物身材碎片}。` |
| 服装 | `• 服装：让人物穿上图N中展示的整套服装和配饰（参考名称：X）…` | `；在保持图N款式与颜色的基础上，额外体现：{人物服饰碎片}。` |
| 姿势 | `• 姿势：严格复现图N中人体模型的身体姿态与镜头角度…` | `；在保持图N姿态的基础上，额外体现：{姿态动作碎片}。` |

约束：

- 补充分句**不覆盖**"保持图N一致"的主句（用户拍板）。
- 文本槽 / 补充文本**不写"图N"**；`_figure_no()` 只对已填图片槽生效。
- 若正文示例里的"额外体现"与实际碎片语义冲突（例如碎片是完整脸型描述），模型自行权衡，这是用户接受的行为，不做额外拦截。

### 5.3 修饰层（始终追加，插在"补充要求"之前）

```
• 拍摄视角：…
• 场景环境：…
• 光影色调：…
• 画风技术：…
• 补充要求：…        ← prompt_suffix（原样保留，与碎片并存）
```

- **拍摄视角碎片优先于库条目 `pose.angle`**：有拍摄视角碎片时，姿势段不写 `镜头角度：{pose.angle}`，改用碎片；否则保留原逻辑。
- 修饰层类型去重按 `type||content` 精确匹配，与 composer 一致。
- 注入 CLIP 前仍需 `strip_headers()`（`【类型】` 只做人读标记）。

### 5.4 画风技术碎片与画风预设互斥（用户拍板）

- 前端：选了"画风技术"碎片时，画风预设下拉置灰/禁用，并给一句"已用碎片描述画风"。
- 后端：`style` 与 `modifier_fragments` 同时存在时，**只渲染碎片，不追加固定 `• 风格：{STYLE_PRESETS[style]}` 段**。
- `is_photo` 判定：若选了画风碎片，`is_photo` 按 `style` 仍为 `realistic` 时的"真人"措辞保留；若用户切到 `none`，按非真人处理。
  文档明确：**画风碎片只替代"风格描述段"，不替代"真人/非真人"的主体判定**。

### 5.5 前端 UI 落点：全宽「文本补充」卡（2026-11-06 拍板）

**位置**：素材区（三槽 + 第 4 张）之后、组合清单之前。页面顺序 = 选图 / 选文字 → 看清单 → 调参数 → 预览 → 结果。

- 卡头：`文本补充（八类碎片，可选）` + `已选 N 条` 徽标 + 展开/收起；**默认折叠**，不选时不占高度。
- 卡内两列（宽屏并列，窄屏单列）：
  - 左列「与参考槽对应」：人物面部、人物身材（人像槽）；人物服饰（服装槽）；姿态动作（姿势槽）。每类名前置一个彩色归属标签，不用 emoji。
  - 右列「画面修饰」：拍摄视角、场景环境、光影色调、画风技术。
- 每类一行：`类型名` + 归属标签 + 已选碎片 chips（可删）+ `选择碎片` 按钮 + `n/2 条 · x 字`。
- 选择弹层：按 `fragment_type` **分类懒加载**（单类 224–307 条），前缀搜索，多选，单类软上限 2 条；**禁止一次拉 2175 条**。
- 负向输入框：放在卡底部，label `负向提示词（可选）`，说明「最终负向 = 后端自动抽取 + 你填写的内容」。
- 画风联动：选中「画风技术」碎片 → 参数卡的画风预设下拉禁用并提示「已用碎片描述画风」；前端同时把 `style` 置 `none`。
- 不选碎片时卡头仍常显，保证入口可发现。

## 7. 联动边界

### 做什么

| 项 | 理由 | 成本 |
|---|---|---|
| 复用 `GET /api/composer/fragments` | 唯一合理碎片来源，支持按 `fragment_type` 懒加载 | 无（现成） |
| 复用 `services/fragment_syntax.py` | 解析/渲染/去重单一真源 | 无（现成） |
| 碎片卡片显示来源 + 跳 `/prompt/:id?frag_type=xxx` | 深链已存在（`PromptView.vue:445-519`），单向、不改状态 | 极低 |
| dry-run 预览即时反映文本补充与负向 | `previewPrompt` 已在（防抖 400ms） | 低 |

### 不做什么

| 项 | 理由 |
|---|---|
| Composer → Studio 跳转 | Composer 出口是 `/api/composer/run` 直接出图，绕道 Studio 投图无收益 |
| Studio → Composer 跳转 | `【类型】` 与 bullet 指令句范式不同，互传必有损 |
| Studio 结果「存为提示词」 | 生成的是 500–800 字 bullet 长句，会被 composer 当碎片解析，污染 2175 条池子 |

判据：**要的是数据层复用，不是页面级跳转。**

## 14. P3：提示词分段编辑与手动改写（2026-11-06）

### 14.1 用户反馈

- 提示词是一整块只读 `<pre>`，看不出每个碎片，无法编辑。
- 八类碎片互相冲突时（例如「户外拍摄视角」+「室内卧室场景」），一眼看不出来。

### 14.2 设计（v2，2026-11-06 按交互理论重做）

设计依据：

- **Direct manipulation**（[NN/g](https://www.nngroup.com/articles/direct-manipulation/)）：对象本身可操作、反馈即时。因此不设「阅读态 / 编辑态」，每段默认就是 textarea。
- **User control and freedom**（[NN/g #3](https://www.nngroup.com/articles/user-control-and-freedom/)）：任意时刻可「恢复自动生成」，手动修改不会被后台刷新悄悄覆盖。
- **Visibility of system status**（[NN/g #1](https://www.nngroup.com/articles/visibility-system-status/)）：顶部常显「自动生成 / 已手动修改」、段数与字数。
- **Progressive disclosure**（[NN/g](https://www.nngroup.com/articles/progressive-disclosure/)）：删除顶部目录 chips（与段标题重复），只保留段标题 + 来源 + 字数；信息不重复，认知负担更低。

实现口径：

- 自动生成保留：碎片 → 后端 dry_run → 返回编译后 `prompt`；未修改时 textarea 跟随刷新。
- 前端把 `prompt` 按行解析为分段：开头、`• 标签：内容` 段、结尾；每段一张卡片，标签彩色（人物/服装/姿势/拍摄视角/场景环境/光影色调/画风技术/风格/补充要求）。
- **任一段输入即视为手动修改**：拼回完整原文作为 `prompt_override` 提交；不再有「手动改写」按钮。
- 手动修改提交时 `skip_compile=true`：后端按原文写入正向，负向只用用户填写的 `negative_prompt`，不再 `compile_prompt` 二次改写。
- 「恢复自动生成」清空 `prompt_override`，重新跟随碎片；素材 / 碎片变化不会覆盖已修改文本，避免吞编辑。
- 负向块保留；已手动修改时提示「负向只包含你填写的内容，不再自动抽取」。
- `prompt_override` 非空时跳过 P2 的槽位文本校验与 `build_recipe_prompt`；仍保留至少 1 图、裁剪、图号、`body_mode`。
- 手动内容全空时卡片内警告并阻止提交，避免空 override 被后端当自动模式静默回落。

### 14.3 契约

- `RecipeRequest.prompt_override: str = ""`；非空 = 手动模式。
- `FaceswapRequest.skip_compile: bool = False`；`inject_prompt` 在 true 时跳过 `compile_prompt`，直接写正向/负向。
- dry_run 返回 `prompt`（原文）、`prompt_raw`（同原文）、`negative_prompt`（用户负向；负向不生效时为空）、`manual_override=true`。
- 前端 `RecipeSubmitRequest.prompt_override?: string`；手动模式不发送三槽文本/修饰/后缀。

- **核心瓶颈是显存**：RTX 5070 12GB + Qwen-Image 2.1 int8 UNet（约 12G）+ Qwen3-VL 8B fp8 文本编码器 + LoRA/VAE，权重总量约 20G，超过显存，ComfyUI 必须换入换出；0.75× 稳定几十秒，1.0× 约 1–2 分钟，1.5× 5 分钟，2.0× 13 分钟。已启用 `--use-sage-attention --cuda-malloc`，不是前端或采样器配置漏项。
- **文生图为什么 30–40s**（2026-11-06 补测）：`历史工作流/QwenImage21_NSFW_文生图_8步_turbo_12G.json` 用的是**同一颗 UNet + 同一颗 Qwen3-VL**，但只有 **8 步、cfg=1.0、832×1216**；合成台是 **25 步、cfg=2.5、896×1184**。同一三图 + 同一提示词下受控计时：

| 配置 | 参考图 | steps | cfg | 输出 | 实测 |
|---|---|---|---|---|---|
| 文生图 8 步 turbo | 0 | 8 | 1.0 | 832×1216 | 用户观测 30–40s |
| 合成台 8 步 | 3 | 8 | 1.0 | 896×1184 | **29.2s** |
| 合成台 8 步 | 3 | 8 | 2.5 | 896×1184 | **42.2s** |
| 合成台 12 步 | 3 | 12 | 2.5 | 896×1184 | **46.4s** |
| 合成台 16 步 | 3 | 16 | 2.5 | 896×1184 | **56.6s** |
| 合成台 25 步 | 3 | 25 | 2.5 | 896×1184 | **82.4s** |
| 合成台 0.75× 12 步 | 3 | 12 | 2.5 | 672×896 | **30.2s** |
| 合成台 0.75× 8 步 | 3 | 8 | 2.5 | 672×896 | **16.1s** |
| 合成台 0.75× 8 步 cfg1.0 | 3 | 8 | 1.0 | 672×896 | **8.0s** |

  CFG>1 每步要再算一次无条件分支，所以 25 步 × cfg2.5 ≈ 50 次前向，8 步 × cfg1.0 ≈ 8 次前向；**步数与 CFG 才是 30s 与 100s 的主因**，参考图与 LoRA 只是次要开销。
- **不必先换显卡**：0.75× + 12 步（cfg2.5，保留负向与 LoRA）实测 **30.2s**，已经进入「几十秒」区间；0.75× + 8 步约 16s，cfg1.0 约 8s，但后两者会削弱负向通道 / 姿势 LoRA 效果，必须先做画质与姿势还原 A/B，不能直接当默认。
- **16GB 显存能改善，但不是「完美」**：权重总量约 20G，16G 仍放不下 UNet + 8B 文本编码器，只是换入换出更少；16G 卡（如 5070 Ti）显存带宽也从 672GB/s 提到约 896GB/s，会更快。24G 才能比较舒服地同时驻留。**更便宜的提速是 0.75×/1.0× + 降步数**；降步数必须先做画质 / 姿势还原 A/B，不能静默改默认。
- **批量投喂不是主因**：`submission.py` 只有 1 个 `job-submitter` 线程，但它在 `prepare`（读工作流 + 复制图片）+ `push_prompt` 后立即处理下一条，**不等待 ComfyUI 出图**；前端 `MAX_SUBMIT_CONCURRENCY=2`，每个 POST 入队后立即返回。ComfyUI 本机 GPU 串行执行，所以 N 张的完成顺序天然是一张接一张，N 张总时长 ≈ N × 单张。提高提交并发只会更快填满队列，不减少 GPU 时间。
- 可选优化（需用户选择，涉及画质/尺寸）：迭代用 0.75×、定稿用 1.0×、1.5× 仅最终出图；减少步数、换更大显存显卡、换更小的文本编码器/量化 UNet。不建议静默改默认。
- UI 已在画质档下方标注本机耗时参考（`studio-quality-time-hint`），避免再按 1.5× 盲跑。
