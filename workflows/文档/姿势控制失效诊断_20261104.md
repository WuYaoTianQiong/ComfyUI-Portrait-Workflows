# 图库专用工作流「姿势不生效」诊断报告

日期：2026-11-04
范围：`图库专用工作流/图库专用_QwenEdit_GGUF-Q5KM_三图_4步_全身构图*_自动裁切.api.json`
证据源：工作流 JSON、ComfyUI 节点源码、`input/pose_studio` 实传图、`output/pose_studio` 实出图、`ComfyUI/user/comfyui.log`
标注口径：本文所有结论分「实测确认」与「待验证」两档，未标注「待验证」的均为实测或源码直读。

---

## 1. 一句话结论（实测确认）

1. **这套工作流里没有任何姿势控制节点**：21 个节点中没有 ControlNet、没有 OpenPose/DWPose、没有 Depth 预处理器。姿势图（图3）只以"第三张参考图"的身份进入 `TextEncodeQwenImageEditPlus` 的 `image3`，属于**语义参考**，不是结构约束。
2. **双人失效是两个独立缺陷叠加**：提示词里从来没写过"两个人"；同时双人姿势图裁切后把画布变成近方形，直接诱导模型出单人半身/特写。
3. **慢的原因不是工作流，是显存**：12GB 卡上 Qwen Edit GGUF + Qwen2.5-VL 7B 必须 offload 约 5.1GB 到 CPU，单步从 11s 涨到 26s，实测 101–467s/张。

## 2. 实测数据

### 2.1 工作流实际结构（`..._自动裁切.api.json`，21 节点）

| 用途 | 节点 | 实际连接 |
|---|---|---|
| 图1 人像 | `#1 LoadImage` | → `#12/#13 TextEncodeQwenImageEditPlus.image1` |
| 图2 服装 | `#2 LoadImage` | → `#12/#13 .image2`，另 → `#22 缩放` → `#23 VAEEncode` → `#25/#27 ReferenceLatent` |
| 图3 姿势 | `#3 LoadImage` | → `#30 PoseTrimWhitespace` → `#12/#13 .image3`，另 → `#10 缩放到 1.0MP` → `#11 VAEEncode` → `#14 KSampler.latent_image` |
| 采样 | `#14 KSampler` | `steps=4, cfg=1.0, sampler=euler, scheduler=simple, denoise=1.0` |

关键事实：

- **`#12/#13` 没有接 `vae` 输入**。源码 `comfy_extras/nodes_qwen.py:93` 中 `ref_latents` 只在 `vae is not None` 时才生成 → 三张参考图**没有任何 VAE 侧参考 latent**，只走视觉语言编码器。
- **`ReferenceLatent` 只挂了服装**（`#25` 正向、`#27` 反向），人像和姿势都没有。
- **`denoise=1.0`**：`#11` 用姿势图编码出的 latent 作为初始画布，但 100% 重噪 → 结构信息在第一步就被抹掉，姿势图对采样的唯一硬影响只剩**画布宽高比**。
- **`cfg=1.0`**：负向分支（含 `#27` 反向服装参考）完全不参与计算，工作流自己的节点标题也写了"cfg=1 时不生效"。

### 2.2 姿势图真正进模型的分辨率（源码直读）

`comfy_extras/nodes_qwen.py:85-92`：

```python
total = int(384 * 384)          # 147,456 像素
scale_by = math.sqrt(total / (samples.shape[3] * samples.shape[2]))
```

三张参考图在进 VLM 前统一被缩到约 **384×384**。900×1200 的白模缩到 384 后，按前景占比折算：

| 类型 | 原图前景像素占比（>12 灰阶差） | 折算到 384² 后的人体像素 |
|---|---:|---:|
| 单人 | 2.69% | ≈ 3,970 px |
| 双人 | 9.32% | ≈ 13,740 px（两人分摊） |

也就是说：单人的"单手支撑·双腿斜向前伸"这类细节，在 VLM 眼里只有不到 4 千像素。

### 2.3 双人姿势改变了画布比例（实测确认）

上传图统一 768×1024；`PoseTrimWhitespace` 按内容边界裁切后：

| 姿势 | 裁切后包围盒宽高比 | 实出成品尺寸 |
|---|---:|---|
| 单人（`studio_pose_1793798710620`，单手支撑） | 0.741 | 880×1184（0.743） |
| 双人（`studio_pose_1793798261241`，双腿之间俯卧依偎） | 0.945 | 992×1056（0.940） |

双人俯卧图裁成**近 1:1 方图** → `ImageScaleToTotalPixels(1.0MP)` 生成方形画布 → 模型在方形画布里画一个人的半身/特写最"省力"。

### 2.4 真实产出对照（同一套人像 f71f980dde3 + 服装 SPR-0001 + 同一张双人姿势图）


## 5. 更正：ControlNet 路线当前**不可用**（2026-11-04 22:20 复核）

> 本节原先写的是「已实测成功：36.1s、2 人正确」。**该结论错误，现予更正并保留过程，避免后续会话踩同一个坑。**

`q21_depth_pair_00001_.png`（1024×1024）经像素级复核：

| 指标 | 数值 | 含义 |
|---|---|---|
| 肤色像素占比 | **0.47%** | 真人照片通常 5–15%，0.47% 说明几乎无皮肤 |
| 彩色度（三通道极差均值） | 58.74 | 伪彩映射的特征值 |
| 与 `q21_depth_pair_00002_` 对比 | 逐像素完全一致 | 同 seed 确定性输出，不是两次不同结果 |

改用「是真实照片 / 3D 渲染 / 深度图」这种提问复核后，VLM 判定为**深度图伪彩渲染**：只有蓝白渐变的人形轮廓，没有肤色、毛发、织物。
第一次误判的原因很明确：提问只问了「几个人 / 有无肢体崩坏」，没问「是否真人照片」——**核对口径不完整，不能算实测通过**。

同批次后续 4 组对照（全部执行成功、全部未出真人）：

| 配置 | 耗时 | 结果 |
|---|---:|---|
| ControlNet 深度图 + 编码器接 vae，cfg 1.0，strength 1.3 | 132.3s | 灰度深度图（肤色 0%、彩色度 1.26） |
| 同上，去掉 vae（`keep_vision=True`），cfg 1.0，strength 1.0 | 60.2s | 伪彩深度图（肤色 0%、彩色度 105.8） |
| 同上，cfg 2.5 + er_sde + beta | 88.2s | 伪彩深度图（暖色被误算作肤色 32.6%，实为深度渐变） |
| 白模 → Canny（0.4/0.8）→ ControlNet，cfg 1.0 | 72.2s | 蓝色线稿/卡通风，**1 人**（肤色 0%、灰度像素仅 5.6%） |

结论：**Fun ControlNet Union 在 cfg≈1 时不听提示词，直接把控制图当输出**；提高 cfg、换 Canny 都没恢复。原先「36.1s 双人正确」的说法作废，据此新建的工作流文件已删除，未进入 `图库专用工作流/`。

以下两类仍是**已实测确认**的负结果，可以继续引用：

- **DWPose 对姿势库灰白人体模型检出 0 个关键点**（`output/pose_diag/dw_pair_00001_.png`、`dw_single_00001_.png` 全黑、唯一色数 1）→ 骨架路线不可用。
- **干净版 Edit 三图 + 明确双人提示词 → 0 人静物**（`result_00018`）→ 提示词补不了人数。

详细接线与排除记录见 `文档/姿势控制改造方案_20261104.md`。

## 6. 上游开源配方的原始设计 vs 当前移植（关键：移植时丢了一条腿）

两个上游项目本机都有副本：`custom_nodes/ai-pose-gallery-zh`（网页合成台 + ComfyUI 插件）、`F:/ComfyUI_Migration/qwen21-nsfw-pose-skill`（Qwen 2.1 控姿配方）。

### 6.1 `ai-pose-gallery-zh` 自己写明了"姿势只做语义"

`docs/comfyui-local.md` 原文：

> **只有人像和服装**通过 `ReferenceLatent` 作为像素级参考；**姿势图只用于语义理解**。
> 实测如果把线稿人偶姿势图也作为像素参考，生成结果会照搬人偶的关节球和分块线条。

也就是说：**我们现在的三图工作流，就是上游"姿势不精确"的那条路**，作者本人在文档里承认了。

### 6.2 上游的精确控姿方案在另一处：`use_depth` → ControlNet Depth

README 原文：

> 原生 ComfyUI 自定义节点插件……姿势与配方节点内置 **`use_depth` 深度图切换，可直接接入 ControlNet Depth**

插件源码 `comfyui_plugin/nodes.py:108` `_pose_image_rel_path(item, use_depth)` 就是该开关：打开后返回 `img/depth/*.webp`。

**我们移植到 atelier/gallery-web 时，只搬了"深度图当第 3 张参考图"，没搬"深度图 → ControlNet Depth"。** 这是姿势不精确的直接原因。

### 6.3 `qwen21-nsfw-pose-skill` 记录了"没有 LoRA 人偶会被完全忽略"

`SKILL.md` §6 原文：

> The pose source must be a textureless **3D mannequin render** …… Photos and illustrations as pose references do NOT work: the model composites the reference person as a second person, or redraws the reference person entirely (retested 2026-10-16 — all variants failed).
> **VNCCS PoseStudio LoRA @ 1.0 is mandatory** — without it the mannequin is ignored entirely (**3 no-LoRA controls**).

- 配方：image1 = 人偶（姿势），image2 = 角色（身份），prompt `replace the pose of <image 2> with the pose of <image 1>…`，25 步 / cfg 1 / euler / simple。
- 本机**其实已装**两个 VNCCS LoRA：`loras/qwen/VNCCS/VNCCS_QIE2511_PoseStudio_ART_V5.9.safetensors`（Edit 2511 用）、`loras/VNCCS_QI2_PoseStudioV1.1.safetensors`（2.1 用），但**都没接进工作流**。

### 6.4 按上游配方实测的结果（今天补做）

| 配方 | 步数 | 耗时 | 双人结果 |
|---|---:|---:|---|
| 现有 Edit 三图（无 LoRA，姿势当 image3） | 4 | 101–137s | 1 人 |
| Edit 三图 + `VNCCS_QIE2511` LoRA + 顺序对调（image1=姿势） | 4 | 120.9s | **0 人（幽灵穿搭）**：VNCCS 训练在 20–25 步，与 4 步 Lightning 冲突 |
| Qwen 2.1 + `VNCCS_QI2` LoRA + 三图（image1=姿势、image2=人像、image3=服装） | 25 | **56.3s** | **1 人**：俯视、姿势近似、服装正确、真人质感（比现状大幅改善，但双人仍不行） |
| **Qwen 2.1 + Fun ControlNet Union（深度图）** | 25 | **36.1s** | **2 人正确** |

结论：**VNCCS 配方是"单角色姿势迁移"，天生只处理一个人**（作者原文 `Single person, identity kept`）；双人必须靠 ControlNet。
