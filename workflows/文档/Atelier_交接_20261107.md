## 3. 下一步：第 3 波剩余

### 3.1 标签单轨（已完成方案 A）

**现状**
- `prompts.tags` **文本**是编辑/写入真源；`sync_prompt_tags()` 立即把文本解析进 `entity_tags`。
- 所有筛选 / 计数 / 详情读 `entity_tags`。
- 问题：`PUT /api/tags/{id}` 改名只改 `Tag.name`，不回写 `prompts.tags` 文本；下次保存提示词时，旧文本会把旧标签名“复活”。

**已完成方案 A**
1. `app/services/tagging.py` 新增 `rename_tag` / `delete_tag_with_refs` / `_sync_prompt_tag_texts`：
   同一事务内更新 `Tag`、精确改写所有 `prompts.tags` 文本、重算 `entity_tags`。
2. `app/routers/tags.py` 的 PUT/DELETE 已改为调用 service。
3. 测试见 `tests/test_tag_rename.py`：改名不复活、带空格/中文分隔符、冲突 400、删除无残留。

> 残余边界：如果用户在改名**之前**打开了某条提示词的草稿，草稿里仍是旧文本，保存时仍可能重建旧标签。彻底解决需要方案 B（`prompts.tags` 不再作为写入真源）。

**备选方案（B，彻底单轨）**：`entity_tags` 为唯一真源，`prompts.tags` 只作为导出/展示的派生字段；所有写入改为标签 ID/名称列表。改动面更大，需同步 `PromptDetail`、导入导出、`usePromptDraft.ts`。

**注意**：不要只改关联表而不改文本，否则下次编辑触发全量重算会把改动冲掉。

## 4. 必须遵守的约定

1. **双入口不合并**：Composer 管文本/碎片，Studio 管三槽参考合成。
2. **行为变更先拍板**：批量条目化 / “一 job 多图”仍属产品决策，不要顺手改；`【避免】` 被提前剥离与取消文案已于 2026-11-07 收尾时修复（见 §6）。
3. **一次一批提交**：改名与改行为分开；提交前 `git status`，并发工作区只提交自己的文件；同一文件混批次时用 hunk 级暂存。
4. **契约生成**：改 `schemas.py` / 路由后必须 `python tools/gen_api_types.py`；CI 会比对生成物哈希。
5. **CRLF 仓库**：批量改文件后确认没有混入 LF；前端构建产物 `web/` 入库。
6. **SQLite 单进程**：`job_state` 单写者 + 内存队列，不支持多 worker。
7. **测试隔离**：pytest 用临时库；生产迁移前先 `python tools/backup_db.py --tag before_xxx`。
