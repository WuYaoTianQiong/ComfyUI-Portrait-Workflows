## 1. 目标与非目标

### 1.1 目标

合成台的真实业务是**四维笛卡尔积**：`槽位组合 × 工作流 × 画质档 × 比例`，最多 100 组、每组一个 job。当前界面把它当普通表单处理，用户看不到"我要生成哪些图"。本轮重构的唯一主线：

> **把"将生成什么"变成页面的第一等公民**——素材能完整看见，组合能逐组看见，工作流能一眼看见，导航不占地方。

### 1.2 非目标（本轮不做）

- 不改后端任何接口（组合计算全部复用已导出的前端纯函数）。
- 不做配方草稿多套保存/切换。
- 不做结果图的收藏、投喂、删除（归画廊）。
- 不重写 `Lightbox.vue`、`DropZone.vue` 的既有调用方行为（只允许新增 variant）。

## 3. 设计原则

1. **所见即所生成**：页面上必须存在一份可逐行阅读的"任务清单"，它和最终 `POST` 的组**同源**（同一个 `buildBatchGroups`），不是另写的说明文案。
2. **素材区以图为主**：槽位是"一小墙图"，不是"一张卡 + 一句被截断的话"。
3. **就地编辑**：加入/移除/排序素材、移除工作流，都在当前页面完成，不强迫跳页签。
4. **常驻出口**：主按钮与"将生成 N 张"永远在视口内（sticky 操作条）。
5. **拆而不是堆**：`ReferenceStudioTab.vue` 现 2306 行单文件，本轮拆成 5 个子组件，每个 ≤300 行。

## 5. 模块设计

### M1 左导航可折叠（对应 H5）

| 项 | 规格 |
|---|---|
| 展开态 | 180px（现 200px） |
| 折叠态 | 64px 图标 rail，图标 16×16 stroke，36×36 点击区，`title` + 自定义 tooltip |
| 折叠按钮 | rail 顶部右缘 chevron（`aria-expanded`），另支持快捷键 `[`（可选 P2） |
| 记忆 | `localStorage: pb.reference_nav_collapsed_v1`，默认展开 |
| 断点 | ≥1024 手动控制；768–1023 强制折叠；<768 回退现有顶部横向药丸条（保持现状不动） |
| 保留契约 | `role="tablist"` / `role="tab"` / `aria-selected` / `id="reference-tab-*"`、`ReferenceView.spec.ts` 断言 |
| 收益 | 内容区 1152 → 1288px（+136px），三槽单卡 199 → 约 250px |

需要新画 6 个图标：图库总览（网格）、姿势（人形）、服装（衣架）、人像（头像）、合成台（图层）、设置（齿轮）。统一 `stroke-width 1.3, currentColor, fill none`。

**新组件 `StudioSlotPanel.vue` 替代 `ReferenceSlotCard.vue`**（后者仅本页使用，可整体替换）。

```
┌──────────────────────────────┐
│ 人像   4 张      更换   清空 │  28px 头部
│ ┌────┐┌────┐┌────┐           │
│ │img ││img ││img │  3:4 网格  │  缩略图 2 或 3 列，内部纵向滚动
│ │  × ││  × ││  × │           │  hover 右上角 ×（触屏常显）
│ └────┘└────┘└────┘           │
│ ┌────┐                       │
│ │img │                       │
│ └────┘                       │
│ ＋ 继续选人像                 │  底部整宽虚线按钮 → 跳库页签
└──────────────────────────────┘
```

- **取消 4 张上限**：`MEDIA_PREVIEW_LIMIT` 删除；缩略图网格 `max-height: 3 行`（约 9 张）+ `overflow-y: auto`，数量徽标始终显示真实总数（4 / 12 / 30）。
- **单项删除**：缩略图 `×` → `draft.removePortrait(item.id)`；姿势槽按 `item.id`，服装同理。删除后 toast 提示"已从人像槽移除 1 张（剩 3 张）"。
- **点击缩略图**：开 `Lightbox`（现状保留，只读）；**不在灯箱里做删除**，避免改共享组件。
- **空态**：整卡虚线边框 + 居中图标 + 主文案「+ 选人像」，可点整卡跳库页签（不再出现 83px 宽的截断文字）。
- **排序（P2，可选）**：拖拽调整顺序，影响组合顺序与种子编号；先在文档标注，不阻塞主流程。
- **键位/ARIA 修复**：卡片不再 `role="button"` 包裹按钮（A9）；改为普通 `section` + 独立"添加"按钮。

### M3 生成清单：笛卡尔积可视化（对应 H1，本方案核心）

**新组件 `StudioMatrix.vue`**，数据源直接复用 `buildBatchGroups()`（已存在、已导出，前端纯函数，不请求后端）。

数据结构（已在 `useReferenceRecipe.ts` 中）：

```ts
buildBatchGroups({ portrait, costume, pose, workflows, qualities, ratios, baseSeed })
// → RecipeBatchGroup[] { index, slots{portrait,costume,pose}, workflow, quality, aspectRatio, orientation, seed }
```

界面形态（**分组清单**，不是表格）：

```
生成清单                                  32 组  ▓▓▓▓░░░░ 32% / 上限 100
[按配方分组 ▾]                          [展开全部] [只看工作流 Qwen]

▾ 人像A × 服装B × 姿势C                              2 工作流 × 2 尺寸 = 4 组
   #1  [图][图][图]   Qwen三图·25步    1024·16:9    seed 100000
   #2  [图][图][图]   Qwen三图·25步    1024·9:16    seed 100001
   #3  [图][图][图]   Flux三图·6步     1024·16:9    seed 100002
   #4  [图][图][图]   Flux三图·6步     1024·9:16    seed 100003
▸ 人像A × 服装D × 姿势C                              4 组
▸ 人像B × 服装B × 姿势C                              4 组
```

| 项 | 规格 |
|---|---|
| 分组维度 | 默认按"槽位组合"分组（组头 = 三联缩略图或名称；组尾 = `N 工作流 × M 尺寸 = K 组`），可切"按工作流分组"（P2） |
| 默认展开 | 仅第一组展开，其余折叠；`展开全部` 切换 |
| 行内容 | `#序号` + 三槽缩略图（24×32，缺槽显示灰底"空"）+ 工作流短名 + 尺寸（caps 不支持时显示"跟随参考图"）+ 种子 |
| 常驻计数 | `N / 上限 100` + 线性进度条（满足 `需求对齐 §3.7` 的"常驻展示"要求，形式从徽标升级为进度条 + 清单） |
| 超限 | 整块转危险色；提示"减少 1 张人像可减 8 组"（按各维数量推算影响最大的维度） |
| 空态 | "三槽都为空：先选素材，这里会逐行列出每一张要生成的图" |
| 性能 | 上限 100 行 × 3 图 = 300 个 `<img>`，全部 `loading="lazy"` 且复用 `slotView` 的 thumb URL；不做虚拟滚动 |
| 可选项（P2） | 行级"跳过该组"（需给提交增加 `skipIndexes`）；"只看某工作流/某尺寸"筛选 |

**为什么不做真表格**：一次 100 行的 6 列表格在 1440px 下可读性差，且缩略图列会很窄；分组 + 折叠既能压住信息量，又能保留"逐组可数"的核心诉求。

### M5 结果区（全宽 + 组映射，对应 A1 / A7）

- **布局**：全宽，按批次纵向排列，最新在上；每批 `批次N · HH:MM:SS · 状态 · 组数/张数 · 耗时`，右侧动作 `复用参数 / 清理已结束 / 任务中心`。
- **网格**：`repeat(auto-fill, minmax(180px, 1fr))`，容器 `3/4` + `object-fit: contain`（**不再裁图**），底部一行 `#组号 · 工作流短名 · 尺寸`。
- **组映射**：`useReferenceRecipe.ts` 的 `runBatch` 中，`submitted` 已携带 `{ group, response }`，只需在批次对象上新增

  ```ts
  groupResults: Array<{ group: RecipeBatchGroup; jobId: number; urls: string[] }>
  ```

  在 `pollOutcomes` 循环里按 `result.outcome.group` 归档；`batch.results` 扁平数组**保留不动**（兼容现有 UI 与测试）。失败组同样进 `groupResults` 并标记 `error`，网格里显示灰块 + 原因。
- **点击**：打开 `Lightbox`（`readonly`、`file-actions=false`、`can-open-gallery=false`），复用 M2 的同一套 item 投影。
- **空态**：180px 轻量块（不再 460px），文案「提交后会在这里按批次展示；GPU 串行执行，新批次可继续提交」。
- **复用参数**：把该批的 `groups[0]` 槽位回填草稿 + 工作流/尺寸选择（`draft.hydrate` 已有），toast「已回填批次 1 的配方」。

## 12. 第二轮：空间利用率重排 + 白模/深度定案（2026-11-06 已落地）

### 12.1 背景

P0–P2 落地后实测发现两个遗留问题：

1. **横向大量留白**：`ReferenceStudioTab.vue` 把左栏写成 `grid-column: 1 / -1`、右栏 `display: contents`，
   导致**所有区块都是全宽单列**。1440 视口下参数卡宽 1172，而画风下拉 / 种子输入只有 336（填充率 29%）；
   「＋添加工作流」按钮一行占满 1172；体态开关行宽 1172、内容 200。
2. **「白模 / 深度」语义错位**：开关位于卡片 header 之下、图墙之上，看起来像"作用于下面这些图"，
   实际是整槽 `setPoseMode()`；且用户无法判断它是否影响出图。

### 12.2 白模/深度：已验证为**纯预览**（不改后端）

三条独立证据（均不消耗 GPU）：

| 证据 | 结论 |
|---|---|
| 拦截 `POST /api/reference/recipes`，在「白模 → 深度 → 白模」下各提交一次：3 份真实请求体逐字段一致，且**请求体无 depth / kind 字段** | 后端拿不到模式信息 |
| 同刻读槽位缩略图 `src`：`kind=image` ↔ `kind=depth` 切换生效 | 开关本身是工作的，只是只改显示 |
| 直接调后端 `_recipe_entry("pose", id)` → `img/<id>.png`；深度图在 `img/depth/<id>.webp`，仅图片端点使用；工作流 JSON 中 `depth` 0 命中 | 注入工作流的是白模原图 |

**定案（选项 A）**：不做逐图开关（做了就是假功能），改为

- 开关移入卡片 header，位于「数量」与「更换 / 清空」之间；
- 卡片底部常驻说明「白模 / 深度仅影响预览，不影响出图」（`data-testid="studio-pose-depth-note"`）；
- 每格缩略图左下角加「白 / 深」角标；
- 选中态改用 `--surface-card`，不再用主色，避免次要控件抢视觉。

若将来要让深度图真正参与出图（归档文档《姿势控制改造方案》的意图），需单独立项：
`RecipeRequest` 增 `pose_kind`、`_resolve_slot` 按 kind 解析、矩阵与提示词同步区分，并补一条 e2e 断言
（请求体 `pose_kind` 必须与 UI 一致）。
