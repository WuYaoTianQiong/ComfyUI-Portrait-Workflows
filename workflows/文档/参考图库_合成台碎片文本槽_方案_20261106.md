# 参考图库 · 合成台碎片文本槽方案（2026-11-06 · 修订版）

> 目的：让 `/reference?tab=studio` 的三个参考图槽（人像 / 服装 / 姿势）可以**不投图、改用碎片组合**，
> 并把拍摄视角、场景环境、光影色调、画风技术等碎片**选择性**填进提示词。
>
> **修订说明（v2）**：工作流已收敛为唯一一个 `图库专用_Qwen21+VNCCS_三图_25步_单人.api.json`
> （QwenEdit ×3、Flux2 ×2 已移出），原方案中为「多工作流差异」设计的分支全部作废，
> 同时暴露出 3 个此前被多工作流掩盖的既有判定缺陷，列为 P2 前置必改项。

## 一句话结论

只剩 Qwen21 一个工作流后，方案从"二维能力矩阵"退化为"一条硬约束（至少留 1 张图）"，
**大幅度简化**；但 `body_mode_auto` / `faceless` / `is_pair` 三处判定都以"槽位有图"为前提，
文本槽会静默改变它们的语义，必须先改这三处；
另外负面提示词从"不值得做"**反转为"应该补"**（唯一工作流负向真正生效，且后端字段已现成）。

## 1. 决策表（v2 与 v1 的差异已标注）

| # | 决策 | 结论 | 变化 |
|---|---|---|---|
| D1 | 文本槽范围 | 三槽都能切文本 | 不变 |
| D2 | 修饰碎片与 `prompt_suffix` | 并存：结构化碎片在前，自由文本兜底 | 不变 |
| D3 | 碎片池范围 | 全库所有提示词（不限分类/标签） | 不变 |
| D4 | 负面提示词 | **补真 `negative_prompt` 字段** | **反转**（v1 为"不做"） |
| D5 | 页面级互跳 | 不做 Composer ↔ Studio 状态互传 | 不变 |
| D6 | Studio 结果存为提示词 | 不做（污染碎片池） | 不变 |
| D7 | 姿势槽文本化 | **允许但排在最后**，UI 显著提示质量损失 | **新增** |

### D4 反转的依据（v1 判错的原因）

v1 基于"6 个工作流只有 1 个负向生效"判定不值得做。现在只剩这一个，而它恰好是生效的那个：

| 事实 | 证据 |
|---|---|
| 编码节点自带负向字段 | node8 `TextEncodeQwenImage21`，inputs 含 `negative_prompt` |
| 负向真的接进采样 | node9 `KSampler.negative = ["8", 1]`，`cfg = 2.5`（>1） |
| 后端字段已现成 | `editor.py:110` `FaceswapRequest.negative_prompt`，`editor.py:591` 已透传给 `inject_prompt` |
| 缺的只有一层 | `reference_library.py:864` 构造 payload 时只传了 `prompt`，没传负向 |

→ 成本：`RecipeRequest` 加字段 + payload 传一行 + 前端一个输入框（常显，不再"忽隐忽现"）。
`inject_prompt` 里 `_detect_negative_effectiveness` 会算成 True，负向正常写入；不需要任何新逻辑。

**修饰层不再单独做「避免项」文本**（v1 的替代方案），避免与真负向重复语义。

### 明确不做

- 不新增碎片表、不新增 `FRAGMENT_TYPES` 第 9 类。
- 不做"三槽全文本"（0 张图）—— 见 §3 C1（但列了一个待验证机会点）。
- 不做权重语法（`(x:1.2)` / `::`）。
- 不做每槽独立工作流（本来也只剩一个）。

## 2. 现状盘点

| 页面 | 本质 | 产物 | 关键代码 |
|---|---|---|---|
| `/prompt` | 提示词库 CRUD，碎片只是**筛选维度** | 提示词记录 | `app/routers/prompts.py`、`views/PromptView.vue` |
| `/composer` | 库文本按 `【类型】` 解析成碎片，8 类各一槽 | 提示词字符串 → `/api/composer/run` | `app/routers/composer.py`、`composables/useComposerCanvas.ts` |
| `/reference?tab=studio` | 三槽图片 → `LoadImage`，提示词后端自动生成 | ComfyUI 任务 | `app/routers/reference_library.py`、`services/recipe_prompt.py` |

要点：
- **碎片没有独立表**，`composer._get_fragment_data()` 直接解析 `prompts.prompt` 的 `【类型】` 块。
- **Studio 提示词不是标签堆**，是强约束 bullet 句，由 `recipe_prompt.build_recipe_prompt()` 生成。
- **空槽已支持裁剪**：`_trim_unfilled_slots()` 删空槽的 `LoadImage` + `images.image_N` 键，并按真实图号重写 `index_map`。

### 唯一工作流的真实结构（必须记住，标题是错的）

`图库专用_Qwen21+VNCCS_三图_25步_单人.api.json`，11 个节点：

| 节点 | 类型 | 标题 | 真实角色 |
|---|---|---|---|
| 1 | LoadImage | 图3：姿势参考 (Pose) · 深度图 | **image_1 = 姿势** |
| 2 | LoadImage | 图1：人像参考 (Portrait) | **image_2 = 人像** |
| 3 | LoadImage | 图2：服装参考 (Costume) | **image_3 = 服装** |
| 7 | LoraLoaderModelOnly | VNCCS 姿势 LoRA（QI2 v1.1，必须 1.0） | 姿势专用 LoRA |
| 8 | TextEncodeQwenImage21 | 正向提示词 | `prompt` / `negative_prompt` / `images.image_1..3`，输出 positive+negative+latent |
| 9 | KSampler | 25 步 · cfg 2.5 | — |

**标题里的「图N」与 `image_N` 编号是错位的**：姿势是图1、人像是图2、服装是图3。
`loadimage_role()` 只认角色关键词、`_build_index_map()` 只信 `image_N` 键 —— 这是对的，不要"顺手修正"标题。

## 3. 硬约束

### C1 至少留 1 张图（唯一不可绕过的约束）

`list_valid_workflows(scope="studio")` 要求 ≥1 个 `LoadImage` 且标题能识别角色；
`create_reference_recipe` 里 `total == 0` 直接 400（文本槽不计入 `filled`）。
三槽全文本 = 文生图，引导去 `/composer`。

> **待验证机会点**：node8 的 latent 输出来自 `resolution=1024`，理论上不依赖图片。
> 若"删掉全部 LoadImage + images 键"仍能出图，则 0 图成立，Studio 可自给自足（但与 Composer 功能重叠）。
> 实验方式：拷贝工作流删 3 个 LoadImage 与 `images.*`，直接 `POST /prompt`。**本轮不做，只记录**。

### C2 可空槽：Qwen21 任意槽（v1 的二维矩阵作废）

依据 `文档/参考图库_合成台工作流实测矩阵_20261106.md`：Qwen21 的 **7 种非空组合全部 done**
（人像 / 服装 / 姿势 / 人像+服装 / 人像+姿势 / 服装+姿势 / 三图齐全）。

| 工作流 | 可空槽 | 额外约束 |
|---|---|---|
| Qwen21+VNCCS | 人像、服装、姿势 | 至少留 1 图 |

因此 v1 的 `optional_slots` 二维矩阵设计**降级**为：后端按工作流探测一次、返回可空槽位数组
（当前恒为 3 个），前端只用来做"至少留 1 图"校验与未来扩展。**不必**为矩阵写置灰逻辑。

### C3 文本槽会静默改变 3 处既有判定（P2 前置必改）

这是 v2 审核新发现的**最严重风险**：现有代码用"槽位是否有图"承载业务语义，
文本槽让"没图但有内容"成为合法状态，三处判定会给出错误结论。

| # | 位置 | 现有逻辑 | 文本槽下的后果 | 修正 |
|---|---|---|---|---|
| C3-1 | `create_reference_recipe` | `if body_mode == "costume" and not filled["costume"]: body_mode = "bare"` | 服装槽切文本 → 被强制判定为**素体展示**，提示词写「不穿任何服装」，与服装碎片直接矛盾 | 条件补 `and not costume_text` |
| C3-2 | `build_recipe_prompt` | `faceless = not portrait and bool(costume and pose)` | 人像槽切文本 → 误判**无脸展示**，会把用户描述的脸抹掉 | 改为 `not (portrait or portrait_text)` |
| C3-3 | `build_recipe_prompt` | `is_pair = pose.id.startswith("pair")` | 姿势槽切文本 → 双人语义彻底丢失 | 文本槽无法表达，需显式"人数"开关或直接禁用文本槽的双人场景 |

> C3-1 的背景注释值得保留：缺服装时 Qwen 会自由发挥（实测连续出裸体），所以这条兜底不能简单删掉，
> 只能扩成"既无服装图也无服装文本"。

### C4 碎片文本长度不受控

实测 `atelier/data/prompts.db`：**355 条提示词 → 2175 条去重碎片**，单条最长 783 字（画风技术），
人物服饰最长 583 字。三槽各 1 条 + 4 条修饰，最坏可拼出 3000+ 字。

处置：单槽软上限 2 条碎片；UI 显示字数；不静默截断。Qwen21 能吃长中文提示词（有专门工作流），
但仍需避免无意义堆砌。

### C5 第 4 张上传块在当前工作流下必然 400

工作流只有 3 个 `LoadImage`（无 `extra` 槽），`total > input_count` 会直接 400
「该工作流只有 3 个输入，但提交了 4 张」。工作流收敛后这个功能 100% 不可用 → 应隐藏或禁用。

### C6 姿势槽文本化的质量风险最高

工作流挂了 `VNCCS 姿势 LoRA`（`LoraLoaderModelOnly`，weight 固定 1.0），专为姿势/深度图训练。
姿势槽切纯文本后，LoRA 仍在作用但**没有骨架输入**，姿势还原会明显退化。
→ D7：姿势槽文本化允许但不推荐，排在实施顺序最后，UI 显著提示。

## 4. 数据契约

### 4.1 前端槽位状态

`RecipeSlotKey = 'portrait' | 'costume' | 'pose'` 不变，槽值仍是数组（多选）。新增模式：

```
RecipeSlotMode = 'image' | 'text' | 'empty'
槽位 = { mode, items: 条目[]（image 用）, fragments: {type, content}[]（text 用） }
```

- `text` 槽**不进 LoadImage**，等价空槽裁剪；碎片只作为提示词来源。
- **同槽多碎片视为一个整体**（槽内拼接），不参与笛卡尔积维度。
- 持久化沿用 `pb.reference_studio_v1`；缺 `mode` 的旧数据按 `items.length ? 'image' : 'empty'` 推导。

### 4.2 后端提交体

`RecipeRequest` 新增可选字段，缺省走旧逻辑：

| 字段 | 类型 | 说明 |
|---|---|---|
| `portrait_text` / `costume_text` / `pose_text` | `str` | 该槽碎片编译结果（已按 §5 渲染成指令句） |
| `modifier_fragments` | `str` | 修饰层编译结果（视角/场景/光影/画风） |
| `negative_prompt` | `str` | 真负向（透传给 `FaceswapRequest.negative_prompt`，字段已存在） |

校验规则（P2 一起做）：
- 某槽同时给 `*_id` 与 `*_text` → 400（互斥，不猜优先级）。
- `body_mode='bare'` 且给了服装文本 → 400（与现有"bare + 服装图"同源）。
- 所有槽既无图也无文本 → 400（等价现有 `total == 0`）。
- 文本槽不计入 `filled`，仍交给 `_trim_unfilled_slots` 裁剪（**不加新分支**）。

### 4.3 工作流能力字段（降级）

`GET /api/workflows?scope=studio` 增加：

```
optional_slots: ['portrait', 'costume', 'pose']   // 该工作流可裁掉的槽位
```

实现：复用 `_resolve_trim_plan()` 逐槽探测后按 mtime 缓存（与 `_slot_cache` 同策略）。
当前只有 1 个工作流 × 3 槽，首次探测成本可忽略；保留探测而不是硬编码，避免将来加工作流踩坑。

## 5. 提示词渲染规则（同构替换，不是追加）

碎片是逗号标签式短句，Studio 是 bullet 指令式长句，**直接 append 会互相干扰**。
正确做法：文本槽与图片槽在提示词里**占同一个位置**，只换句式。

| 槽 | 图片版（现有） | 文本版（新增） |
|---|---|---|
| 人物 | `• 人物：图2中的人物，保持其脸型、五官、发型（X）和发色一致…` | `• 人物：一位 {人物面部碎片}；{人物身材碎片}。肤色与质感按风格要求呈现。` |
| 服装 | `• 服装：让人物穿上图3中展示的整套服装和配饰（参考名称：X）…` | `• 服装：人物穿着 {人物服饰碎片}，颜色、款式、面料与配饰以文字描述为准。` |
| 姿势 | `• 姿势：严格复现图1中人体模型的姿态…不要军姿，不要 T-pose` | `• 姿势：{姿态动作碎片}。` + **保留**"不要军姿、不要 T-pose、不要双脚并拢" |

修饰层（不占图位，按 8 类固定顺序，插在"补充要求"之前）：

```
• 拍摄视角：…
• 场景环境：…
• 光影色调：…
• 画风技术：…
• 补充要求：…        ← prompt_suffix（原样保留，与碎片并存）
```

约束：
- 文本槽**不写"图N"**；`_figure_no()` 只对已填图片槽生效（现有逻辑已按 `filled` 过滤）。
- 注入 CLIP 前仍需 `strip_headers()`（`【类型】` 只做人读标记）。
- 类型去重按 `type||content` 精确匹配，与 composer 一致。

## 6. 图号错位风险（P2 头号验收项）

`_build_index_map()` 按 `images.image_N` 的 N 写"图N"，且**裁剪后不压缩重排**。
当文本槽导致**靠前的图位被删**时（典型：姿势槽切文本 → `image_1` 被删），
提示词仍写"图2人物 / 图3服装"，而模型实际只收到 2 张图（人像、服装）。

矩阵只验证了"能出图"（HTTP 200 + 有产出），**没有验证编号语义是否正确**。
这是既有行为，不是本次引入，但文本槽会**大幅提高触发频率**。

处置：
1. P2 验收必须包含「姿势槽文本 + 人像图 + 服装图」，人工确认服装/人像没有互换；
2. 若错位成立，改法是把 `index_map` 改成**裁剪后的压缩序号**（而非原始 `image_N`），
   即 `_build_index_map` 按 fill 顺序重新编号 —— 这会改动既有行为，需单独评估。

## 7. 联动边界

### 做什么

| 项 | 理由 | 成本 |
|---|---|---|
| 复用 `GET /api/composer/fragments` 碎片池 | 唯一合理碎片来源，不新建表 | 无（现成） |
| 复用 `services/fragment_syntax.py` | 解析/渲染/去重单一真源 | 无（现成） |
| 碎片卡片显示来源 + 跳 `/prompt/:id?frag_type=xxx` | 深链已存在，单向、不改状态 | 极低 |
| dry-run 预览即时反映文本槽与负向 | `previewPrompt` 已在（防抖 400ms） | 低 |

### 不做什么

| 项 | 理由 |
|---|---|
| Composer → Studio 跳转 | Composer 出口是 `/api/composer/run` 直接出图，绕道 Studio 投图无收益 |
| Studio → Composer 跳转 | `【类型】` 与 bullet 指令句范式不同，互传必有损 |
| Studio 结果「存为提示词」 | 生成的是 500-800 字 bullet 长句，会被 composer 当碎片解析，污染 2175 条池子 |

判据：**要的是数据层复用，不是页面级跳转。**

## 8. 分批实施

### P1 修饰碎片层 + 负向 + 隐藏第 4 张（低风险先行）

- 修饰层 4 类碎片 + `modifier_fragments` 渲染（§5）。
- `negative_prompt` 打通：`RecipeRequest` → payload → `FaceswapRequest`（字段已存在），前端常显输入框。
- 隐藏/禁用第 4 张上传块（C5）。
- **不动**槽位模式、不动 `filled`、不动裁剪。
- 验收：同一组图仅加/去修饰碎片与负向，dry-run 预览差异符合 §5；实际出 1 张确认负向生效
  （对比 cfg 2.5 下负向写「扭曲的手」前后手部质量）。

### P2 三槽文本化（含 C3 三处修正，风险最高）

顺序（由易到难，每步独立验收）：**人像 → 服装 → 姿势**。

1. **前置必改** C3-1 / C3-2 / C3-3（§3），否则文本槽语义直接错。
2. 前端槽位加 `mode`，`StudioSlotPanel` 加「图片 / 文本」分段控件 + 碎片选择弹层。
3. 碎片弹层按 `fragment_type` **分类懒加载**（单类 224–307 条），带前缀搜索；
   **不要**一次拉全部 8 类（2175 条、400KB+，渲染必卡）。
4. 后端 `build_recipe_prompt` 加文本分支（§5 对照表）。
5. 互斥校验（§4.2）。
6. **验收（必须真出图）**：
   - 人像文本 + 服装图 + 姿势图 → 脸是否被抹掉（C3-2 回归）；C3-1 是否误判素体；
   - 服装文本 + 人像图 + 姿势图 → 服装是否被强制素体（C3-1 回归）；
   - 姿势文本 + 人像图 + 服装图 → **图号是否错位**（§6）、姿势还原度是否可接受（C6）；
   - 三槽各有图（回归）→ 与改动前逐像素/肉眼一致。

### P3 能力标注与收尾

- `/api/workflows?scope=studio` 加 `optional_slots`（§4.3）。
- 前端：0 图时引导跳 `/composer`；文本槽在工作流不可空时置灰（当前恒可空，逻辑留作扩展）。
- 验收：6 种槽位组合（3 单文本 / 3 单图）逐一提交，前端拦截与后端 400 文案一致。

## 9. 风险与坑

| 风险 | 处置 |
|---|---|
| **C3 三处判定语义漂移** | P2 第 1 步强制先改，三处各配一条回归用例 |
